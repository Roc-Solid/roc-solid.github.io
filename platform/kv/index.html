The platform · Kv

Values in memory, by key

Kv keeps values by key in the server's memory, for as long as you say or until the server stops. Nothing goes to disk: a restart forgets everything. Use it for what is cheap to lose and read on many requests: rate-limit counts, a cache, a one-time token. A value is any type JSON can encode, read back as the type its reader asks for.

Counting: a rate limit#

Kv.increment! counts atomically: two requests at once both count. A counter's time to live starts when it is made and later increments don't move it, so it counts in windows: here, one minute from an address's first try.

Once: a sign-in's state#

Kv.take! returns a value and forgets it in one step. The state another site sends back completes one sign-in; a second use finds nothing. Of two requests taking one key at once, one gets the value, the other NotFound.

The operations#

Every operation is atomic. Each that keeps a value takes a time to live, { ttl_ms }; 0, the default, keeps it until the server stops.

  • Kv.set!(key, value, { ttl_ms }) keeps a value, replacing what was there. Kv.get!(key) reads it: NotFound if missing or expired, BadValue(why) if it isn't the type asked for. Kv.delete!(key) forgets it.
  • Kv.increment!(key, by, opts) adds to an integer (from 0) and returns the new value: counts and rate limits.
  • Kv.add!(key, value, opts) keeps a value only if the key is empty, else answers Exists. Of two requests adding one key, one wins: a claim, or a request seen once (an idempotency key).
  • Kv.take!(key) reads a value and forgets it: a one-time token.
  • Kv.swap!(key, was, value, opts) replaces a value only if it is still was, else answers Changed. To update a value from its old one (a tally, a list of overrides), read, swap, and on Changed read again and retry, so concurrent updates never lose one.
  • Kv.push!(key, value, { keep }) puts a value at the front of a capped list, keeping its newest keep; Kv.list!(key) reads it, newest first.

The store holds 64 MiB (--kv-max-mb, or KV_MAX_MB); past that, the least recently used values go, so a cache can't grow without end. By convention, a key starts with its owner (login:…, email:mailbox), so a package's keys never meet an app's. An app runs as one server, so there is one store, with no network between it and your code.

What must survive a restart belongs in a table (the database) or an actor. Every kind of state, side by side: which to use.

Tested

The platform's tests let a value expire, count 200 increments at once, cap a list, and pass the limit to see the least recently used values go.
