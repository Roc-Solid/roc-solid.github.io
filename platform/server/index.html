The platform · the server

Roc compiled to native code, in a Rust host

An app's server is one executable: your Roc compiled to machine code, linked with a Rust host (tokio and hyper). The host answers HTTP, runs your code for each request, keeps a crash to its request, and frees the memory used. Your Roc decides what each request gets; the host carries it out.

Running it#

rocx dev runs the server with --dev. A built executable takes these options (with the environment variable that does the same in parentheses):

  • Request bodies. The host reads a body whole before your code runs: up to 16 MiB, or --max-body (bytes, KiB, MiB or GiB, as in 64MiB). A larger body gets 413.
  • Static files. --static and --file serve files typed by their extension (cache-control: no-store under --dev). A file directly under /rocx/ whose name ends in a dash and 16 hex digits (styles-0123456789abcdef.css, as rocx build names the stylesheet) is cached for a year (cache-control: public, max-age=31536000, immutable).
  • Proxies. Outgoing requests use HTTPS_PROXY or HTTP_PROXY when set, except to hosts in NO_PROXY (HTTP).
  • Starting. The server reads .env into its environment (settings) and takes its port, stopping if the port is in use. Then it opens the database, checks the plugins, applies migrations, runs the app's init!, starts the background loops, and answers requests.
  • Stopping. On SIGTERM or Ctrl-C, it stops listening and taking jobs, then waits up to ten seconds for running requests, streams and jobs.
  • Without a database (a Postgres app with no URL), a server whose app or plugins have tables doesn't start, and says which have them; under --dev or --debug it starts and logs a line. Without tables, it starts, and what needs the database says so when used.

The log#

Every line on stderr is an event: a level, a message and fields, from your app, the host (starting, stopping, a crash with its method, URL and error) or a plugin (a migration applied, a failed job). Keep messages fixed and details in fields, for log collectors to filter on. Log with Log.info!, Log.debug!, Log.warn! or Log.error!, a message and a record of fields ({} for none); Log.line! logs a message alone. The program sets the format:

Auto, the default, follows ROCX_LOG (pretty or json) if set; otherwise pretty lines, the level in colour, to a terminal, and JSON elsewhere. A field named time, level or msg is written as fields.msg and so on, so it can't replace the line's own.

Logging never waits for stderr: a thread of its own writes queued events in order, flushing when the queue empties and before exit. When the queue is full (64k events), the caller waits rather than lose a line.

Deploying#

rocx build writes dist/server, migrations inside, and dist/static (rocx). --target arm64musl (or x64musl) makes a static Linux executable, from macOS too: the prebuilt host carries musl's C library and unwinder. To deploy:

  • Put it in a container with the app's static files: rocx build --image writes an image of nothing else, without a Dockerfile, for docker load -i my-app.tar (rocx). With only the app's database engine and no debug info, a hello world's image is 3.7 MB to send.
  • Give a Postgres app a DATABASE_URL, a SQLite app a file on a volume (--database-url sqlite:/data/app.db).
  • Pass settings (APP_SECRET, SMTP_URL, an API's key) as environment variables, or in a file read at start (--env-file; the environment wins). A plugin missing a setting stops the start, naming it.
  • Put a TLS proxy in front, and set PUBLIC_URL to the public address for the links the app sends (settings).

The platform's test app runs all its tests this way, in a container against a Postgres.

An app whose pages need no server once rendered (docs, a blog, a landing page) can be deployed as files: rocx build app --static dist writes every page, its data and what it loads, for GitHub Pages or a CDN (a static copy).

What is Rust, what is Roc#

The host gives Roc general building blocks. Everything built on them is Roc, in the platform or packages, and an app could write its own:

  • Rust (server/host): HTTP; threads; the database (a pool of Postgres connections plus one listening for notifications, or SQLite's file in the process, its calls on threads of their own); time zones; TCP and TLS sockets; live topics and rooms; channels' streams; background loops and isolated calls; actors' mailboxes and timers; values in memory (Kv); secure random numbers, AES-GCM and P-256; reading .env; rendering pages of components.
  • Roc (server/platform/*.roc): migrations, plugins (checking and running them), actors' state and messages, decoding database rows. Jobs, cron and email (an SMTP client, MIME) are Roc packages on the same effects (packages/jobs, packages/email).

The platform reference lists every effect, with its type.

A call pauses while it waits#

Your Roc runs on threads of its own (one per CPU core, or --roc-threads / ROCX_ROC_THREADS), beside tokio's, which handle HTTP, sockets and timers. Each call into Roc (a request and its page, a stream, an actor's turn, a background loop) is a coroutine with its own stack.

When an effect waits (a query, a socket, another server, a sleep), the call pauses and its thread runs other calls; it resumes on the same thread when the wait ends. A waiting call holds no thread, so any number can wait at once. In the tests, eight requests each waiting 0.3 s on Postgres take about 0.3 s together, and 2,000 each waiting a second, on two threads, about a second.

The costs:

  • Roc computing for long without an effect (a long pure loop) can't pause, so calls queued on its thread wait. New calls go to Roc's other threads.
  • A call with a time limit (a job's) still ends on time: the server interrupts its thread and, in the app's code, ends the call as a crash would.
  • Each stack reserves 8 MiB (Roc's default; a page is a deep tree to render), but a paused call costs only the memory its stack touched.
  • Profilers and debuggers see calls on their own stacks, not on threads.
  • A stack overflow still ends the process, saying so on stderr first.

Each call has its own context (its open transaction, rooms joined, topics listened to, sockets), given back when it ends. A value Roc makes belongs to its call until the call returns; then the host owns it, and may move it to another call (a stream's, to the call that sends it) but never shares it.

A crash ends one call#

In Roc, a crash or an integer overflow stops the program, but Roc's ABI lets the host choose how: roc_crashed must never return, so it can end the process or jump out of the Roc code that called it. This host jumps. A guard (server/host/src/guard.c) sets a jump target around every call into Roc, so a crash ends only that call:

  • A request is answered 500 (with the crash's message under --dev).
  • A stream ends.
  • A job counts as failed and runs again later.
  • An actor's turn is logged and reported to whoever asked; the actor's state stays as it was.
  • A transaction the call had open is rolled back.

A crash skips only Roc's frames and a small trampoline's, so no Rust destructor is skipped.

Memory#

So that a crash leaks nothing, every allocation a call makes goes into a list the call owns. When the call returns, the answer's strings are copied out and the list is freed (a stream's once the call sending it is done); when it crashes, everything in the list is freed. Roc's reference counts are atomic in native builds, so a value moved to another thread stays correct.

The tests crash 200 requests at once, half after allocating 2,000 strings, then check that Roc holds no allocation (--debug serves the count at /__rocx/allocations). This site's tests check the same after rendering its pages over and over.

Streams of events#

An endpoint can answer with server-sent events: a loop, Events.stream(|{ send!, sleep! }| …), which the host runs as its own call while the stream is open. send! writes an event; sleep! pauses. When the client leaves, sleep! wakes early and the next send! returns Err(Gone), so ? ends the loop. A sleeping stream holds no thread: the tests keep 2,000 open on two threads and still answer a request at once. Events shows one, with a component listening.

For live data that pages follow, a channel is usually better: a tab's channels share one stream the host keeps without a call, and Roc runs only briefly, for a check or hook.

Pages, rendered on the server#

A page is one tree of components: its layouts, the page, and what they contain. The host renders it whole (server/host/src/signals.rs) exactly as the browser's runtime would: each component and hole runs once, nothing is tracked or waits, and a memo is computed when made. HTML comments mark each hole for hydration; markup inside <NoHydration> is plain HTML, never hydrated. The site's tests check that the host and the browser's runtime render every page the same, byte for byte.

A component's endpoint read (Endpoint.read!, a GET of the app's own path) is made in-process: through the app's respond! and the route directories' middleware, with accept: application/json, the page's headers (cookies included) and the app's context, so it gets the answer the browser would. Each URL is asked once per render. The answers go, by URL, into a script at the end of the page, before /rocx/start.js, and the browser reads them there instead of asking again. Reads inside a <NoHydration> aren't recorded: the browser never makes them.

On a failure (a context nothing provides, a failed memo, an endpoint answering anything but 200), the nearest <Errored> shows its fallback, as in the browser. An endpoint's redirect redirects the page; a crash ends the render with a 500.

Photos' copies#

Write a photo as <img enhanced:src={path} alt="…" /> and the server makes smaller WebP copies of it, 160 to 1920 pixels wide. The first page to show it gets the plain src, and the photo joins a queue two of the host's workers take from. Later pages get the copies: a srcset, sizes, and the photo's width and height, so the layout keeps its room. No page waits, and there is nothing to set up: no job, no build step.

  • Whose photos: files in the app's static/, or what the app's routes answer someone signed out (the server asks itself, without cookies). Never another site's, and never a photo only signed-in users may see: its copies would be anyone's.
  • Where they're kept: data/images, named by content and served at /rocx/images/… for browsers to cache for good. The directory is its own index, so a restarted server has the copies on its first page.
  • Pruning: photos no page named for 30 days go, then the least recently used while the directory is over 1 GiB (--images-max-mb). A removed one is made again the next time a page shows it.
  • A changed photo (a rewritten file, a route's new answer) gets new copies; its page shows the plain src until they exist.
  • A static build (rocx build --static) waits for every photo's copies and ships them with the pages.

Background loops and isolated calls#

At start, the server asks the platform's Roc which loops to run in the background: plugins' loops (the jobs plugin's workers, schedules and hourly sweep of finished jobs) and checks (the email plugin's look at the SMTP server). Each runs as its own call until the server stops; one that crashes restarts a second later. A loop sleeps with Live.next!, which wakes on a publish to a topic it listens to, when its time is up, or with Gone at shutdown. Db.notify! (and Postgres's NOTIFY) publish on db:<channel>: that is how job workers sleep until a job is queued.

An isolated call runs Roc inside another call, guarded on its own: a crash ends it alone, and the caller learns why. Plugins use them (Plugin.isolated!); the jobs plugin runs each job in one, so a crashing job just fails and the worker goes on.

An actor's turn is a guarded call too: its mailbox, in the host, runs it with the kind, key, state and message as strings, so a crash frees them all. No lock is taken: one task routes each message to its actor's mailbox, and each actor handles its messages one at a time (actors).

Plugins#

A plugin is a package that adds what only the server runs: tables, background loops, files, scripts every page loads, development pages, work at start, checks; never a route. Name the package in the app's header and list its plugin in the program. The jobs, email, auth, push, Stripe and audio packages, among others, are plugins.

A plugin is one value, a Plugin.Value, made by its package from its own options:

  • No routes. Every URL is a file under the app's routes/ (D-116). A package that answers requests offers handlers for the app's own route files (respond! = |{ request, .. }| JobsPage.respond!(request, { mount: "/admin/jobs" })), wherever the app puts them, behind that folder's middleware.
  • Tables (migrations) are applied after the platform's and before the app's, recorded under the plugin's name; a plugin may list one per database flavor.
  • Calls, loops, starts and checks get the app's context (from its init!) without knowing its type (Plugin.Value(context)).
  • Needs the compiler can't check: an environment variable, a database (any, or Postgres or SQLite only), another plugin.
  • Files and scripts, below.

At start, the server checks every plugin and stops on any problem, listing them all: two development pages at one method and path, a file at the root where the app has a route, two files at one place, a name used twice, a need not met. Then it logs what each plugin added.

A plugin package names the server platform in its header, as an app does; a second header, browser.roc, lists the modules the browser's copy of the app can compile too.

A plugin's files are embedded at build (with an import … : List(U8), below) and handed to the host at start. The host serves them before anything else, the app's middleware included, so a sign-in guard never blocks a service worker or script: at /rocx/plugins/<plugin>/<path>, or /<path> with at: Root (a service worker, whose scope is where it is), to GET and HEAD, with its content type and an ETag of its bytes (304 when the browser has them). Every server-rendered page loads the files listed as scripts, as modules before start.js. Such a script can register browser effects that Browser.call! finds as <plugin>.<effect>; each gets { under }, which puts a URL under the site's base path. The push plugin serves its service worker at the root and its script this way, and the audio plugin its player.

Sockets and randomness#

Tcp.connect! (or connect_tls!, or start_tls! on an open socket) opens a socket for the call. write_bytes!, read_exactly!, read_up_to! and read_until! pause the call while they wait; close! closes it, and the call's end closes any left open. TLS is rustls, checked against the web's certificate authorities. Random.bytes! and Random.seed_u64! are the OS's secure randomness (crypto). The email package's SMTP client and roc-pg, a Postgres client in Roc, are built on these.

Not yet#

  • HTTP/1.1 only, and no TLS: put the server behind a proxy that terminates TLS.
  • A stack overflow in Roc still ends the process (it says so first).
  • Photos' copies take a photo's colours as sRGB: one in a phone's wider colour space comes out slightly paler. No AVIF, no HEIC, no photos of other sites yet.
  • One instance: live state, Kv and actors' mailboxes are in one process's memory, so an app isn't meant to run as several copies.

Built on

tokio and hyper (HTTP), corosensei (coroutines), tokio-postgres with deadpool, rusqlite with SQLite compiled in, turso_core (Turso's engine; a release has Postgres's and Turso's only if its program names them), image, fast_image_resize and libwebp (photos' copies, in a release whose markup writes an enhanced:src), chrono-tz (time zones), rustls with ring (TLS, random numbers, AES-GCM and P-256), and Roc's glue for the types the platform's header names (just glue writes server/host/src/roc_platform_abi.rs).
