The platform · crypto

Secrets, and what to do with them

Most apps need unguessable tokens (stored so a leaked table is useless), unforgeable links, and secrets stored encrypted. Secure random bytes, AES-GCM and the elliptic curve P-256 come from the host. The rest is plain Roc in packages/crypto, checked against published test vectors. The secrets come from the app's environment.

The samples are from server/test/app/Samples.roc, compiled and run by the platform's tests. Its header names the crypto package (crypto: "../packages/crypto/main.roc"), and it imports crypto.Hmac and the rest from it.

Tokens, and their digests#

Random.bytes!(count) is the operating system's secure randomness (through ring). If the system has none, the call crashes rather than make a key from anything weaker. A sign-in link's token is 32 random bytes; the database keeps only its SHA-256 digest, so a copy of the table signs no one in.

Signed links#

The app derives a link-signing key from its APP_SECRET with HKDF, so the key serves this one purpose, then signs the link with HMAC-SHA256. Hmac.verify_sha256 checks a link in constant time, so its timing doesn't tell a forger how much of a signature was right.

Sealed secrets#

AesGcm.seal!(key, plaintext) encrypts with AES-256-GCM under a 32-byte key (BadKey otherwise), with a fresh random 12-byte nonce each time. It returns the nonce, ciphertext and 16-byte tag, in that order: Web Crypto's output with the nonce in front, so either side can open what the other sealed. AesGcm.open! answers Forged for anything changed or sealed under another key.

P-256: ES256 and ECDH#

P256 is the elliptic curve P-256 (secp256r1), as much as Web Push needs. A public key is an uncompressed 65-byte point (4, then x and y); a private key is its 32-byte scalar. These are the raw forms browsers, Web Crypto and web-push generate-vapid-keys use, in base64url.

  • P256.generate!({}) makes a key pair from the operating system's random bytes: { public_key, private_key }, 65 and 32 bytes, for sign!. The push plugin makes its VAPID keys with it under --dev. Keep a private key in the server's environment, never in the app's code.
  • P256.sign!(private_key, public_key, message) is an ES256 signature (ECDSA on P-256 over SHA-256): 64 bytes, r then s, as a JWT carries it. ECDSA draws a random number, so each signature differs, and each verifies. It answers BadKey unless the keys are a pair, so one signing also checks a pair from the environment.
  • P256.ecdh!(peer) makes a key pair for this call, agrees a secret with peer's public key, and forgets the private key. It answers the new public key (for the other side) and the 32-byte shared secret, which only the holder of peer's private key can also compute. Derive keys from the secret with HKDF; never use it as a key. Web Push encrypts each message this way (RFC 8291). It answers BadKey unless peer is on the curve.
  • AesGcm.seal_with_nonce!(key, nonce, plaintext) is AES-GCM with the caller's 12-byte nonce, for protocols that derive their own: AES-128 under a 16-byte key (Web Push's aes128gcm, RFC 8188), AES-256 under a 32-byte one. It answers the ciphertext, then the tag. A nonce used twice under one key gives the key away, so otherwise use AesGcm.seal!, which draws one.

The modules#

ModuleWhat
AesGcmseal!, open!: AES-256-GCM, by the host; seal_with_nonce!: AES-128-GCM or AES-256-GCM with the caller's nonce
P256generate!: a new key pair; sign!: ES256 signatures; ecdh!: a shared secret with a key pair made for one call
Randombytes!(count), seed_u64!: the operating system's randomness
crypto.Sha256hash: 32 bytes; hex: 64 hex digits
crypto.Sha1hash: 20 bytes; hex. For authenticator apps' codes (TOTP) alone: never sign with it or keep a digest in it
crypto.Hmacsha256(key, message); verify_sha256(key, message, signature) and equal, in constant time; sha1 and verify_sha1, for TOTP
crypto.Hkdfsha256(key, salt, info, length) (RFC 5869), TooLong past 8160 bytes; extract, expand
crypto.Base64encode, decode; url_encode (unpadded), url_decode; encode_unpadded, url_encode_padded, lines (MIME's)
crypto.Base32encode, encode_unpadded (an otpauth:// secret), decode (either case)
crypto.Hexencode, decode

AesGcm, P256 and Random are the platform's, done by the host (ring). The rest are the crypto package's: pure Roc without effects, so they run anywhere, a browser page and expect tests included. They are checked against the test vectors of NIST, RFC 2202, RFC 4231, RFC 4648 and RFC 5869; Sha256 wraps Roc's builtin Crypto.SHA256. Decoding is strict: only the alphabet, no spaces, padding absent or exact, and the last character's unused bits zero (Hex and Base32 take either case, as people type secrets).
