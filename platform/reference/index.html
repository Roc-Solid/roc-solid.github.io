Requests and HTTP#

Server browser too

web/platform/Server.roc

The server: what it knows about a request, and how it answers. An app's respond! gets each request from its platform (from_http) and gives back the answer; its routes, endpoints and middleware (rocx writes them from routes/) take and make these in between. A component talks to the server through endpoints (Endpoint).

The flash a plain form's post came back with, on the page the redirect lands on: the next page a browser asks for after it (clear_flash). On the server it waits in the server's memory, its id in the request's cookie, and the first page that reads it takes it (it is read once); the page notes it for the browser (a script hydration reads), so both render the same. A field the page has as an <input type="password"> is left out of that note, and the page never fills such an input in again. Err(NoFlash) on any other page. use_submission! reads it for you.

The answer to a plain form's post, instead of the endpoint's own: back to the page it was posted from (Referer, when it is this site's; / otherwise), with a 303, and the flash (url posted to, the form's body as posted, the answer's status and body) kept for that page to read (flash!): in the server's memory for a minute, under a random id that a cookie (rocx-flash, HttpOnly) holds, and nothing else. However long what was typed, it is kept.

The request being answered: on the server, the one the host is answering (a page's, an endpoint's, a GET a page reads as it renders), its peer too; empty, a GET of /, anywhere else. The host hands it over as text, so a body that isn't UTF-8 comes with U+FFFD where it isn't: an endpoint is given its request's bytes as they came.

Endpoint browser too

web/platform/Endpoint.roc

An HTTP endpoint: a method at a path, which a route's +server.roc defines (get!, post!, put!, patch!, delete!; events!, a stream of events, asked for with GET). Anyone may call it over HTTP. The app calls it through what rocx writes from the routes (Generated/Api.roc), as a function of its params: its contract, the method, the URL and the types its handler's annotation gives, and nothing the handler does, so any module may import it (D-037). A component reads a GET endpoint as a plain value (Api.get_board({}).read!()): while the server renders the page, the server answers it, and the page carries the answer to the browser. It sends any endpoint (Api.post_card({}).send!(card), a refusal as a value; a GET too, with {}), or listens to one's events (listen!), through the platform's Call. On the server, a handler sends one of the app's own endpoints with send! too, answered in-process by its route, behind its middleware (D-103), and a channel's messages are published to it (publish!).

A handler is given the request, the context its middleware handed on, its path's params and its body, and answers Ok(result), sent as JSON with the status 200, or a Refusal: a status and why, or an answer of its own (Answer: a redirect that sets a cookie).

Its arg is one type whoever sends it: JSON (an action, a script) is read as JSON; a form's fields (a plain form, or one the runtime sent) are read by the arg's type too (FormBody, D-038), a number from its text, a box left unticked Bool.False, the values a name has as a List. The endpoint keeps that reader (form), made where its arg's type is known (remote, local).

A form's fields may be given ahead of time (with_fields, Solid Router's action.with): they go in the URL the form posts to, and its own fields after them.

Its arg may be checked as well as typed (checked, D-093): read by rules of the app's (a form of packages/forms), from a form's fields or a JSON object alike, and refused with their issues (422, as JSON) when it doesn't pass them. Generated/Api makes it so for a method whose route file names its body's rules (post_body = Signup.form).

A GET endpoint's answer, as a plain value, for a component or a computation (create_memo!(|| Api.get_profile({ id }).read!())): one definition of a page's data, the endpoint's, read where the page renders.

  • While the server renders the page, the server answers it in-process. The GET goes through the endpoint's route, as the browser's would, with accept: application/json and the page's cookies and headers, behind the route's middleware. The answer is noted for the page.
  • Hydrating, the browser reads that answer from the page and asks nothing.
  • Asked again later (refresh!), the browser GETs the endpoint's URL.

An answer that isn't 200 fails the computation: the nearest <Errored> shows its status and why (GET /api/likes: 500: the database is down). One no <Errored> of the page's catches reaches the app's root one (rocx writes it), and the page is the app's error page (+error.rocx), answered with the refusal's status when it is a 4xx (GET /notes/9: 404: Not found is a 404, as a path no page has is: Errored.status_of), else 500. A boundary of the page's own that catches it shows its fallback, as it would in the browser, and the page is answered as it is (200, unless the fallback says otherwise with <HttpStatusCode>). A redirect, while the page renders (a signed-out visitor sent to sign in), is the page's answer instead. with_query adds a query; endpoint.send!({}) gives a refusal as a value, for a computation that shows it itself.

Its answer, a refusal as a value: Ok(result), or Err(Refused(404, why)) and the like (Api.post_api_shout({}).send!({ word })). From a handler, in the browser, it is sent with the platform's Call.fetch!; the handler stops until the answer is in, and runs again then. A GET (Api.get_board({}).send!({})) is asked as read! asks it, while the page renders too, for a computation that shows a refusal itself. On the server, from the code answering a request (a handler, an MCP tool), one of the app's own endpoints is answered in-process, by its route, as the browser's request would be: behind the app's middleware and the endpoint's, with the request's headers (its cookies, its authorization), so what guards the endpoint guards this call too (D-103).

From a component, in the browser: listens to an endpoint's events with the platform's Call.listen! (Endpoint.listen!(Api.events_api_count_to({ to }), heard!)): heard! is given each event as it comes, typed, then Ended, or what went wrong.

From a component, in the browser: subscribes to a channel (a route's channel!), from an effect, until the effect runs again or its component goes (create_effect!(|| org!(), |org| Endpoint.subscribe!(Api.channel_org_org_news({ org }), heard!))). heard! is given what its subscription hears (Channel.Event), in order, one at a time: Resync when it should read its data again, then each Message; or why it hears nothing.

Every subscription in a tab shares one stream (/rocx/live), which the runtime opens once the page has rendered, and opens again, a little later each time, when it drops. When what the page subscribes to changes, the runtime tells the stream so (a post), and the route's on_close! hears Dropped for a channel the page no longer subscribes to. Two components on one channel share its subscription. A message it can't read as message is a Resync. On a host with no server (a static copy), it is Refused(404, …), asked for once. On the server, it does nothing.

From a component, in the browser: says said on a channel, to the server, where its route's receive! hears it, if its check lets the page in (Endpoint.say!(Api.channel_rooms_room({ room }), Moved({ x, y }))). What a page says in one frame goes in one request (POST /rocx/live/send); nothing waits for it, and a refusal is a warning in the console. Not on the server.

From a component, in the browser: asks the server for a Resync on a channel this tab subscribes to (and the route's on_open! messages after it), as when the page saw it missed something (a gap in the numbers its messages carry). Every subscriber to it in the tab hears it. Not on the server.

On the server: publishes message to every page subscribed to a channel (Endpoint.publish!(Api.channel_org_org_news({ org: "acme" }), news)), from a request, a job or an actor: only those subscribed with the same params hear it. A subscriber hears the messages on a channel in the order they were published; one that falls too far behind (256) hears Resync instead of what it missed. In the server's memory (Live): published while nobody listens, it is gone.

On the server: publishes message as publish! does, but only the latest with each key matters (where each member's cursor is, say: its key, the member). A subscriber behind gets only the newest with each key, and never a Resync for these: what it missed is replaced. They aren't ordered with the channel's other messages.

On the server: the answer to the host's question about a subscription (/rocx/live), as the generated routes give it, behind the route's middleware: its check, given the context that handed on; then, as the host asks (x-rocx-channel), who it let in and what it is sent first (open), who it is now (check), or what a page said, for received! (receive). A refusal is its status and why, or the answer it is (a redirect).

Its hooks: opened!, the messages a subscriber is sent first; received!, what a page said, as JSON (receiving reads it as the channel's said); closes, whether the host tells the route when a subscription ends.

On the server: a subscription has ended, as the host tells it (x-rocx-channel: close, its body who the check said it was and why it ended): the route's on_close!, given them. Its middleware doesn't run, nor its check: a subscription refused at a beat ends too.

On the server: the answer to a request to it, given the context its middleware handed on. Its arg is the body, read when it says it is JSON (application/json, or a type ending +json) or a form (application/x-www-form-urlencoded: its fields, as a browser posts them, read by the arg's type, FormBody; a field it lacks or can't read is a 400 naming it). Any other body (an upload: application/octet-stream, video/mp4, or no type at all) isn't read: the arg is {}, and the handler reads request.body, the bytes as they came. No body is {} too. A checked endpoint (checked) reads a form's fields, or a JSON object's, by its rules instead, and refuses what doesn't pass them with their issues (422, JSON); a JSON body that isn't an object of fields is a 400. Its result is sent as JSON, a refusal as its status and why (text; JSON for Json), or as the answer it is. A body it doesn't read, for a handler that wants an arg, is 415.

A form a browser posted without the runtime (a plain <form method="post">: a form's body, accept: text/html) gets neither its result nor its refusal, which would be a page of JSON or of text: it goes back to the page it came from, which reads them with what was typed (Server.flash_back!, Server.flash!, use_submission!). A form the runtime sent (x-rocx-submission) gets them, and a redirect of its handler's own comes back as 200 with x-rocx-redirect (fetch would follow it before anyone could read it), for the runtime to go there. An answer of its own is otherwise sent as it is.

On the server: as respond!, for an endpoint whose result is an answer of its own: a handler annotated => Try(Server.Response, Endpoint.Refusal) (D-106), which rocx build answers with this. Its Ok is sent as it is, as Err(Answer(…)) is (a redirect of its own comes back to a form the runtime sent as 200 with x-rocx-redirect); its refusals are respond!'s. A text, a file, a redirect that sets a cookie: an answer that isn't JSON, without its success being an Err.

On the server: the answer to a request for an endpoint's events (events!, asked with accept: text/event-stream), given the context its middleware handed on: a stream, each event sent as JSON as it comes; a refusal as its status and why, or as the answer it is.

Middleware browser too

web/platform/Middleware.roc

Code that runs around an answer. A middleware gets the request, the context so far and what comes next: it answers itself (a guard: a redirect, a refusal), or calls next! with the context it hands on (who is signed in), or changes what comes back (a header).

a.then(b) is a, then b; Middleware.when(Server.changes, guard) is guard for some requests alone. Middleware is named by folder, as routes are (D-103): a +middleware.roc under routes/ (middleware = Middlewares.member) runs around every page, endpoint and channel in its folder and the folders below it, outermost first; the one in routes/ itself runs around every request the app answers: every URL is a route file (D-116), a package's handlers and the OpenAPI document included, so a folder's middleware is around them as around the app's own. A folder in brackets, (members), adds nothing to the path: pages and their endpoints under api/ share one that way. What a middleware hands on is typed: a handler that reads context.user compiles only behind one that adds it.

Runs it around last!: what answers once every middleware has passed the request on.

Router browser too

web/platform/Router.roc

Solid Router's, on both sides. Where the page is (useLocation): on the server, the request's path and query; in the browser, the location the page on screen was rendered for, which each navigation in place changes (D-040). A trailing slash is dropped (/syntax/ is /syntax), as the server drops it from what it answers. Navigating (useNavigate, useIsRouting); and submissions to an endpoint: the latest (useSubmission), all of them (useSubmissions), and a handler's own, without a form (useAction).

Where the page is: on the server, the request's path and query; in the browser, the location the page on screen was rendered for (location.pathname without the site's base, and location.search). Tracked: a hole or a memo that reads it runs again when a navigation in place changes it.

Navigates to to (Solid Router's useNavigate), from a handler: a path (Paths makes them), a path with a query, or a query alone (?days=30, on the page's own path). One of the app's pages is rendered in place, the old page staying until the new one's document is in (is_routing!); anything else (another site, a path no page has) the browser loads. Queued with the handler's writes, so a handler that waits for the server and runs again navigates once. Called while computing, it fails: rendering mustn't navigate. On the server no handler runs, and it does nothing.

navigate! with Solid Router's options: replace replaces the history entry instead of pushing one; scroll: Bool.False leaves the scroll where it is (else the new page starts at the top, or at the element its hash names).

Whether a navigation in place is on its way (Solid Router's useIsRouting), tracked: true from the click until the new page is on screen, or the navigation fails or is overtaken; false on the server and while hydrating.

Runs listener! before each navigation away from the page (Solid Router's useBeforeLeave, D-040), as a handler: a link, navigate!, <Navigate>, a GET form, a submission's redirect, a change of the query alone, back and forward. It is given the navigation (Leave: to, from, options, delta), which it may stop (leave.prevent!()), and let go later (leave.retry!(force), from another handler: an app's own dialog). Called in a component (or a computation), it listens while that is there, and stops when it goes. Listeners are asked in the order they came.

A listener decides from what the page has (a signal, a memo already in): the navigation is decided once each has run, and one that waits for the server can't hold it (it isn't run again when the answer is in; a dev build says so). A load (leaving the site, reloading, closing the tab) the page can't hold: the runtime asks each listener ahead of time, with to "" (and its writes dropped), again whenever what it read changes, and while one would stop it, the browser asks the visitor first, with its own words (beforeunload). On the server no navigation happens, and it does nothing.

The page's query (Solid Router's useSearchParams, D-040): get! and all! read it, tracked; set! and set_with! change it in place, from a handler. See Search.

The app, told to the runtime as its page renders: Generated/Root.roc calls it first, and an app never does. build is the build's id (rocx build's hash of the app's sources): the server writes it on the page's bootstrap (data-build), and the browser loads a page of another build instead of rendering it. dev: rocx built it with --dev. routes: the app's pages, as JSON rocx build wrote (each page's path, /lists/[id], and its levels' code, from the root layout to the page), which the browser navigates in place to.

The latest submission of a form to endpoint (Solid Router's useSubmission(action)): its pending!(), input!() (field!(name)), result!() and error!(). The runtime sends a method="post" form whose action is one of the app's endpoints (Endpoint.url_of) with fetch, and the page stays, whether a component asks for its submission or not (D-095): this is how the page shows how it went. (An endpoint the route table doesn't have, in an app with no routes/, is sent so while the component that asks is there.) Without the runtime, the form posts, and the endpoint sends the browser back to the page with a flash, which the submission is.

Every submission to endpoint, each its own (Solid Router's useSubmissions(action)): its forms' (sent with fetch, as use_submission! says) and its actions' (use_action!). See Submissions.

Sends endpoint from a handler, without a form, and without the handler waiting for its answer (Solid Router's useAction(action)): each call is a submission of its own, which use_submissions! lists, sent once the handler is done (so a handler that waits for the server and runs again sends it once). Its arg goes as JSON (Endpoint.send!'s request). A result (200) has the page's reads read again before the submission is done; a refusal is its error (the error of its record in Submissions.all!, or Submission.error! of the latest).

Called from anywhere but a handler, its function fails; on the server, no handler runs.

A top-level field of its arg holding the URL of a file the page has (one on:drop.files, on:paste.files or on:change.files gave, Html.File's url), or a list of them, sends the file: the action goes as a form with files (multipart/form-data), its other fields as a form's, and the endpoint reads the field as the file's name, its bytes with Server.file.

Which of the page's reads a submission's result reads again (Solid Router's revalidate keys), each a URL (Endpoint.url_of(Api.get_board({}))): a GET the page read is read again when its URL is one of them, or begins with one and a / or a ? ("/api/notes": every note). Without it, a result reads every GET the page read again, as before; with [], none, and the submission is done at once.

  • In an endpoint's handler, on the server: said in its answer (x-rocx-revalidate), for the runtime that sent the submission (a form's, or an action's).
  • In a handler, in the browser: those reads, read again now (Solid Router's revalidate(keys)), once the handler is done. Anywhere else in the browser it fails.

Http

server/platform/Http.roc

Requests to other servers over HTTP/1.1, plain or over TLS (https, the server's certificate checked against the web's certificate authorities): an API, an OAuth server, S3. One effect makes them, Http.fetch!(url, init), as JS's fetch does; init says what isn't a plain GET, each field left out has its default, and {} is a GET:

The host makes each request (server/host/src/client.rs), the call pausing while it waits, as with Db and Tcp, on a connection kept alive from an earlier request to the same place when there is one, and through the proxy init.proxy says (the environment's by default). Any status is an answer (Ok, an HttpResponse): a 404 or a 500 is the other server's to give, and res.ok says whether it is a success. An Err means there was none: it couldn't be reached, TLS failed, or it broke off (HttpErr); it didn't answer whole in time (TimedOut); its body was larger than allowed (TooLarge).

Request, Response, Opts, defaults, send!, send_request!, get, post_form, post_json, with_header, header and text are the API before fetch! (D-024), kept for the apps that use them, deprecated: each is fetch! underneath.

Makes a request to url, as init says ({}: a GET, as fetch(url) makes), and reads its answer whole: any status is Ok (res.ok if it is 2xx). Err(HttpErr(why)) with no answer: no server there, TLS that failed, a URL that isn't http or https, or a header that can't be sent (a line break in it, or a colon in its name); Err(TimedOut), no whole answer within timeout_ms; Err(TooLarge), a body over max_bytes.

Makes a request as fetch! does, and hands its answer to step! as it comes, rather than whole: its head (Head(res)), then each chunk of its body (Chunk(bytes)), each with what step! answered last (start first). What it answers after the last chunk is the result. An Err from step! ends the request there, its connection closed (Err(Stopped(why))). For a body too large to hold, or one to pass on as it comes (a model's answer, word by word, to a stream of events): no chunk is kept after step! has it.

timeout_ms runs from the request to the body's last byte, and max_bytes counts every chunk: 0 for either is no limit, as a stream that runs long wants. The errors are fetch!'s, and Stopped.

deprecated: use Http.fetch!. Makes request as opts say: fetch! with the request's method (as written), headers and bytes.

deprecated: use Http.fetch! (this was fetch! before it). send! with defaults.

Call browser too

web/platform/Call.roc

Requests from a component: an HTTP request (fetch!), its answer read as a plain value, and a stream of events (listen!). While an answer is on its way, the computation or handler that asked stops, and runs again once it is in; if there is none, the nearest <Errored> shows why. Endpoint reads and sends an app's endpoints with them.

An HTTP request from the browser (an endpoint's, say: Endpoint.send!): its answer, read as a plain value. A handler or computation that asks stops until it is in, and runs again then; no answer at all (offline) shows the nearest <Errored>. On the server, while a page renders, a GET of one of the app's own paths is answered in-process and noted for the page (Endpoint.read!), and any other request is a handler's, which fails there; outside a render, a request of the code answering one (a handler's Endpoint.send!) to one of the app's own paths is answered in-process, by its route, behind its middleware (D-103).

Submission browser too

web/platform/Submission.roc

A submission to an endpoint, as Solid Router's useSubmission gives it: whether it is on its way, what was sent, and the endpoint's result or refusal. Its fields are methods: submission.pending!(). Router.use_submission!(endpoint) is the latest one; Router.use_submissions!(endpoint) lists them all, each its own (Submissions).

With the runtime, a form posting to the endpoint is sent with fetch, as is an action (Router.use_action!), and the submission is one the runtime sent. Without it (before it loads, or with no JavaScript), the form posts as a form does, and the endpoint sends the browser back with a flash (Server.flash!): until the runtime sends one, the latest submission is that flash, when it is the endpoint's. On the server it is the flash, or none.

A submission the endpoint answers with its result (200) stays pending until the page's reads (Endpoint.read!) have been read again, so what the page shows next is the server's, all at once.

Whether it is on its way: sent, and not yet answered (or answered, and the page's reads being read again).

What was sent, as the endpoint reads it (its arg: a form's fields, as a record, or an action's arg). Err(NoInput) with no submission, or fields it doesn't read.

A field as it was typed (FormData.get), to put back in its input after a refusal: "" after a result (D-122: the form starts empty again, as the page a plain post comes back to has it, and as SvelteKit's does; input! still says what was sent), with no submission, no such field, or for an action's (its arg isn't a form's fields: input! reads it).

The endpoint's result, once it is in. Err(NoResult) before, without one, or after a refusal.

What went wrong, once the answer is in: the endpoint's refusal (Refused(status, why)), or none at all (HttpErr). Err(NoError) before, without one, or after a result.

Forgets it (Solid's clear), the flash too, from a handler: it leaves the endpoint's submissions, and there is none until the next is sent.

Sends it again (Solid's retry), from a handler, with what it sent before: pending again, its answer to come. One still on its way isn't sent twice; with none (or the flash: a plain form's, which the runtime never had), nothing.

OpenApi browser too

web/platform/OpenApi.roc

Data#

Db

server/platform/Db.roc

The app's database: Postgres, SQLite or Turso, as its program says (database, D-045, D-046). Its SQL is the app's, in its database's flavor: nothing is translated.

  • Postgres is at --database-url (or DATABASE_URL); without one the app has no database, and a server whose app or plugins have tables doesn't start, outside --dev and --debug.
  • SQLite is a file in the server's process, at the program's Sqlite(path) (or a sqlite:<path> --database-url), made when missing. Reads go on while a write does; writes take turns. So keep anything slow (Http.fetch!, a wait) out of a transaction: on SQLite it holds every other write back until it ends.
  • Turso is SQLite written again in Rust: the same SQL, at the program's Turso(path) (or a turso:<path> --database-url, which runs a SQLite app on Turso too). Its writes go on at once (MVCC, D-049): each transaction on a snapshot of its own, one that loses to another's write to the same row run again (transaction!). The server keeps the file to itself while it runs, and in MVCC mode it is Turso's alone (turso:<path>?mvcc=off once gives it back to SQLite, its writes then taking turns); no FTS5.

A statement's parameters are $1, $2, …, given as Values, in both.
