The platform · the database

One database, and the types you say

An app has one database: Postgres, or SQLite inside the server's own process. Db runs statements and decodes rows into the record type you annotate. Transactions keep one connection for a call; migrations run once each as the server starts. Actors' state and the jobs queue live there too.

Postgres or SQLite#

The program picks the database, and the app's SQL is written for it: nothing is translated.

  • Sqlite(path), the default (data/app.db when the program names none), is a file inside the server's process, at path from where the server starts, made with its directory when missing. There is nothing to set up. It suits an app on one server, which is what the platform runs; every example app with a database uses it.
  • Postgres is found at --database-url (or DATABASE_URL). Without one there is no database, and an app with tables doesn't start (below). Choose it for data other programs share, or more than one server's disk holds.
  • Turso(path) is SQLite's SQL on another engine, whose transactions can write at the same time (below).

--database-url sqlite:/var/lib/plate.db moves a SQLite app's file (onto a volume, or to a test's own). A URL for the other kind of database stops the server at start, naming the one the app wants.

A package names the databases it works with in its plugin's needs: Database (either), Postgres or Sqlite; a mismatch stops the app at start. A package with SQL for both asks Db.backend! which to run, and lists a migration for each ({ name: "0001_jobs", sql: lite, on: Sqlite }), as the jobs plugin does.

Parameters are $1, $2… on both databases, each a Db.Value: Null, Text, Int or Bool. Postgres receives text and reads it as the type its place wants ($1 in where id = $1 becomes a bigint). SQLite receives each as it is (a Bool as 1 or 0), and a number column accepts numeric text. Never build a statement from strings: pass values as parameters.

On Postgres, Db.array passes a list as one parameter, in Postgres's text form for arrays ({"work","to do",NULL}), read as the array of text or numbers its place wants: = any($1), @> $1, $1::bigint[], unnest($1::text[]) (alone, unnest($1) needs the cast). Each text is quoted, so a comma, a brace or the word NULL inside stays text. SQLite has no arrays: pass JSON text and read it with json_each (where tag in (select value from json_each($1))).

Rows, as records#

The host hands Roc the rows as JSON, each column as the database typed it. Db.all! and Db.one! decode each row into the record you annotated, matching fields to columns by name. A row that doesn't fit is BadRow, saying why.

  • Nulls are typed. Read a column that may be null as Db.Nullable(a): Null or Some(a). A null where the record reads a plain value is BadRow, naming the column.
  • From Postgres: booleans, integers, floats, text, json and jsonb, uuid, and timestamps and dates (as text). Other types need a cast (::text).
  • From SQLite: values as they are (an integer or a real as a number, text as a string), a column declared boolean as a Bool, one declared json as its JSON. A boolean computed in a statement (exists (…)) is 0 or 1, an I64. SQLite has no time type: store milliseconds in an integer (Time.now_millis!).

Writing#

Db.run! runs a statement and returns how many rows it changed. Db.script! runs several statements without parameters (separated by ;) as one transaction: if one fails, none stays.

Transactions#

Db.transaction! runs a function on one connection. Its writes, and the jobs it queues, stay only if it returns Ok. An Err, a failing statement, a crash, or the call ending with the transaction open rolls all of it back.

Inside, ? works on what Db, Job and your own code return, with no error mapping. Their errors are open tag unions (Db.run!'s is [DbErr(Str), ..others], Job.enqueue!'s [JobErr(Str), ..others]), so the transaction's error is their union: with an app's own Err(Refused), [DbErr(Str), JobErr(Str), Refused], which the caller matches.

A job queued in a transaction is a row in it: it runs only if the transaction commits, and the workers wake when it does (jobs).

Keep transactions short on SQLite

On SQLite, reads go on beside a write, but writes take turns: a transaction holds the write lock from its start, so other writes wait until it ends. Keep anything slow (a request to another server, a wait) out of it. On Postgres it would hold only the rows it wrote.

A transaction inside another#

A helper can open its own transaction and still be called inside another: the inner Db.transaction! is then a level of the outer one (a savepoint). On Ok, its writes stay in the outer transaction, which commits them or not. On Err, or a failing statement, only its own writes are undone, with what it notified and the jobs it queued, and the error comes back to the outer body, which can handle it and go on:

  • An outer Err still undoes everything, inner levels included, and a crash rolls back the whole transaction.
  • Levels nest as deep as you like; a level's writes stay only if every level around it commits.
  • It works the same on Postgres, SQLite, and Turso in both modes. On Postgres a failing statement aborts the transaction until its level rolls back, so an inner body that ignores the error and returns Ok still gets it from Db.transaction!, and its level is undone.
  • On Turso's MVCC, a level that loses to another transaction's write isn't run again alone: the whole transaction has lost. Its statements fail from then on, and the outermost Db.transaction! runs its body again when the error reaches it.

Migrations#

An app's schema is a list of migrations built into its executable. With rocx build, put each in a .sql file in migrations/ (0001_tables.sql, 0002_seed.sql…): the build embeds them in name order. A hand-written program lists them in program.migrations, each a name and its SQL, imported from a file:

At start, the server applies each migration it hasn't yet, in order, each in its own transaction, and records it by name in rocx_migrations: the platform's tables (rocx_actors, rocx_actor_timers) first, then the plugins' (the jobs plugin's rocx_jobs, as jobs/0001_jobs), then the app's. A failing migration stops the server, saying why. Two servers starting at once (a deploy's old and new) take turns, by an advisory lock on Postgres or the write lock on SQLite.

Where it can be used#

Anywhere only the server runs: an endpoint, a middleware, a job, an actor, a stream. A component also compiles for the browser, so it can't query; it reads through a GET endpoint (Endpoint.read!), which the server answers in-process while rendering. Only the server runs the handler, so it may query; the browser's copy has just the endpoint's method and URL (who is asking).

  • Connections. A statement borrows a connection from a pool (16 for Postgres, 8 for a SQLite or Turso file); a transaction keeps one until it ends. Statements are prepared once per connection, and kept. SQLite's and Turso's calls run on threads of their own, so a call waiting on one holds none of Roc's.
  • Postgres connections use TLS when the database offers it (or the URL's sslmode asks), checked against the web's certificate authorities. In this repository, just db runs a Postgres in Docker and prints its URL.
  • No database? A Postgres app with no URL and no tables still runs: each query answers that there is no database, and Db.connected! says so up front. One whose app or plugins have tables (the jobs plugin's, auth's) doesn't start, saying which have them; under --dev or --debug it starts and logs a line.
  • SQLite's file is in WAL mode, with -wal and -shm files beside it. Back it up with sqlite3 data/plate.db ".backup copy.db", or copy it while the server is stopped (a Turso file only that way: the server holds it while it runs).

Notifications#

Db.notify!(channel, payload) tells whoever listens on channel, when the call's transaction commits (never if it, or the level that notified, rolls back), or at once outside a transaction. A call listens with Db.listen!(channel), then gets each notification from Live.next! as a message on the topic db:<channel> (topics). On Postgres it is pg_notify, so other processes can notify too; on SQLite it stays within the server. Job workers sleep on it until a job is queued.

Checking queries: rocx check --sql#

rocx check --sql checks an app's SQL with the engine it runs on, and its row types with the compiler, without running anything. Each string-literal statement at a Db.all!, Db.one! or Db.run! is prepared (never run) on a scratch database that the app's own server builds from its migrations: a file for SQLite and Turso, or a database on the Postgres server DATABASE_URL names, either removed afterwards. It never migrates a database nobody named for it: without the CREATEDB privilege, it says to grant it, or to name a database it may migrate (--sql-database URL). rocx dev runs the check after each build.

  • The SQL. The engine judges the statement: its syntax, tables, columns and functions, Postgres's types, and what Turso doesn't support yet. A call's parameter list must be exactly the statement's $1 to $n, each used.
  • The rows. For a Db.all! or Db.one! whose rows are annotated (rows : List(T), row : T, or the result of the function the call is in), it compares the record with the statement's columns: a field the statement doesn't return, a type the column's values can't decode into, and a plain field over a column that may be null (no not null), which Db.Nullable should read. rocx reads the type with the compiler's parser, in a small app beside a copy of yours (packages/dbcheck), so aliases, nominal types and packages' types read as the compiler has them.
  • What it can't check: SQL built from strings ("select ${columns} from notes") or passed in a variable, which --verbose counts and lists; and statements on a table the app creates at run time, not in a migration, which you mark with Db.unchecked(sql).
  • Where to run it: by hand, in CI, and in just examples for each example. --engine turso asks Turso about a SQLite app (or SQLite about a Turso app). Describing a statement takes milliseconds; most of a check is the server starting and migrating.

Turso: SQLite's SQL on another engine#

Turso(path) is Sqlite(path) on Turso, SQLite rewritten in Rust, also inside the server's process. Its SQL and file format are SQLite's, so what this page says of SQLite holds for it, including packages' and plugins' SQLite migrations and needs. Db.backend! answers Sqlite for both; Db.engine! tells them apart.

The URL picks the engine: --database-url turso:data/plate.db runs a SQLite app on Turso, and sqlite: a Turso app on SQLite, to compare them under rocx dev. A release (rocx build --release, --image) has only the engine its program names, to stay small, and refuses another at start.

What Turso adds: writes at the same time. Its file is in MVCC mode. A transaction (Db.transaction!) begins concurrent, on its own snapshot, and writes beside the others. When two write the same row, the second to commit rolls back and its body runs again (up to a hundred times; the outermost body when transactions are nested), so keep what isn't the database's (a fetch, an email) out of a transaction. A write outside a transaction is its own concurrent transaction, retried the same way; a schema change (a migration) takes the file to itself. Two transactions that read rows and write different ones both commit, where on SQLite the second would wait.

What differs:

  • In MVCC mode the file is Turso's alone; SQLite refuses to open it. --database-url turso:data/plate.db?mvcc=off, run once, gives it back (in that mode Turso's writes take turns, as SQLite's do).
  • The server locks a Turso file while it runs (an OS lock), so sqlite3 or a test's node:sqlite opens it only after the server stops.
  • Turso has no FTS5, so the full-text search in examples/notes and examples/plate needs SQLite, and no order by inside an aggregate (json_group_array(value order by key), which examples/board uses).
  • Turso is younger than SQLite (0.8, before its 1.0). Once it has checkpointed rows, deleting many of them badly slows what follows until its next checkpoint; pragma wal_checkpoint(truncate) after such a delete avoids it, and ?mvcc=off doesn't have the problem.

examples/sqlite-vs-turso times the same work on both, in Roc in the server (writes, reads, scans, JSON, eight callers at once); its page has the numbers.

roc-pg: queries checked at build#

For Postgres, roc-pg is a client written in Roc. It speaks Postgres's protocol over the platform's Tcp, signs in with its Random, and checks each query against a schema at compile time: a missing column, a parameter of the wrong type, or a nullable column read as non-null fails the build. The platform's example (server/examples/roc-pg) uses the same schema.sql as its migration, so roc-pg checks against what the server applied.

Use either, or both. Db has a pool, transactions that take jobs with them, and rows decoded into the record you annotate, checked by rocx check --sql. roc-pg has queries the compiler checks, and a connection per use (no pool). Checking the example takes under a second from cold, an optimized build about six; the platform's tests build it and run it against Postgres.

Not yet#

  • The check's blind spots, besides SQL it can't read (above): a row whose type isn't annotated where rocx can read it, a column from the outer side of a left join (taken as its table says), and, on SQLite, an expression's type and nullability. Those still show when the query runs (BadRow).
  • Parameters are four kinds (null, text, integer, boolean) and arrays of them: no floats (pass a number as Text, which Postgres reads as the type its place wants) and no bytes yet. A row reads an array column through a cast (array_to_json(tags)).
  • No cursors or streaming: a query's rows come back whole.
  • SQLite is a file: no in-memory database (the server's connections couldn't share it), and a blob is read through hex(…).
  • Turso's sync to Turso's cloud and its own full-text search aren't used yet; in MVCC mode it has no WITHOUT ROWID tables and no REINDEX.
