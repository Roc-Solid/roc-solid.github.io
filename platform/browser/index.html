The platform · the browser

The components in WebAssembly, a Rust host, and a page of JavaScript

The browser runs the same components the server renders: every page, with its layouts, compiled to one WebAssembly module. Your Roc decides what each hole shows and what each handler does. A JavaScript runtime tracks what reads what, runs a hole again when what it read changes, and touches the DOM. You write no JavaScript.

The parts#

web/runtime.js

JavaScript. Hydrates the server's document. Keeps the signals, memos, effects and computations, and which component owns what. Runs a hole's Roc again when what it read changes, and patches its node. Runs effects once their markup is on the page; starts timers, sends requests and forms, navigates, and listens to streams and channels.

⇄ids and strings

One wasm module

web/host

Rust, inside the wasm: Roc's memory, and each of the platform's effects passed on to the runtime.

The app, on web/platform

Roc: your components, their markup with holes as closures, escaping and safe URLs, and endpoints as requests.

Markup reaches the runtime as JSON: elements, text, and holes, each a Roc closure the runtime keeps boxed under an id. Running a hole calls the app's run with its box, and the answer is JSON again: a text, an attribute's value, or markup. The server renders the same JSON natively (pages, rendered on the server). Lists are cheaper: once the page is up, a .map's first row sends its skeleton (its elements, and the attributes and text written in the file), which the runtime keeps and copies; each later row sends only what fills the copy (its holes, handlers and values). The bootstrap, web/start.js, ends every page: it loads the runtime and the wasm from beside itself, and hydrates the document.

What components can use#

Components use the browser platform's modules, which the server platform has too (the build copies them):

  • Html (markup), Solid (signals, memos, effects, timers, contexts), Store, Context, Repeat (a row per index in a range, what virtual lists are made of), Transition, Loading and Errored: components.
  • Endpoint, Call, Events, Channel, Submission and Submissions: talking to the server.
  • Router, Search, Leave, Navigate, Title and HttpStatusCode: routing and navigation.
  • Browser (Browser.call!: the page's own JavaScript, or a plugin's script, from a handler) and Time (the clock).

Server, Middleware and OpenApi are there too, so route files compile on both sides. Roc compiles only what a program reaches, so server-only code costs the wasm nothing.

The header#

What an app gives the platform, and what the platform gives the host:

main! is the app's root, written by rocx build --client (Generated/Root): a whole document, the page at the browser's path inside its layouts. The platform gives the host two functions: mount the root, and run a kept box. The browser answers no requests: every endpoint a component reads is the server's (in the tests, Node answers reads from the answers the page recorded). The rest of the header is what Roc may ask of the runtime, each a call into JavaScript: boxes, signals, memos, fetches (an endpoint's read is a GET), streams, channels, contexts, where the page is (Router.location!), and so on.

The whole header: web/platform/main.roc

One click, step by step#

You press + on the counter on the front page. Then:

  1. JavaScript The button's listener, attached at hydration, holds the id of the handler's box. The runtime opens a turn and asks the host to run it.
  2. Roc || set_count!(count!() + 1) runs: count!() asks the runtime for the signal's value (3), and set_count! hands it the next one (4), boxed.
  3. JavaScript When the handler returns, its writes apply: the signal holds 4, and the three computations that read it are due: the <output>'s text, the negative class, and the Reset button's disabled.
  4. Roc Each runs again: the text is "4", the class still off, disabled still false.
  5. JavaScript Only the text changed, so only its node is set: an unchanged value isn't patched. (Reset to 0 would patch the button too.)

Hydration#

Hydration is how the browser takes over the server's page without building it again:

  1. JavaScript The page ends with a script holding its endpoint reads' answers, then the bootstrap, /rocx/start.js. It fetches the runtime and the app's wasm (310.5 KB with brotli for this site, one module for every page) from beside itself, has the runtime compile the wasm, and asks it to hydrate the document.
  2. JavaScript The runtime reads the answers and takes their script out of the page.
  3. Roc The root runs once: it reads where the page is (Router.location!) and renders that page in its layouts, a whole document, each component once, where it is rendered.
  4. JavaScript The runtime walks the server's nodes beside Roc's markup, from the doctype and <html> down, attaching each computation to its node. The server's HTML comments mark each hole, list row and if branch (<!--x-->…<!--/x-->). Nothing is fetched or built again: a read whose answer the page has (under GET and its URL) gets it from there.
  5. JavaScript Elements a browser extension put straight in <body> or <head> (a password manager's popup, a dark theme's style) are passed over, and stay. Any other mismatch (the HTML parser moved a <div> out of a <p>) makes the runtime warn, naming the node and its place, tell the page (a rocx:mismatch event, for error reporting), and render <body>'s children again from the same answers. <head> is left alone: rendering it again would rerun its scripts and flash its styles. To investigate one, localStorage.setItem("rocx:strict", "1") makes the next load throw at the mismatch instead.
  6. JavaScript The bootstrap tells the page it is done with a rocx:ready event, carrying how long hydrating took. From then on, a read the page has no answer for is a GET of the endpoint's URL.

What it never hydrates#

<NoHydration> (Html.no_hydration in Roc) marks markup only the server renders: prose, listings, anything that never changes in the browser. The server runs it once and writes it between <!--nohydration--> and <!--/nohydration-->, with no markers inside, leaving its reads out of the page's answers. In the browser's copy of a .rocx file (rocx build --client) the region has no children, and imports only they used are gone, so none of it is in the wasm. Hydration skips the nodes between the markers, never building, adopting or patching them; a <body> rendered again keeps them.

Nothing inside runs in the browser, so rocx refuses a handler, a key or a transition written there, at its line, and the server refuses to render a handler a component put there: a 500 naming the element, rather than a button that silently does nothing. This page is all one <NoHydration>, so its prose costs the wasm nothing.

Moving between pages#

After hydration, a link to another of the app's pages doesn't reload. The runtime fetches that page's HTML document, as a reload would, and renders it from the document's answers with the wasm it has (every page is in the one module). Layouts both pages share stay, the address goes into the history, and scroll, focus and title change as on a reload. Navigating without a reload lists what an app controls.

Waiting, in wasm#

A component reads a memo that waits for the server (an endpoint's answer, say) as a plain value: no async in Roc, and no JSPI. Until the answer is in, the read throws, in JavaScript, through the Roc frames that asked. The runtime catches it where it ran the computation, puts Roc's stack pointer back, and runs the computation again when the answer comes; the host frees what the stopped run allocated (memory). The first time, a <Loading> above shows its fallback; after that, what was shown stays until the new value is in (waiting and failing).

Roc's floating-point code weighs most in the wasm. Building with and without it, parsing a float from a string costs about 18 KB compressed, printing one about 12 KB, and sine and cosine about 5 KB. So the runtime sends frame times as whole microseconds, the showcase's flock prints its positions as whole numbers, and a bird's heading is a random vector scaled by a square root, one wasm instruction.

Memory#

A page keeps its wasm instance while it is open, so memory has to come back. Roc's memory is the host's: a Rust crate, web/memory, which the phone's host uses too. It allocates power-of-two slots, as Zig's allocator for wasm does, and counts what is live. A box the runtime keeps (a hole's closure, a signal's value) is released when what made it goes: a row dropped, an if switching branch, a value replaced. A run that stops to wait skips the frees Roc would make on the way out, so the host notes what each run allocates and frees what a stopped run still held once the runtime lets go of what it made. The tests click, type, add and drop rows, wait for the server, and render pages over and over, checking that live allocations don't grow.
