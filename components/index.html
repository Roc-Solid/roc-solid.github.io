Components

Values that change, and values that are on their way

Components are a page's interactive parts, on SolidJS 2.0's model, in Roc: a component runs once, and each hole in its markup runs again when a value it reads changes. Server data is a plain value, and boundaries say what shows while it loads.

Try itPutting one on a pageComing from Solid

At a glance#

A component is a function from props to markup (Html), written in a .rocx file: Roc with markup wherever an expression can stand (see the syntax page). The file has import pf.Html; its module defines view or view!. The front page's counter, the smallest component with state:

The component runs once

view! runs once, where the component is rendered: it makes the signal count!, builds the markup, and never runs again.

Holes run again

Each {…} or attribute that reads count!() reruns when the count changes, and patches its own node. No virtual DOM, no diffing.

Server data is a plain value

A memo that reads an endpoint gives a Str or a record, never a loading state. <Loading> and <Errored> say what shows while it waits.

Rendered on the server

The server renders the page with every answer in it. The browser takes over the server's nodes (hydration) and asks for nothing again.

Know SolidJS? Coming from Solid maps each of its functions to its name here.

Signals, holes and memos#

The functions come from the platform's Solid module:

A signal

A value that changes, as two functions: an accessor, count!, reads it (count!()) and tracks the read; a setter, set_count!, writes a new one. Its type is fixed when it is made.

A hole

A computation in the markup. The runtime notes which signals it reads and reruns it when one changes, patching its own node.

A handler

What an event runs, and where signals are written. Its writes apply together when it ends.

A memo

A value computed from others, again when they change; read it like a signal. Computed again to the same value, it tells no one.

These names end in ! because Roc marks every function that has an effect, and the compiler checks the mark. Reading a signal is an effect: the read is tracked. Signals, memos and changing props are all read through an accessor.

What runs, and when

In the counter above:

  1. The body runs once. view! makes the signal and builds the markup; each hole is a closure it doesn't run. As in Solid, the body's own reads aren't tracked.
  2. Each hole runs once to show its first value, and the runtime notes what it read: the <output>'s text, the negative class and Reset's disabled all read count!.
  3. A click runs a handler. set_count!'s write applies when the handler ends, with any others it made.
  4. Those three holes run again and patch their nodes. Nothing else runs, so the signal keeps its value.

Attributes are holes too (disabled?={count!() == 0}, class:negative={count!() < 0}, style:--size={…}). A hole that calls nothing ending in ! can't change, so rocx writes it once, with no computation ({label}, a pure component's prop). A hole that ran and read nothing that changes (a prop given a constant) is static too: plain text from the server, nothing kept in the browser.

A signal's write isn't compared with the old value: writing the same count again reruns every hole that reads it (one whose text comes out the same patches nothing). Memos and store selections do compare, with ==.

Writing from the value

Since writes apply when the handler ends, a read in it gives the old value: set_count!(count!() + 1) twice adds one, as in Solid 2.0. update! (Solid's setCount((c) => c + 1)) writes from the value the handler's writes so far leave, so two updates add two. Only update! sees a pending write; a plain read still gives the old value.

It also takes an optimistic value's accessor and setter. A store's setter already takes a function and composes the same way.

Memos and the server

A memo starts computing when it is made. One that reads an endpoint (Endpoint.read!, see talking to the server) is async: five such memos send five requests at once, and a hole that reads one waits (waiting and failing). refresh!(user!) asks the server again; the old value stays on screen, and is_pending!(user!) says it is on its way out. Roc can't compare functions, so refresh! finds the memos by running the accessor once and noting what it reads.

A read in the body is read once

doubled = count!() * 2 in the body is the starting count times two, for good. To follow the count, read it in the hole ({(count!() * 2).to_str()}) or a memo. This is the one mistake the model invites, so a dev build (rocx dev, rocx build --dev) warns in the browser's console, once per place, as Solid 2.0's does:

When one read is meant (a start value), untrack! (Solid's untrack) reads without tracking and silences the warning: create_signal!(untrack!(|| start)). In a memo or hole, create_memo!(|| count!() + untrack!(|| base!())) reruns when count! changes, not base!. A hole whose reads are all untracked is static. The warning misses reads inside a helper function.

Two rules the runtime enforces

  • Write signals in handlers: an event's handler, an effect's apply, a cleanup or a timer's tick. A write in a hole, a memo or a component's body fails, and the nearest <Errored> shows why.
  • Read server data in holes, memos and handlers, not in a component's body. A hole can wait for an answer; the body can't, and stops with an error.

Pure and effectful components#

Components use Roc's ! mark too: a function without one can't call one with one. A component's module defines either view (pure) or view! (effectful). The counter above is effectful; this site's section heading is pure:

view: pure

Makes markup from its props, which are plain values. It can't make a signal, read a context or call the server: the compiler refuses. It is called where it is written, like any function: <Heading id="why">…</Heading> becomes Heading.view({ id: "why", children: […] }).

view!: effectful

May make signals and memos, read a context, and read endpoints. It runs once, where it is rendered, like a Solid component: <Counter start_value={3} /> becomes Html.component(|| Counter.view!({ start_value: || 3 })), which the runtime calls at its place in the tree, under the contexts above it. Its props are getters (props that change).

You don't mark the call: rocx build writes the one that fits, so a component can switch kinds without its callers changing. Start with view; add the ! when the component needs its own state, a context or the server. Solid can't tell the two apart, since any JavaScript function may do anything. Roc can, so a pure component is guaranteed to keep no state, and costs no more than a function call.

A pure component can still show changing values. Given one (<Badge count={unread!()} />), its call becomes a hole: when the value changes, the component is called again and its markup replaced. It has no state to lose, but its elements are new, so the focus or text typed in them goes. To keep them, pass an accessor for its holes to read (<Badge count!={unread!()} />, typed count! : () => U64), or make it a view!. This is on purpose: a pure component stays a function of values, so a test or an email's HTML (Html.to_str) can call it with plain values.

Props that change#

An effectful component runs once, so a changing prop must be read where it is used. Like Solid's compiler, rocx passes each value prop of a view! as a getter, a function that computes it, and the child (written with a plain text : Str) calls it wherever it says text:

Where the child reads a prop decides what follows it:

  • In a hole, an attribute, a memo or an effect's compute: read again when the value changes, patching only that place. The component and its signals stay.
  • In a handler: the value when the handler runs.
  • In the component's body: read once (first = text keeps the first value). Fine for a start value, with untrack!; otherwise the dev build warns (a read in the body is read once), and rocx build warns at a call given a match arm's name or a row's item (if, match and .map).
  • In a pure function the component calls (items.keep_if(|item| item.owner == me)): a value. A pure function can't call a getter, so the hole or memo around the call reads the prop and passes the value in.

So destructuring is safe. In Solid, const { text } = props loses reactivity; here |{ text }| means props.text, because rocx rewrites every read of text. A prop given a constant (level={2}) is static, and the dev warning ignores it.

Accessor props. A prop named with !, text!={user!().name}, is the same getter written by hand: the child types it (text! : () => Str) and calls it (text!()). It lets a pure component follow a changing value and keep its elements (above). To let a child write, pass the setter; it is already a handler, so on:input.value={set_draft!} needs no wrapper. children is markup, whose holes are already live.

Passing props on. |{ kind, ..rest }| takes kind out and keeps the rest (Solid's omit); <Base {...rest} size={3} /> passes them on, still getters (Solid's merge: the last of a name wins). With the view's props annotated, rocx writes the fields out one by one (label: rest.label), and other attributes can add or replace some. Without, it writes Roc's record update ({ ..rest, size: || 3 }), so Base's props must be exactly that type, and only one such record can be spread on a tag.

A row per key: .map

{...todos!().map(|todo| <li key={todo.id}>{todo.title}</li>)} is Solid's <For>. Each row is kept by the key on its root: made once, moved when its key moves, dropped when its key goes. todo is a getter for the current item, so an edit that keeps the id keeps the row's elements, focus and typing.

  • A key is required when the list changes; rocx refuses a row without one, at its line. Roc's values have no identity, so Solid's default (a row per object) can't work. A key can be any value: a string as is, anything else as Str.inspect writes it.
  • The key goes on the row's root, an element or a component (where it is never a prop). A row that is an if puts a key on each branch.
  • A row is told only when its item changed, compared by ==: toggling one todo of a thousand runs that row's holes alone. So an item must be data (records, tags, lists, text, numbers), not a function or markup.
  • A row runs once, like a component (Solid's mapArray): what it reads at its top is read once; its holes, and the props it gives components, follow the item. It may hold another .map, an if, or plain markup.
  • A list that reads nothing that changes (a constant, or one in a <NoHydration>) is built once and needs no keys.

A row per position. .map_with_index(|pick, i| <li key={i}>…</li>) is Solid's <For keyed={false}> (formerly <Index>): rows stay put, and the item at each position changes (the right list). With any other key, it is a row per key whose index is a getter too (the left list). A key computed from the index is refused: write key={i} alone.

A part per branch: if

{if (count!() > 3) <Timer />} shows its part while the condition holds (no else needed). The part is remade only when a different branch holds, so the <Timer> keeps its signals as the count goes from 4 to 5; holes inside still follow what they read. An if whose branches are all text, {if (on!()) "On" else "Off"}, is an ordinary text hole.

A part per arm: match

One part per arm: Solid's <Switch>, and its <Show> narrowing a value that may be missing (in Roc, a Try):

An arm's names (card in Card(card)) are getters for the newest value: the part stays, and <CardView title={card.title} /> follows it. For a part remade per value (Solid's keyed <Show>), .map a list of one, keyed by the value or its id: {...[card!()].map(|card| <Editor key={card.id} card={card} />)}.

A component that reads such a name or a row's item once, in its body (shown = card), keeps the first value: a bug. rocx build warns at the call, and rocx check exits with 2. The ways out: read the prop where it is used, write untrack!(|| card) if one read is meant, or key the part by the value as above.

When parts are made

A part (a branch, an arm or a row) is made like a component: once, where it is rendered, its own reads untracked, and again each time it reappears. So a value prop inside, <Podium players={game!().players} />, is read where the component reads it, while the part shows. A signal made inside a part goes with it.

Rows by index: Repeat

<Repeat count!={n!()} from!={first!()}>{|index| …}</Repeat> (import pf.Repeat, Solid 2.0's <Repeat>) makes a row per index from from! (default 0) up to, not including, from! + count!, with no list behind them. When the range moves, only rows entering it are made. With on:viewport it becomes a virtual list: packages/virtual renders a million rows as the twenty that show.

Stores#

A store (Solid 2.0's createStore) holds many parts in one value, each read on its own. Use one where a single signal would rerun every reader on every change: a board, a big form, a filtered list. Roc has no proxies, so a read selects a part with a function, tracked by the value selected:

  • A part's readers rerun only when it changes. Each write recomputes every selection and compares it with its last value by ==: clicking Done reruns the filter's hole alone. So a part must be data (a type of your own needs an is_eq), not a function or markup.
  • A write is a function of the state (Solid 2.0's draft setter, with Roc's record update as the draft). Two writes in one handler compose.
  • A read outside a computation (a handler, a component's body, untrack!) selects once, untracked.
  • Store.of(board!) (import pf.Store) reads any accessor by parts: an endpoint's answer, a memo, a prop. It has no setter. In a hole or an effect's compute, Store.of(user!).get!(|u| u.id) reruns only when the id changes.

The cost: each write runs every live selection of its store (four hundred take about half a millisecond). Solid's store touches only the paths written.

Selectors#

When one row of a list is picked (selected, open), every row reading a plain signal reruns on each pick. A selector (Solid's createSelector) answers whether a key is the picked one and tracks each key on its own: a pick reruns only the row it leaves and the row it comes to.

Its source is any accessor (a signal, a memo, a store's part), and keys have its type. On the server it is computed once, like a memo.

Contexts#

A context (Solid's createContext, useContext) gives a value to every component under its provider, however deep. The picks above and the tally below read their list and setter from one. Here is the context (no default) and the record of accessors and setters it provides:

Its provider is a tag named after it (picks_context gives <PicksContext value={…}>). Under it, use_context! reads the value:

  • Defining one. name = create_context() must be provided; create_context("light") has a default. Either is a module's definition, in a file importing pf.Context. rocx names each after its module and definition: Context.required("Demos/Picks.picks_context") (or Context.define, with a default). create_context has no !: it makes nothing until provided.
  • Providing it. The tag (the name in PascalCase) works in the context's module or any module importing it, in a file importing pf.Context. It takes value={…} and children. A layout can provide one for every page under it.
  • Nothing above? A context with a default gives it; one without fails, and the nearest <Errored> says so.
  • Read it in a component's body or a computation, and keep what it gives for your handlers, as the tally does. A component sees what is above where it is rendered, because rocx defers each component's call (Html.component(|| …)) until the runtime builds that place.

A page is one tree: its layouts, the page, and their components. A component goes on a page as in another component, by its tag. Nothing to register, no islands.

Handlers#

A handler is the function an event runs, written on the element: on:click={|| set_count!(count!() + 1)}. Its writes apply when it ends, and each computation that read them runs once then. A dotted name after the event gives the handler what the event carries, or narrows which events it runs for:

WrittenWhat the handler gets
on:click={|| …}Runs on the event, given nothing. Any DOM event works: on:input, on:focus, on:dragstart…
on:input.value={|text| …}The field's value.
on:change.checked={|on| …}Whether the box is ticked.
on:keydown.key={|key| …}The key's name, as the browser has it: "k", "Enter", "ArrowUp".
on:keydown.keys={|keys| …}The key and the modifier keys held, a record (Html.Keys): if keys.mod and keys.key == "s" { save!() }.
on:keydown.Escape={…}Runs for that key only, with no modifier key held.
on:keydown.Shift+Enter={…}, on:keydown.Mod+K={…}Runs with exactly those modifier keys held. Mod is ⌘ on macOS and Ctrl elsewhere.
on:click.prevent={…}The browser's default is prevented first: a link's click goes where the handler says, not to its href.
on:frame.ms={|ms| …}Runs every animation frame while the element is on the page, given the milliseconds since the last frame (at most 100).
on:viewport={|view| …}The part of the element's content that shows (Html.Viewport: top, left, width, height), once it is on the page, then on each scroll or resize, at most once a frame. A virtual list renders by it.
on:pointermove.point={|point| …}Where the pointer is over the element, as fractions of its width and height from 0 to 1 (Html.Point), at most once a frame. Live cursors send this.
on:drop.files, on:paste.files, on:change.filesThe files dropped, pasted or picked (drag and drop).
  • Keys with modifiers run only with exactly the modifiers named (Shift+Enter isn't Enter), and the browser's own action is prevented: an arrow key a game takes doesn't scroll, and ⌘K doesn't focus the browser's search.
  • The whole document. A page-wide handler (⌘K anywhere, Escape to close a panel) goes on <Document on:keydown.Mod+K={open!} />. It renders nothing and listens while its part is on the page, so an if around it turns it on and off. <Document on:visibilitychange.visible={|shown| …} /> is told whether the page shows (false while its tab is hidden); <Window on:resize={…} /> listens to the window.
  • A form's on:submit runs instead of a page load (the runtime prevents the default). A form that posts to an endpoint is different (forms and submissions).

Going to another page

Timers, sounds and the browser

  • Timers. set_interval!(ms, tick!) runs tick! every ms milliseconds; set_timeout!(ms, done!) runs done! once after ms. Each returns a clear!, and stops by itself when what started it goes (effects, cleanups and timers).
  • The time. Time.now_millis!({}) and Time.now_nanos!({}) (import pf.Time, as on the server) read the clock in a handler, an effect's apply or a timer's tick. Never while rendering: the markup would differ from the server's.
  • Sounds. Audio.play!("/sounds/eat.wav") plays any sound file the browser can, with nothing prepared (Audio.play_with! sets volume and rate). It comes from the packages/audio plugin; the showcase's games use it.
  • The page's own JavaScript. For what the platform has no module for (vibration, the clipboard), Browser.call!("vibrate", { ms: 50 }) (import pf.Browser) calls the function the page gave the runtime as vibrate (Runtime.load(wasm, { effects })), with the argument as parsed JSON, like Elm's ports. Browser.focus!("card-title") focuses the element with that id. Both run after the handler and the page's patch; in an effect, on_settled!(|| Browser.focus!("card-title")) focuses a field as its part shows.

Effects, cleanups and timers#

An effect is what a component does outside its markup: listen to a stream, run a timer, focus a field, call the browser. As in Solid 2.0, create_effect!(compute, apply) has two halves: compute reads, tracked; apply acts on its result once the markup is on the page. When a read changes, compute reruns, then the last apply's cleanups, then apply.

  • apply runs like a handler: untracked, its writes applied when it ends. Every run of compute runs it, uncompared; to act only on a real change, read through a selection: create_effect!(|| Store.of(user!).get!(|u| u.id), |id| …).
  • An effect goes with what made it (an if switching branch, a row going), running its cleanups.
  • on_cleanup!(|| …) (Solid's onCleanup) runs when what is running now is done: a component, when it goes; a computation, before it reruns; an effect's apply, before the next. What a part owns goes first, then its own cleanups, last one first. In an event handler it fails, since nothing would run it.
  • A listen started in an effect stops with it: the request is aborted. One started in a click's handler runs to the stream's end.
  • Timers clean up too, as if their starter had called on_cleanup!(clear!). A component's timer stops when the component goes; an effect's, before its next apply and when the effect goes; an event handler's, when its element goes. The server starts none. The showcase has a stopwatch, a search that waits for a pause in typing, and a clock that goes with its if.
  • on_settled!(|| …) runs once, in the browser, once the component is on the page (Solid 2.0's onSettled, formerly onMount). An on_cleanup! inside runs when the component goes. Browser-only work goes there: reading what the page kept, focusing a field, measuring.
  • A render effect applies at once. create_render_effect!(|| query!(), |_| set_page!(1)) (Solid 2.0's createRenderEffect) applies right after compute, during the render: in a component, before its markup is built; in an update, before other effects apply. It keeps a value in step with the render, with no frame between; anything that reads the page wants create_effect!.
  • An effect can handle its own failure. create_effect_with!(compute, { apply, error }) is Solid 2.0's createEffect(compute, { effect, error }). When compute fails (a failed read, a missing context), error gets why after the update, instead of an <Errored> showing. When compute succeeds again, apply runs.
  • On the server, no effect runs. The browser hydrates the page as it was before any effect, then runs them. (Solid's server runs both halves of a render effect; here, its first apply's writes are patched in during hydration.)

Waiting and failing#

A hole that reads an endpoint waits for its answer. Meanwhile <Loading> shows a fallback until the first values come, and <Errored> one when something fails (import pf.Loading, import pf.Errored).

The design came from this component in the browser platform's tests: five answers (you, your posts, friends, likes and notifications), one spinner until all are in. Posts and friends can each fail alone; anything else fails the whole. (Api.current_user!({}) and the others wrap Endpoint.read!, which reads a GET endpoint.)

  1. Asking Five memos, five requests, all at once. The <Loading> shows its fallback until every one is in: one spinner, not five.
  2. In Everything appears at once. A later change that waits, such as a rename, keeps what is shown until its answer is in: no spinner again.
  3. Posts fail Their <Errored> shows its fallback, with an Again button, and the rest stays. Anything else failing fails the whole, which can try again too.
  • <Loading fallback={…}> shows its fallback until everything inside has its first values. Later waits keep what is shown; is_pending! can flag them.
  • <Errored fallback={|problem, retry| …}> shows its fallback when something inside fails: a refused read, a request with no answer, a context nothing provides. It gets why (a Str) and retry, a handler that asks again for what failed (and the failed reads it came from, even ones nothing inside reads), then renders the children again.
  • A failure no <Errored> of yours catches reaches the app's root one, which rocx writes: the page answers with its error page (+error.rocx), with the endpoint's status for a 4xx refusal, else 500 (where no page is).

On the server nothing waits: endpoint reads are answered in-process, and the browser reads the answers from the page. Talking to the server follows one read from the server's render to a click in the browser.

Loading again: is_pending!#

A memo reading again (after a refresh!, or because its URL changed) keeps showing the old value, with no spinner. is_pending! (Solid 2.0's isPending) tells the reader it is about to change. The first load is <Loading>'s job; loading again is is_pending!'s.

  • True while a memo the accessor reads has a value and waits for a new one, from the update the click started until the answer is in. A memo that reads a pending memo is pending too: is_pending!(count!) is true while count!, which counts posts!(), waits with it.
  • False on the first load (<Loading>'s job), for a failed read (<Errored>'s), and on the server, which renders final values, so hydration sees false too.
  • Several at once: is_pending!(|| (user!(), posts!())) is true while any of them is.
  • It never waits or fails, and doesn't make its caller depend on the values it reads: its caller reruns only when its answer changes. The class:stale above is patched twice a refresh, on and off.

latest!(posts!) (Solid 2.0's latest) is the last value a memo settled at. Every read here gives that already, since nothing holds writes back as Solid's transitions do; it exists for code written the Solid way.

No live demo here: this site's static copy answers reads from files at once, so there would be nothing to see. A form's submission.pending!() is different: whether a submission is on its way (forms).

Forms and submissions#

A form posts to an endpoint, which reads its fields as a record. use_submission!(endpoint) (import pf.Router exposing [use_submission!], Solid Router's useSubmission) is the latest submission to it: pending!(), input!() (what was typed, as the endpoint reads it), field!(name), result!(), error!(), and clear!() and retry!() for a handler. The runtime sends a form posting to one of the app's endpoints with fetch, so only the page changes:

  • A form whose submission a component reads gets its result or refusal there; a result reads the page's data again, and a redirect is followed.
  • A form nothing reads is followed in place like a plain form: back to the page with the flash (below), or to the endpoint's redirect.
  • A form that succeeded is emptied (data-rocx-keep keeps it). A server failure shows in the nearest <Errored> around the form.

Without the runtime (before it loads, or with JavaScript off), the form posts like any HTML form, and the endpoint sends the browser back with a flash: what was typed and the result or refusal, kept on the server for a minute under an id in a cookie. The page's submission is then the flash, so the page looks as it would with the runtime and hydrates as rendered. Server.flash!({}) reads it directly: Ok({ url, fields, status, body }) or Err(NoFlash). The endpoint's side and redirects: forms, on the server page.

Actions and optimistic values#

use_action!(endpoint) (Solid Router's useAction) gives a function a handler calls with the endpoint's arg, without a form or waiting: each call is a submission, sent as JSON when the handler ends. A form posting to the same endpoint sends fields, read into the same type (a number from its text, an unticked box as false). use_submissions!(endpoint) (useSubmissions) lists every submission: whether on its way, what it sent, its result or refusal.

An optimistic value is the server's data with the pending submissions applied, shown before the server confirms. Drag a plan to another day: it moves at once, though the server takes 800 ms and refuses a full day or the dentist.

What the runtime did, newest first

  1. Waking up…
  • It shows at once. The memo reads the server's week and the moves on their way (pending_inputs!()); a drop adds one, so the plan shows where it was dropped.
  • It gives way without a flicker. A result has every endpoint the page read read again (Solid Router's revalidation), and the submission stays on its way until they are in; then the server's week and the move's end show together. Meanwhile is_pending!(plans!) is true, and the week dims.
  • A refusal puts it back and says why: its error is the refusal (Refused(409, why)) until moves.clear!(id).
  • Several can be on their way, each answered on its own. Apply a value (a plan's day), not a step (one more): the server's data, read again, may already include a pending move.
  • Nothing optimistic exists on the server: the browser hydrates the week with no submissions. Submissions are kept by the endpoint's URL, so what varies goes in the body, not the path.

Or the other way round, as in Solid 2.0: create_optimistic!(|| board.read!()) is a signal holding the server's value until a handler writes it. The write shows at once and holds until that handler's submissions are done and the page's reads are in again; then it is undone in the same update, with no flicker. A refusal undoes it at once, as does a write whose handler sent nothing. Use it for a value the handler knows; use the memo above for many pending moves on the latest data.

  • What a result reads again is the endpoint's call (Solid Router's revalidate keys): Router.revalidate!([Endpoint.url_of(Api.get_board({}))]) in its handler limits it to that URL and those under it (after / or ?); [] means none. In a browser handler, it reads them again at once.
  • Retrying: submission.retry!() or moves.retry!(id) resends what was sent, pending again.
  • A form's fields given ahead of time (Solid Router's action.with): Endpoint.url_of(Endpoint.with_fields(toggle, { id: todo.id })) is the form's action, its fields in the URL (/todos/toggle?id=7), read before the form's own, with or without JavaScript. An action binds values with a closure instead.
  • Files: a form with an <input type="file"> (enctype="multipart/form-data") is sent as the browser sends it, as is an action whose arg holds a file's URL (dropped, pasted or picked). The endpoint reads the field as the file's name, and its bytes with Server.file(request, "photo").

Drag and drop#

Drag and drop are plain events: on:dragstart and on:dragend on what is dragged (with draggable="true"), on:dragenter, on:dragleave and on:drop where it goes. Keep what is dragged in a signal: dragstart sets it, drop reads it, as the planner above does:

  • Only an element with a drop handler is a drop target: the runtime accepts a drag over it as a move (preventing dragover's default) and keeps a dropped link or file from opening in the tab.
  • Its dragenter and dragleave are its own, like mouseenter and mouseleave: a child fires neither, and a drop or the drag's end counts as leaving. So a lit day stays lit over its plans.
  • It works in every browser, Firefox included (the runtime adds the data Firefox needs to start a drag). on:drop.value gives text dropped from elsewhere: a link, a word from another program.
  • By touch and pen too. Holding a finger still on a draggable element for a quarter second starts the runtime's own drag, firing the same events; swipes still scroll and taps still click. A copy follows the finger, and a scrolling list scrolls near its edge. A mouse keeps the browser's drag, which can reach other windows. Give keyboard users another way, as the planner's menus do.
  • What a drag carries for other pages: drag:data={[("text/uri-list", url), ("text/plain", title)]} puts each piece on the drag by type, so a link dropped in another tab opens. A drop target gets every piece with on:drop.data={|items| …}. drag:image={id} shows a copy of the element with that id (hidden or not), held where the dragged one was grabbed.
  • Files dropped, pasted or picked come to on:drop.files, on:paste.files or a file input's on:change.files, each with its name, type, size and a blob: URL to show it by (<img src={file.url}>) while the element is on the page. An action sends one as a field of its arg.

Transitions#

A row or part can animate as it comes and goes, with the transition written on the element as in Svelte (import pf.Transition). A leaving element stays in place, inert, until its animation ends. The browser plays the animations, so they cost Roc nothing per frame.

  • transition={…} plays both ways; transition:in={…} and transition:out={…} one each.
  • A transition is a Roc value: Transition.fade, Transition.fly({ x, y }), Transition.scale(0.5), Transition.grow(Bottom), or your own hidden style, animated to and from the element's own: Transition.style([("opacity", "0"), ("translate", "0 8px")]). .ms(…) (default 200), .delay(…), .easing(…) and .origin(…) adjust it; .plus(…) plays two at once. A style value with anything but letters, digits, spaces and .,%#()-+ is dropped, so data can't write CSS.
  • They play when a row or part comes or goes, on that row's or part's own elements only (Svelte's local transitions): a list inside a leaving part stays as it is. Nothing plays during hydration.
  • A transition that reads a signal is computed like any attribute, and the one current when the element goes plays. Chart bars shrink into the axis, up or down by their value: give a bar chart new data and watch.
  • Moves: transition:move={Transition.glide}. When a change moves the element (reordered, or pushed by one coming or going), it glides from its old place to its new one (the FLIP technique: measured before and after). With a key={…}, an element is the same anywhere on the page: leaving one list as it enters another, it glides between them, with no in or out transition. Moving between scrolling boxes (a card into another column), it glides above the page, unclipped, growing or shrinking to its new size. The planner's plans glide from day to day.
  • With prefers-reduced-motion, none plays: what goes, goes at once, and what moves lands in place.

Solid's core has no transitions (the community's solid-transition-group uses classes and a callback). Roc Solid takes Svelte's form, because a transition on the element is a value the compiler checks.

The document's head#

<Title> (import pf.Title, as in @solidjs/meta) sets the document's title from anywhere in the page, its holes live. The last one rendered that is still on the page wins: a page's over its layouts'; one in an if's part while that part shows. With none, the root layout's own <title> stands.

  • On the server, it goes first in the <head>, as a <title data-rocx> before the layout's own, since browsers take the first. The layout's <head> is rendered as written, and hydration passes over the platform's element.
  • In the browser, the runtime keeps document.title in step: a changed <Title> changes it, and one that goes hands the title back to the one before it, or to the layout's.

The other @solidjs/meta elements need no import: <Meta name="description" content={post!().summary} />, <Link rel="canonical" href={…} /> and <Style>p { … }</Style>, written like their lowercase tags, anywhere in the page. The server puts them just before </head>, in render order, and the browser keeps them there, following their holes. A later <Meta> with the same name (or property, http-equiv, charset) replaces an earlier one, so a page can replace its layout's default description. Hydration keeps the server's elements, so a stylesheet isn't loaded twice.

Where they differ, Roc is the reason:

  • Names end in !: reading or making a signal and rendering a component are effects to Roc (count!(), create_signal!, Picks.view!).
  • A pair is a tuple ((count!, set_count!) = …): Roc's list patterns can't take a list apart into names.
  • Props are getters, and destructuring keeps them: props can only be named by a Roc pattern, so |{ text }| reads like props.text (props that change).
  • A row says its key: Solid keys a row by its object's identity, and Roc's values have none.
  • Branches are Roc's if and match, not components. A match narrows a Try where <Show> narrows what isn't null. rocx reads the branches before the compiler, as Svelte reads {#if}.
  • rocx names a context after its module and definition, since values have no identity. create_context has no !, so it can be a module's constant.
  • An effect's apply calls on_cleanup! instead of returning a cleanup: a Roc function can't return "nothing" when it has none. Neither half gets the previous value.
  • A submission's fields are methods (submission.pending!()), and a form's action is the endpoint's URL: Roc can't turn an endpoint into a string by itself.
  • A setter takes a value. A Roc function takes one type of argument, so Solid's function form is update!(count!, set_count!, |c| c + 1), given the accessor since Roc can't tell which signal a setter writes.
  • Signals don't compare. A signal may hold functions, which Roc can't compare, so a write always runs its readers (Solid skips an equal one). Memos and store selections compare with ==. Keep state nothing shows (the snake's time since its last move) in a signal nothing reads.

Under the hood#

  1. A component runs once, where it is rendered and returns markup whose holes are Roc closures. The runtime, in JavaScript, keeps them as boxes and runs them as needed, running the components inside as it builds.
  2. A read that has to wait stops its hole It throws, in JavaScript, through the Roc code that made it. The runtime restores Roc's stack pointer and reruns the hole when the value is in. No JSPI needed.
  3. On the server, nothing waits Reads are answered in-process; comments mark the holes. The answers go at the page's end, with the script that starts the browser's side.
  4. In the browser, nothing is made twice The runtime walks the document, binding each computation to its node with the answers from the page, and skips every <NoHydration>.

The browser platform has the rest: the wasm, its host, the runtime, and the numbers. The platform reference types every function in the modules used here (Solid, Store, Html, Router and the rest).

Roadmap#

Solid 2.0 is the roadmap: what it has, Roc Solid should have, unless Roc says otherwise.

Works now

  • Signals and update!, memos, refresh!, is_pending!, latest!, untrack!
  • Holes in text, attributes, classes and styles; static when nothing they read changes
  • Pure and effectful components; getter and accessor props; {...rest}
  • Warnings for a value read once in a body, an arm or a row
  • Contexts; components that run where they are rendered
  • One tree per page, hydrated whole; <NoHydration>
  • if and match in a hole, each part kept while its branch holds
  • .map by key and by position; <Repeat> by index
  • Stores tracked by part; selectors; rows told only when their item changed
  • <Loading>, <Errored>, retry
  • Handlers that wait for the server; modifier keys; frames; on:viewport; document and window events
  • Effects split as in Solid 2.0; render effects; error handlers; on_cleanup!, on_settled!
  • Timers, cleared by clear! or with their part
  • Forms sent by the runtime; submissions; a flash without it
  • Actions, submissions, optimistic values, retry!, revalidate keys, fields ahead of time, files
  • Drag and drop by mouse, touch and pen; drag data and image; dropped files
  • Transitions in and out; moves, keyed across lists
  • <Title>, <Meta>, <Link>, <Style>
  • Navigating without a load: links, navigate!, back and forward, the query in place
  • Sound files (Audio.play!) and the page's own functions (Browser.call!)

Not yet

  • Derived stores and projections (createStore(fn, seed), createProjection); a memo does for now
  • createOptimisticStore; reconcile and storePath
  • Store writes that touch only the paths written (each write runs every live selection)
  • Finer reads within a row (a changed item reruns all its row's holes)
  • A dev warning for a value read once in a helper function or at a .map row's top
  • Dragging by keyboard (offer another way, as the planner's menus do)
  • Loading only a page's own components (every page loads one wasm with all of them)

A working prototype

Roc's new compiler is pre-0.1, and so is this. The pieces are tested together, on the server and in a real browser; what's missing is listed above.
