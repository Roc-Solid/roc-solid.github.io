Routing

A page is a file

An app's URLs come from the files under its routes/ directory, as in SvelteKit. A +page.rocx is the page at its directory's path, wrapped by the +layout.rocx files above it. A +server.roc answers HTTP requests at its path, and +error.rocx is shown where nothing answers. Every page gets a typed path and every endpoint a typed function, so a link to a missing page, or a call to a missing endpoint, fails to compile.

The files#

This site's route files, one for every page you can open here:

FileWhat it is

routes/blog/+page.rocxthe page at /blog
routes/blog/[slug]/+page.rocxthe page at /blog/anything, given params.slug

routes/admin/+middleware.rocthe middleware around every page, endpoint and channel in admin/ and below it (below); routes/+middleware.roc runs around every request

routes/.well-known/…routed, as RFC 8615 asks; any other directory whose name starts with a dot is skipped

Each directory names one part of the path, in lower case (blog, getting-started, feed.xml), or a param in brackets ([slug]). It may start with an underscore, for a path another service names (_verify is verify in Api and Paths). rocx build refuses other names, and says why.

A page#

A route file has no module header: imports, then definitions. A page defines view!, the component that renders it, and may define meta, a record its layouts are given. On this site, meta holds the title, the description and the table of contents on the right:

  • view! is given the page's params: view! = |{ params }| …, a record of strings, or of the types its handlers give them ({} without params; write |_|). A page is an effectful component: its body runs once, and it may make signals.
  • Its data comes from endpoints. A page isn't given the request. It reads its location with Router.location!({}) and its data with Endpoint.read!, answered by the server as it renders (talking to the server). What middleware knows, such as who is signed in, comes the same way, from an endpoint behind it (below).
  • Imports are relative to the file. This one is two directories down, so the site's components are under ../../Ui.
  • A route file can define components of its own (Board := [].{ view! = … }) and use them as <Board />. Put them before or after the file's definitions, not between: rocx writes them as types beside the page's module, so their view! isn't taken for the page's (an example). They can use the file's other definitions; a name a component defines itself is its own.

Layouts#

A +layout.rocx wraps every page in its directory and below it. Layouts nest, the outermost first. The root one, routes/+layout.rocx, renders the whole document (<html>, <head>, <body>); without one, an app gets a plain document. A layout's view! is given:

  • children: the page, or the next layout in;
  • params: the ones its directory names (routes/[lang]/+layout.rocx gets lang; the root layout gets {});
  • meta: the page's meta. Every page under a layout that takes it must give it the same type; rocx build reports a page whose meta has other fields, or none. Where no page is, the error page's meta stands in.

On navigation, a layout stays, with its state, while its file and its own params are the same (navigating). This site's one layout, the document around every page, reads the location where it uses it, so it is kept:

Params, and typed links#

A directory in brackets is a param: routes/blog/[slug]/+page.rocx is the page at any /blog/…, and its view! is given params : { slug : Str }. A param is a string, decoded from the URL, unless a handler's annotation gives it another type. Fixed parts are tried before params, so /blog/new can be a page of its own beside /blog/[slug]. A directory may name a file, with dots between letters or digits: routes/sitemap.xml/+server.roc answers /sitemap.xml, and its names drop the dot (Api.get_sitemap_xml). rocx also writes Paths: a string for each page without params, and for each page with them, a function that encodes them into the URL. Link through it, and a link to a missing page, or with the wrong params, fails to compile at your line (Paths.blog_slug({ slg: "x" }): Maybe slg should be slug?). Paths.all lists the pages without params.

Typed params. A handler's annotation may give a param a type other than Str: a number, Bool, or a union of tags written out ([Draft, Live]). The router reads the path's part as that type first; a part that doesn't read is no match, so /api/count/five is a 404 the handler never sees. The type is the directory's: its handlers must agree (rocx build says where two differ), and its pages, layouts, Paths and Api take it too. A page whose endpoints are under api/ declares its own, Params : { id : I64 }: rocx never reads a page's types from another directory. This site's count of events is typed:

Where no page is#

routes/+error.rocx is the app's error page. A browser asking for a path nothing answers gets it, inside the root layout, with a 404; other clients get a plain-text 404. A page that fails shows it too, unless an <Errored> inside catches the failure. Its status is the 4xx an endpoint refused a read with (NotFound makes the page a 404), or else 500. The error page's view! is given status and problem, why it failed, as text. Without one, an app gets a plain one. Endpoints: +server.roc#

A +server.roc (+server.rocx if it has markup) answers HTTP requests at its directory's path, with a handler per method: get!, post!, put!, patch! or delete!. A handler gets the request, the path's params, its middleware's context and, for a method with a body, the body as its annotated type. It answers Ok(result), sent as JSON with a 200, or Err(refusal), such as BadRequest(why) (400) or NotFound (404). Annotated Try(Server.Response, Endpoint.Refusal), it answers with its own response: a redirect, a cookie, a file that isn't JSON. This one answers the form on this site's joining page and sets a cookie:

  • Bodies. JSON (application/json) and forms (URL-encoded, or multipart/form-data with files) are read; a missing or unreadable field is a 400 that names it. Any other body, such as raw bytes, isn't: the handler takes {} as its body and reads the bytes from request.body.
  • Checked bodies. Beside the handler, post_body = Signup.form (a form of packages/forms) reads and checks the body, form or JSON, before the handler runs; the handler's body is the rules' record. A body that fails is a 422 with the issues as JSON, and /openapi.json documents it with the rules' schema (D-093).
  • Three more names. events! answers a GET that asks for events (accept: text/event-stream) with a stream (events). channel! defines a channel pages subscribe to (channels). respond!, given the request, params and context, answers every method the file doesn't name with its own Server.Response: a page mounted from elsewhere, a JSON-RPC endpoint.
  • A path is a page or an endpoint. A page's endpoints (what it reads and what its forms post to) live under routes/api/, at the page's path: the page at /members reads GET /api/members. One URL, one answer, so no cache mixes them up. A directory may still hold both: a browser's GET (accepting HTML) gets the page, anything else the endpoints, with Vary: Accept. An unanswered method is a 405 listing the answered ones (Allow).
  • Typed at both ends. Each handler must be annotated: rocx copies the annotations into Generated/Api.roc, which any module may import (a component, a job, an actor), and binds each handler in Generated/Handlers.roc, on the server only (what rocx writes).
  • A form posted without JavaScript goes back to its page with a flash the page reads (forms): JSON would show as a bare page.

Talking to the server shows the rest, with this site's endpoints live.

Middleware: what runs, in what order#

Middleware runs around the answer to a request. Given the request, the context so far and next! (what comes after it), it can answer itself (a guard's redirect or 401), pass the request on with more context (who is signed in), or change the answer coming back (add a header). Guards, sessions, security headers and logs are middleware; a.then(b) runs a, then b.

Middleware goes by folder. A +middleware.roc names the middleware around every page, endpoint and channel in its directory and below; nothing else runs any. The one in routes/ is the app's, around every request (a package's handlers and paths nothing has included). This site's adds two headers to every answer:

Below it, each runs inside the ones above, outermost first; what one hands on is the context of the next and of the handlers inside (get! = |{ context, .. }| …). The members' page and its endpoint, /members and /api/members, sit in a group, routes/(members)/, and share one guard; the joining page, routes/members/join/, has its own. Before any of them, a change sent by another site's page (POST, PUT, PATCH or DELETE) is refused, unless App.program says cross_site: Allowed. This site's middleware:

A request to /members goes through routes/+middleware.roc's middleware, then the group's Middlewares.member, then the page, and the answer goes back out through them. The page isn't given the context: it reads GET /api/members, which the server answers through the endpoint's route, behind the same middleware, so the handler gets the member's name. A handler's Endpoint.send! and an MCP tool made from an endpoint go that way too: what guards an endpoint guards every way to it. rocx routes lists every route and what runs around it, outermost first:

  • The context is typed. member is a Middleware({ facts : Str }, { facts : Str, member : Str }): it adds member to the context it is given. The members' endpoint can read context.member; outside the group, that wouldn't compile.
  • A new file is guarded by where it is. A page or endpoint added to the group runs behind its middleware with no line of its own. A route file can't name middleware: rocx build refuses middleware = … in a page, an endpoint, a layout or the error page, and says which +middleware.roc to move it to.
  • Only some requests. Middleware.when(Server.changes, guard) runs guard only for requests that change something, and lets reads by: a rate limit on a form's posts, say.
  • Try it with just dev. /members sends you to join; join, and it greets you by name. These pages aren't in the static copy of this site, which has no server.

Navigating without a reload#

A click on a link to another of the app's pages doesn't reload, as with Solid Router. The runtime fetches the new page's HTML document as a reload would: from the server, through its middleware, with reads answered and redirects followed (on a static copy, the file the build wrote). The app's wasm already holds every page's code, so it renders the new page from the document's answers and <NoHydration> parts, and asks for nothing else. Every link works this way, with no change to the app.

The old page stays until the document is in. Then the address is pushed to the history, the new page is made, and its <head> is updated (loaded stylesheets stay). The page scrolls to the top or to the link's #hash, focus goes where a reload would put it (an autofocus element, or the page's start), and a screen reader hears the new title. Back and forward render their entry's page the same way and restore its scroll. A document fetched in the last ten seconds is reused.

  • Layouts are kept. Each layout below the root one, and the page, is a level, made anew only when its file or its own params change: from one blog post to the next, the blog's layout keeps its sidebar's scroll, an open menu and its signals. A level that reads its location once, at the top of its body (path = Router.location!({}).path), would show a stale location, so the runtime remakes it on every navigation and a dev build warns in the console. Read the location where you use it, in markup or a memo. A kept level's <NoHydration> parts come from the new document.
  • A change of the query alone happens in place. A link to ?days=30, search.set! or navigate!("?days=30") fetches no document: the page and layouts stay, and what read the query reads it again. A read whose URL changed asks its endpoint (behind its middleware), showing its last value meanwhile. Back goes to the previous query. A <NoHydration> doesn't follow the query: the browser has no code for it.
  • The server decides, as on a reload. The document is a page's GET with x-rocx-navigate: 1, so middleware that counts views can tell it from a reload. Guards refuse or redirect as usual, and a redirect lands at its address. The browser reloads instead when the target isn't one of the app's pages (a plugin's page, a file, a path no page has), when the answer isn't a document of this build (a text 401, a crash, a new deploy's page), or when the fetch fails.
  • A link is fetched before it is clicked. Hovering, focusing or touching a link prefetches its document (x-rocx-navigate: preload), so the click asks nothing. A prefetch renders a page that may never be seen: middleware that counts views should skip those, and an app with costly pages can turn prefetching off.
  • Leaving unsaved work can ask first. A component holding unsaved work registers a listener with use_before_leave!. Before each navigation away (a link, navigate!, a form's redirect, a query change, back and forward), it is told where to (to, from, and for back and forward how far, delta). It may stop the navigation, keeping the page and its address, or hold it while the app asks; leave.retry!(Bool.True) then lets it go, skipping the listeners (Bool.False asks them again). A listener decides from what the page has, without asking the server, and goes with its component. A real page load (another site, a reload, the tab closed) can't be held: when a listener would stop one, the browser asks the visitor itself. The tasks example's task page does this.
  • Page scripts run on a load only. A navigation doesn't run the new page's <script>s. Script that sets up on rocx:ready should also do so on rocx:navigated, a document event with the URL and how long the navigation took (this site's inspectors do).
  • What the old page started stops with it. Its effects' cleanups run, its timers and event streams stop, and its channels are left, unless the next page subscribes to one too.

What rocx writes#

rocx build turns the routes into Roc modules under Generated/. You never edit them, but knowing them helps you read the compiler's reports:

Roc names a module after its file, and +page isn't a valid name, so each route file becomes a module named after its path (routes/showcase/+page.rocx is ShowcasePage). rocx keeps the lines where they were: the module's first line goes on the blank line after the imports (or, with none, at the start of the first definition's line). The OpenAPI document#

An app can serve an OpenAPI document (3.2) of its endpoints, for client generators or people exploring the API. It lists:

  • each path and its params (a typed param with its type's schema);
  • each method, with the doc comment above its handler. The comment's first sentence, without a method and path it may start with, is the summary Swagger UI and Scalar list the method by: ## POST /api/shout: what it is sent, shouted. gives What it is sent, shouted.;
  • the JSON Schemas of what each endpoint is sent and answers: the handler's types as the compiler has them. This site's GET /api/shout/{word} answers { word : Str, shouted : Str, bytes : U64 }, and its document says so.

Pages' endpoints are in it too. A body a form can send (a record of text, numbers, yes-or-no, choices and lists of them) is listed three ways: application/json, application/x-www-form-urlencoded and multipart/form-data, with one schema, except that a form may leave out a yes-or-no or a list, as it leaves out an unticked box. A body checked by rules (post_body) is listed the same three ways, with the rules' schema: what they require, and their lengths, patterns and ranges.

Turning it on

An app serves it from routes of its own (D-116): routes/openapi.json/+server.roc answers with the document, and routes/openapi.html/+server.roc with a page that shows it in Swagger UI or Scalar. Without them, neither is served.

  • They are routes like any other: their folder's middleware runs around them (put them in a guarded group to keep the document from strangers), and rocx routes lists them. Under --dev, the server lists the page as it starts.
  • The page loads its viewer from jsDelivr, pinned to one version and checked against its hash, and tells it not to call home: no validator for Swagger UI; no telemetry, fonts, developer tools or agent for Scalar. Bundling a viewer instead would add 2 to 5 MB to every app's server.

This site serves both: its API, in Swagger UI, and the document.

Who makes it, and when

Neither platform makes it: rocx writes Roc that asks for it, the compiler works it out, and the server only sends it.

A parser that writes

Roc has no reflection: no code can ask what a type is. But the parser the compiler writes for a type works with any format: it calls the format shape by shape (a record, its next field, a string, a number), handing a record's format its field names. OpenApi.Schema is a format that reads nothing: for each part, it writes that part's schema and gives back a value nothing looks at. OpenApi.body asks the compiler for the parser of what the endpoint is sent, for Schema, and runs it:

A tag union is the one shape whose parser doesn't say what it holds: it asks the format for a tag's name, then reads that tag's payloads. So rocx gives the document tags, every name in the app's code (and its packages' and platforms') that could be a tag, and Schema offers each in turn. The parser turns down names not in the union; for the others it reads the payloads, and Schema writes their schemas. [Red, Rgb(U8, U8, U8)] is a string, "Red", or an object, { "Rgb": [r, g, b] }, as Json writes them.

  • A GET with events (events!) answers text/event-stream too: each event's data is JSON, with its schema, and an end event ends the stream.
  • A refusal is every method's default answer: its status, and why, as text.
  • A type of your own (Email := Str.{ parser_for : _ }) is described as Json reads it. Write its parser for any format (encoding.parse_str), not for JSON alone, and the document can describe it too.

Not yet#

  • No static pages with params. This site's static copy writes the pages without params (Paths.all) and behind no directory's middleware but routes/'s. A page with params would need a list of the values to write.
  • One error page, the app's, at the root of routes/: rocx build refuses a +error.rocx anywhere else.
  • No rest params ([...path]).
  • The OpenAPI document calls every JSON field required, describes a type that holds itself (a tree) only so many levels deep, and has no $refs. Its title is the app's directory's name. A tag union's tags come from the names in the app's code, until Roc's parsers say which tags a union has, as they say a record's fields.
