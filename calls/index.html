Talking to the server

One definition, the endpoint's

A page talks to its server through endpoints: handlers for one HTTP method at one path, in a route's +server.roc, typed at both ends. The server answers a page's reads as it renders and sends the answers with the page. Event handlers send endpoints, forms post to them, and pages follow events and channels live. Other clients (another app, curl) get the same answers, behind the same middleware.

A page's data: read!#

Write a get! in a route's +server.roc, and read it in a component with Api.get_….read!(). Api is the module rocx writes, with a function per endpoint. The value is the handler's typed result, for a memo or straight in markup:

From the server's render to a click#

  1. server The component runs as the server renders the page, and the memo reads GET /api/echo/{message} for each message. The server answers each read in-process, through the endpoint's route and middleware, with accept: application/json and the page's cookies and headers. A URL read twice is asked once.
  2. server The page goes out with the chosen answer in the <output>, and every answer in a script at its end, each under its URL (GET /api/echo/hello).
  3. browser Hydrating, the browser runs the same component. The memo finds its answers in the page and asks nothing; the server's nodes are kept.
  4. browser A click, on:click={|| set_draft!(message)}, writes the signal. The memo reruns and finds that message's answer, and the one text node showing it is patched. Nothing is asked.
  5. browser A read whose answer isn't in the page GETs the endpoint's URL: a URL built from a signal (one an <input> writes, say), a read redone with refresh!(memo!), and every read on the page after a submission's result. Meanwhile the memo keeps its last value and is_pending!(memo!) is true; <Loading> waits only for first values. Answers may arrive in any order: the memo takes only the one for its latest ask.

Put a page's data under api/, at the page's path

routes/api/members/+server.roc answers GET /api/members, which the page at /members reads; each is behind its own Middlewares.member (both files below). To pass the page's query on, Endpoint.with_query(Api.get_api({}), Router.location!({}).query) reads /api?weeks=1 for the page at /?weeks=1, and the handler reads request.query. A layout, or a component many pages show, reads an endpoint at a path of its own: this site's footer reads GET /api/facts.

When a read fails#

An answer other than 200 fails the memo or hole that read it, and the nearest <Errored> shows its fallback, given why as text (GET /api/notes/9: 404: Not found) and a function that tries again. To handle a refusal yourself, use Api.get_….send!({}) instead, which returns Ok(result) or Err(problem). A problem is a Server.Problem:

  • HttpErr(why): no answer came (the network, say);
  • Refused(status, why): the endpoint's or its middleware's refusal, or a 404 for a path the server doesn't have;
  • BadAnswer(why): an answer of another type, from a server of another build.

A refusal met during the server's render goes in the page too, so the browser fails in the same place without asking again.

  • A redirect redirects the whole page. When a read's middleware redirects during the render (a signed-out visitor sent to sign in), the page answers with that redirect.
  • A failure nothing catches shows the app's error page (routes/+error.rocx), with the refusal's status if it is a 4xx: an endpoint answering NotFound makes the page a 404. A 5xx, or no answer, is a 500. When an <Errored> catches the failure, its fallback shows and the page is a 200, unless the fallback sets a status with <HttpStatusCode>.
  • Guard the root layout's reads. They run for every page, with nothing above to catch a failure. Wrap the holes that read in an <Errored>, or one failure makes every page a 500.

Who is asking#

The server's GETs during a render carry the page's cookies and headers. So a handler works out who is asking from the request, whoever sent it, and never takes the browser's word for it. The bag on the components page finds its owner this way:

What its directories' middleware hands on, such as who is signed in, is a handler's context: get! = |{ context, .. }| Ok({ member: context.member }) (middleware). A handler can use what only the server has (the database, Kv, jobs, email), and none of it reaches the browser.

Endpoints: +server.roc#

A route's +server.roc (+server.rocx if it has markup) answers HTTP methods at its path: get!, post!, put!, patch! and delete!. Each handler is given a record: the request, the path's params (strings, or the types its annotation gives them), its middleware's context and, for a method with a body, the body, read as its annotated type. It answers Ok(result), sent as JSON, or Err(refusal), sent as a status and why. An Endpoint.Refusal is:

  • BadRequest(why) (400), Unauthorized (401), Forbidden (403), NotFound (404), Conflict(why) (409) or Status(code, why);
  • Json(code, json): a JSON body, sent as application/json, such as a form's issues (Issues.refusal);
  • Answer(response): a response of its own in the result's place (JSON with a cookie).

A handler whose answer is always its own (a redirect that sets a cookie, a file) is annotated Try(Server.Response, Endpoint.Refusal) and answers Ok(response), sent as is. A route file may also name rules to read and check its body with (post_body); a body that fails them is refused before the handler runs.

What they answered when this page's endpoint asked them during its render:

RequestBodyStatusAnswer
GET /api/shout/rocx none 200 {"bytes":4,"shouted":"ROCX","word":"rocx"}
POST /api/shout "hi" 200 "HI"
POST /api/shout "" 400 say something to shout
POST /api/shout {} 400 POST /api/shout can't read its body: Invalid JSON

The app calls them as functions. rocx writes Generated/Api.roc, the app's contract: for each endpoint, a function of the path's params ({} with none), typed by the handler's annotation. It holds the method, URL and types, nothing the handler does, so the browser gets it too and any module may import it: a component, a route, a job, an actor. Generated/Handlers.roc, the server's alone, binds each endpoint to its handler for the router (Endpoint.bind checks that the two agree):

In the browser, an event handler (an on:click, say) sends any endpoint with Api.….send!(arg) and gets Ok(result) or Err(problem). The handler pauses until the answer is in, then runs again; only that run's writes are kept. This component shouts the clicked word, Api.get_api_shout_word({ word: word }).send!({}). What the runtime did, newest first

  1. Nothing yet: shout a word.

On the server, a handler sends the app's own endpoints the same way, Endpoint.send!(endpoint, arg), answered in-process: no HTTP, but through the endpoint's route and middleware, with the request's headers (cookies, authorization). What guards an endpoint guards every way to it, an MCP tool's call too. This page's endpoint asked the shout endpoint this way: ROCX, 4 bytes.

  • A path is a page or an endpoint. A page's endpoints live under routes/api/, at the page's path. A directory holding both still works: a browser's GET (accepting HTML) gets the page, anything else the endpoints, each answer saying Vary: Accept. An unanswered method is a 405 listing the answered ones (Allow).
  • Behind middleware. A POST, PUT, PATCH or DELETE from another site's page (its Origin isn't this server) gets a 403, unless the app says cross_site: Allowed. Clients that aren't pages, such as curl, send no Origin and get through. A directory's +middleware.roc adds more around its routes (middleware).
  • Typed at both ends. Both copies of Api take their types from the handler's annotation, which rocx build requires. A component that sends the wrong body, or reads the answer as anything else, doesn't compile, and rocx check points at its line.
  • JSON both ways. An F64 goes as a number; NaN or an infinity, which JSON can't write, is a 500 that says so. A Try goes as its tag, {"Ok":5} or {"Err":"Empty"}, except two shapes: Try(a, [Null]) is a value that may be null, and a record field's Try(a, [Missing]) may be left out.

Forms: actions and submissions#

A form posts to an endpoint like any HTML form, and the endpoint reads the fields by its body's type. For { name : Str, count : U64, gift : Bool, toppings : List(Str) }, a number is read from its text, an unticked box is Bool.False, and a name sent several times is a list. A missing or wrong field is a 400 that names it. JSON and forms read into the same typed record, so one endpoint takes both.

What Solid Router calls an action is the endpoint here: it already has a URL, a method and types. use_submission!(endpoint), in a component, is the latest submission to it: whether it is on its way, what was sent, and the result or refusal.

  • With JavaScript, the runtime sends every form that posts to one of the app's endpoints with fetch, and the page stays. pending!() is true while the answer is on its way and, after a result, until the page's reads are read again, so the new data and the result show together. Then result!() is the result, or error!() the refusal (Refused(409, "…")) or why no answer came. input!() is what was sent, as the endpoint reads it. After a refusal, field!(name) gives back what was typed in a field; after a result it is "", and the form is emptied (unless it, or what is around it, says data-rocx-keep), so an add form isn't filled again. Only the latest submission counts; clear!(), in an event handler, forgets it. An endpoint's redirect (Ok(Server.redirect(…)), setting a cookie, say) sends the browser there. A form nothing on the page reads is answered as a plain form, followed in place: back to its page with the flash, or to the endpoint's redirect (D-118).
  • Without JavaScript (before the runtime loads, or with it off), the form posts as forms always have. Instead of JSON or text, which the browser would show as a bare page, the endpoint sends the browser back to the form's page with a flash: where the form posted, what was typed, and the result or refusal. The server keeps the flash for a minute (a cookie holds its id) for the next page view to read once; a typed password is never sent back. There the submission is the flash, so the page shows the refusal and the typed field as it would with JavaScript, and hydrates as rendered. Server.flash!({}) reads the flash as it came.
  • The endpoint says where to go next, either way: Ok(Server.redirect(…)), its annotation answering Server.Response, as behind this site's joining page (which sets a cookie too).
  • Without a form. use_action!(endpoint) (Solid Router's useAction) is a function an event handler calls with the endpoint's arg. Each call is a submission, sent as JSON once the handler is done; the handler doesn't wait for the answer.
  • Every submission, and optimistic values. use_submissions!(endpoint) (useSubmissions) lists every submission to an endpoint, from forms or actions: all!(), pending!(), pending_inputs!(), clear!(id) and retry!(id). An optimistic value is a memo of the endpoint's data with pending_inputs!() applied: see actions and optimistic values, live on the components page.
  • Files. A form with an <input type="file"> (enctype="multipart/form-data") is sent as the browser sends it, with or without JavaScript. The endpoint reads a file's field as the file's name, and the file with Server.file(request, "photo"): its name, type and bytes, which Storage.put_upload! can keep. An action whose arg holds the URL of a file the page has (dropped, pasted or picked) is sent the same way. A request's body, files included, is 16 MiB at most unless the server's --max-body says more; over that, the answer is a 413.

Where Roc Solid differs from Solid Router here:

  • A record has no getters, so a submission's fields are methods (submission.pending!()), and input!() is the endpoint's own type, not a FormData.
  • The form's action is Endpoint.url_of(endpoint): Roc can't turn an endpoint into a string by itself.
  • Solid's action.with is Endpoint.with_fields(endpoint, { id }), which puts fields in the form's URL; an action binds its values with a closure instead.
  • Revalidate keys are URLs, not query keys: the handler names which of the page's reads a result redoes with Router.revalidate!([url]), each a URL or its beginning.

Events, as they happen#

An answer is sent once it is whole. For what the server learns piece by piece (a job's progress, a feed, what others did), an endpoint can stream server-sent events instead: events! in a +server.roc answers a GET asking for events (accept: text/event-stream) with Events. This one sends each count from 1 to params.to with its square, 300 ms apart:

  • A stream is a loop. Events.stream is given send!, to send an event, and sleep!, to wait some milliseconds; the stream ends when the loop returns. The server runs it as a call of its own, paused while it sleeps, so it holds up no other request. When the page goes, send! answers Err(Gone), a sleep ends early, and ? ends the loop. Events.from_list(items, ms) and Events.map make the simple ones.
  • Each event is JSON, typed by events!'s annotation, sent as a data: line; an end event closes the stream, so the browser doesn't ask again. Anything may listen: curl -N -H 'accept: text/event-stream' localhost:8080/api/count/3.
  • A component listens with Endpoint.listen!(endpoint, heard!). heard! runs like a click's handler: with Event(counted) for each event, typed as the endpoint's events; then Ended; or Failed(problem), a refusal being Refused(status, why). Started from an effect or an event handler, it listens until its component goes. When an event says an endpoint's data changed, refresh!(memo!) reads it again.
  • Behind middleware, as any endpoint. A guard refuses a stream before the loop runs.

It isn't live here: this site's static copy is files and can't stream. With just dev, the curl above shows one.

Channels: live data for a page#

Each listen! is its own stream, checked once as it starts. For data a page follows live (a board others edit, who is online), use a channel. A route's +server.roc defines one with channel!, a check that lets a subscriber in (Channel.allow(who)) or refuses it. Its annotation types what the server publishes and what pages may say. A lobby that lets everyone in, and a component that subscribes:

  • Subscribe from an effect. Endpoint.subscribe! hears the channel until the effect runs again or its component goes. Endpoint.say! sends to the server, where the route's receive! hears it.
  • Publish from anywhere on the server: Endpoint.publish!, from a request, a job or an actor, reaches every page subscribed with the same params, in the order published.
  • One stream a tab. A tab's subscriptions share one connection. Each channel's check runs again every 15 seconds, so someone who loses access stops hearing. A subscriber that may have missed something hears Resync, its cue to read its data again.

The lobby is live on the live and channels page, with the rest: hooks, reconnecting, the latest value with each key.

What rocx build does#

  1. It names each endpoint by its method and path, in Generated/Api.roc: get_api_echo_message for get! in routes/api/echo/[message]/+server.roc. It is a function of the path's params, so no URL is written twice and wrong params don't compile. Its type is copied from the handler's annotation (body and answer; a channel's Channel(who, message, said)), with the imports those types need and no route file. So a module a route imports (a store, a job, an actor) may import Api too, and publish on a channel by name. A module defining a type a route's annotation names can't import Api, since Api imports it: rocx build says so, and suggests moving the type to a module of its own.

  2. It routes them. Generated/Routes.roc gives each path's requests to its page or its endpoints (each with its handler from Generated/Handlers.roc), behind its folders' middleware. The server's GETs during a render go the same way.

  3. It leaves the handlers out of the browser's copy. The browser's app is built from a copy of the app rocx writes (--client site/build/client), with the same Api but no Handlers and no middleware: only the server runs those, and they may read the environment or the database.

Coming from SolidStart#

SolidStart has server functions ("use server"): code the browser calls at a URL the framework picks. Roc Solid has none. A page's data is a get! endpoint at a URL you choose, read with Api.get_…(params).read!(), so the server's render, hydration, later reads, other clients and the OpenAPI document all meet one handler, behind one middleware. rocx build refuses server!(…) and says what to write instead.

Limits, for now#

  • A page reads with GET. During a render, the server answers GETs of the app's own endpoints (a path, /…). A POST or another site's URL is for an event handler to send from the browser. For another server's data during a render, give the app an endpoint whose handler fetches it with Http.fetch!(url, init).
  • Types must compile in the browser. A handler may use what only the server has, but the types it takes and answers must compile in the browser's copy: rocx build refuses a type from a module that imports pf.Db, at the route's line, naming the type and the module.
  • A static copy of the site has no server. Its pages are files, and so are the answers the server gave at build time: each page's GETs, in the page, and the GETs its components send from event handlers (just site writes those). Any other read, a POST or a stream needs the server (just dev, or wherever the app runs). roc-solid.github.io is such a copy: this page's echo and shout work there, and a demo that sends or follows something (the planner's moves, the lobby's channel) says no server answers.
  • Only the endpoints' handlers stay on the server. Anything else a component imports ships to the browser. The server must check each request itself.
