The ecosystem · packages/testing

Tests that read a page as a person does

Helpers for testing a Roc Solid app. A test finds a heading, a link by its name and a field by its label, as a person using the page does, not by the page's classes.

The same queries, with the same rules, work in a Roc expect and from Node's test runner against the running app, its database and a real browser (four ways to test).

Four ways to test#

Rules and pure components, in Roc

An expect beside the code. Html.to_str renders a pure component, and Dom.parse reads it. Fast, typed, and run by roc test.

The app, over HTTP, from Node

A node:test file builds the app as a deploy does, starts its server on its own port, and asks what a browser would: pages, forms, endpoints, events, and the mail it sent.

Its database and its jobs

Each test gets its own database, Postgres or SQLite, migrated by the server. A test can wait for the jobs it caused and see how each ended.

A real browser

Chromium's headless shell, or Firefox. The page hydrates strictly, and the test clicks and types as a person does. A component with signals is tested through its story.

The queries#

Roc and JavaScript share the queries and their rules. The JavaScript ones use Testing Library's names.

In RocIn JavaScriptFinds
Role(role) getByRole(role) elements with that ARIA role, either written (role="tab") or implied by the tag: a <button> is a button, an <a href> a link, an <h2> a heading, a <ul> a list, an <input type="checkbox"> a checkbox
Named(role, name) getByRole(role, { name }) elements with that role whose accessible name is name. The name comes from aria-labelledby, aria-label, a <label>, alt, the element's text (for a button, a link, a heading or a cell), or title
Text(text)getByText(text)elements whose own text is text, not counting their children's
Label(text) getByLabelText(text) the field that a <label> with that text names (by for, or by wrapping it), or whose aria-label or aria-labelledby says it
TestId(id)getByTestId(id)the element whose data-testid is id
Tag(tag), Attr(name, value)(none)elements by tag, or by an attribute's value, hidden or not

Text is compared as a reader sees it: whitespace collapsed and trimmed. Roles, names, text and labels skip what a reader can't see: an element marked hidden or aria-hidden="true", or styled display: none or visibility: hidden, with everything inside it; and <head>, <script>, <style>, <template> and <noscript>. In JavaScript, a name or text may also be a RegExp, and getByRole also takes a heading's level and { hidden: true }.

Dom, in Roc#

Dom.parse(html) reads HTML into a tree. It expects closed elements, as Roc Solid writes them and a browser serializes them. A query on an element looks only inside it, and two Doms compare with ==.

FunctionGives
page.get(query)Try(Dom, [NotFound(Str), TooMany(Str)]): the one element, or why not
page.first(query), page.all(query)the first match; every match, in the page's order
page.contains(query), page.count(query)whether anything matches; how many do
page.text_of(query), page.texts(query)the text of the one match; the text of each
node.text()what a reader reads in it, whitespace collapsed

From Node#

For what a pure component can't show (pages, forms, endpoints, the database), test the running app from node:test. buildForTests builds the app as a deploy does (rocx build, the browser's wasm, the server); a markup problem, type error or warning throws, reported at its line in the .rocx file. startServer starts that server on a free port, usually once for a file's tests:

app.client() is one person at a browser, with their own cookie jar. Every answer has its status, its text, and a dom with the queries:

A client sends a form in one of two ways:

  • post sends it as a browser does without the runtime: the endpoint answers with a redirect back to the page and a flash holding its result, which the test reads with client.flash (a test's server runs with --debug, so it tells the test what the flash holds).
  • submit sends it as the runtime does once the page has hydrated, and gets the endpoint's answer directly.

read reads a GET endpoint as a page reads it, and events reads an endpoint's server-sent events as they arrive:

With no SMTP_URL, the email plugin keeps the last 100 messages in the server's memory instead of sending them, under --debug (which startServer passes) as under --dev. So each test server starts with an empty mailbox. app.mail() reads the messages (each with to, cc, bcc, reply_to, headers, subject, text, html, and the raw message, in which no header names the Bcc); waitForMail waits for one that matches (a list such as cc matches when one of its addresses does); links finds a message's links:

A database, and jobs#

Each test can have its own database, so tests never see each other's rows. The server migrates it as it starts.

  • On Postgres, testDatabase() makes a new database in the Postgres at DATABASE_URL.
  • On SQLite, testSqlite() makes a database file in its own temporary directory, read and written with Node's node:sqlite. Pass the database itself to the server, startServer(server, { database: db }), so it can wake the server's job workers (SQLite can't tell another process that a row changed).

Both have sql (a tagged template that escapes its values), query, jobs, enqueue, settleJobs and drop (which removes the database when the test is done).

settleJobs() waits until every due job has run, with the jobs those queued, and answers how each one ended. It doesn't wait for a failed job's later retry; settleJobs({ later: true }) runs retries and jobs queued for later at once, until their attempts are spent. enqueue queues a job as a cron would at its time.

In a browser#

launchBrowser() starts Chromium's headless shell ($CHROME, or Playwright's cached one). With none, it answers null so the test can skip, and the run says so once. In CI (CI set, as GitHub Actions does) or with ROCX_BROWSERS=required, a missing browser is an error, so a broken browser install fails CI instead of skipping its browser tests. ROCX_BROWSERS=optional lets them skip in CI too.

browser.open(url) opens a tab and waits until the page hydrates, strictly: if the server's page isn't what the browser's half renders, it throws. The tab has the same queries; each element found can be clicked, typed in and filled through the browser's own input. findBy… keeps looking until the page shows what it asks for.

launchBrowser({ engine: "gecko" }) starts a Gecko browser instead, headless ($GECKO, Zen or Firefox), driven over WebDriver BiDi. Its tabs do what Chromium's do, except take a screenshot in dark mode.

tab.drag(source, target) drags one element onto another as a mouse does, firing dragstart, drag, dragenter, dragover, drop (if the target accepts it) and dragend, each with its coordinates. Chromium uses its own drag and drop. Gecko never finishes a drag that WebDriver starts, so there drag fires the DOM's drag events itself, carrying one DataTransfer. tab.touchDrag(source, target) drags with a finger, with real touch input in both browsers.

Html.to_str can't render a component with signals: its holes need the runtime. Test it through its story: buildForTests(dir, { dev: true }) serves each story as a page, at storyPath("Counter", "At ten"), to fetch or open in a tab.

The JavaScript modules#

Plain .mjs files with no dependencies, each usable alone; index.mjs exports them all. The package's README lists every function and option.

ModuleGives a test
dom.mjs screen(html), or parse(html) and within(node): the queries, each as getBy… (one, or it throws), queryBy… (one, or null), getAllBy… and queryAllBy…. A node has text, attr(name), role, name and hasClass(name)
server.mjs startServer(executable, { statics, database, dev, flags, env }); its client(), with get, post, submit, json, put, read, events and flash; mail(), waitForMail, logs() and stop(); and links, until and storyPath
postgres.mjs testDatabase(): url, query, sql`…${value}` (each value written as a literal), jobs, enqueue, settleJobs and drop, over a small Postgres client of its own
sqlite.mjs testSqlite(): url, path, query, sql`…${value}` (each value a parameter), jobs, enqueue, settleJobs and drop, over node:sqlite
browser.mjs launchBrowser({ engine }), browser.open(url, { strict, cookies, script }): a tab with the queries, findBy…, waitFor, errors, console, screenshot, drag and touchDrag; elements with click, fill, type, press and value

Status and limits#

Everything above works and is tested: roc test packages/testing/main.roc runs Dom's expects, and node --test runs the JavaScript against a small app it builds, with Postgres and Chromium when they are there. The examples' tests use it too, such as tasks and board.

Not yet (each needs a change outside the package, written up in packages/testing/PROPOSALS.md):

  • A clock a test sets, and randomness it seeds: a test mode for the server.
  • Outbound requests (Http, and the S3 requests of packages/storage, which go through it) answered by stubs, so a test makes no network calls.
  • Jobs and crons run on request, by name. Today settleJobs works through the database, and enqueue repeats a cron's input.
  • Emptying the dev mailbox between tests. Today, pass { after } to waitForMail to skip the messages already there.
  • Endpoints and pages tested in Roc, answered inside the server; and a component with signals rendered in a Roc test.
  • Helpers in this package that run inside the server under test.

Limits:

  • The tabs of one browser share cookies, so open clears them first. To test two people at once, launch two browsers.
  • Dom.parse doesn't close elements that HTML lets you leave open: <p>one<p>two is read as one paragraph inside another.
  • The JavaScript uses the Roc Solid repository it is in (or the one ROCX_ROOT names): its compiler, its browser driver, and its platforms' hosts, which must be built first (just test builds them).
