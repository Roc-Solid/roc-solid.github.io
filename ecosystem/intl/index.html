The ecosystem · packages/intl

Every reader's language, written the same on the server and in the browser

Numbers, money, dates, relative times and translated messages with plurals, written as each reader's locale writes them. It is plain Roc on no platform: the server renders a page in the reader's language, and the browser hydrates the same text. In the demo below, pick a language or change n.

Installing it#

Name the package in your app's header (main.roc):

Both halves of the app, and tests, import its modules. One locale's formatting is an Intl value:

The one component, <Language>, holds the reader's locale as a context and is a picker. rocx build copies it into your app (using a package); import intl.Language imports the copy.

Language.store! makes a store: the reader's Intl in a signal, the supported locales, and a catalog of messages. <LanguageContext value={store}> provides it to everything inside as a context; <Language /> is the picker. Picking a language rewrites only the holes that call intl!(). Here remember! does nothing, so your choice isn't kept; in an app it sends the choice to an endpoint that sets a cookie (below).

The demo's catalog is empty: messages work in the browser too, but would add about 13 KB to the wasm every page of this site loads. Its message is under Messages, written as this page was built.

The reader's locale#

An app lists its supported locales, default first. A request gets the locale its locale cookie names (the reader's choice), else the one Accept-Language asks for, else the default. Locale.wanted(request, "locale") reads both, most wanted first; Intl.choose takes the closest supported locale. pl-PL gets pl; without plain en, en-US gets en-GB, not another language.

Keep the app's locales and words in one module. A GET endpoint answers the request's locale, and the root layout reads it. The server renders in that locale and sends the answer with the page, so the browser hydrates in the same one.

Formatting#

number_with(x, options) takes the fraction digits and grouping ({ ..NumberFormat.defaults, min_fraction: 2 }). ago picks the unit: seconds under a minute, then minutes, hours, days (under a week), weeks (under 30 days), months (under a year), years. Arabic follows CLDR 48: Latin digits, invisible marks that keep right-to-left text in order, and its dual without a digit ("خلال ساعتين", "in two hours").

Messages#

A catalog holds keyed messages for each locale, one locale the default: Catalog.new("en", [("en", [(key, message), …]), ("pl", […])]), as in I18n.rocx above. intl.t(key, args) looks a key up in the reader's locale, then its fallbacks (pl-PL, then pl), then the default. So a regional set (en-GB) holds only what differs, and a missing translation shows the default's words. A key no set has shows as itself, so you spot it.

The demo's message, files, in five languages, and what t("files", [("count", Int(n))]) says for a few counts. Each language has its own plural categories: German two, Polish four (and =0), Arabic six, Japanese one.

Catalog.problems(catalog) lists what a translator still has to fix: a key missing from a locale, a key the default lacks, a message that can't be read (shown as written), and arguments that differ from the default's. Add expect Catalog.problems(I18n.catalog) == [] to your app's tests. For this catalog:

  • pl has no "colour" yet (the default's is shown)
  • pl's "hello" reads {imie} where the default's reads {name}
  • pl's "extra" isn't a key of the default's: misspelt, or no longer used?
  • pl's "cart" can't be read, so it is shown as written: at 69, `count`'s plural is never closed

A form's errors#

packages/forms gives each issue a key and parameters: Issues.key(code) is "too_short", Issues.params(code) is [{ name: "min", value: "3" }]. intl.issue(key, params) says it in the reader's language from Validation.catalog, which words all nineteen of forms' keys in every starter locale, in forms' voice ("Use at least 3 characters"). Merge it under the app's catalog (Catalog.merge(Validation.catalog, words)), as I18n.rocx does. To reword a key, or word one of your own (a Custom issue's), put validation.<key> in the app's catalog (validation.not_postcode).

A number in the params picks the plural and is written the locale's way; a day (too_early, too_late) as the locale writes dates.

Locale data and size#

tools/locales.mjs writes packages/intl/Locales.roc from the CLDR in Node's ICU: the symbols, patterns and names for numbers, money, dates and times, and relative-time words for each plural category. Plural rules are code, in Plural.roc. To add a locale, add it to the script's list (with its plural rules if the language is new), run the script, and format the package with rocx fmt.

An app's wasm holds only the locales it names, under 1 KB (brotli) each. The code is the larger part and grows with what the app calls. Measured on 2026-11-21, before the browser's host moved to Rust: numbers alone added 12.6 KB to a small app, all the formatting 22.1 KB, and messages too 34.5 KB. The demo above added about 17 KB to this site's wasm (the store, the picker, numbers, money, dates and relative times in five locales; three would have saved 1.2 KB).

Status#

Works today, tested for the ten starter locales: everything above. The example app renders on the server, hydrates, switches language in place and keeps the choice in a cookie.

Not yet (each has a proposal in packages/intl/PROPOSALS.md):

  • The app writes the server's side: the endpoint that answers the locale and keeps a choice (as above), and any middleware that sends Content-Language.
  • Message keys are strings, so the compiler doesn't check them. A build step that writes a function for each key from message files would.
  • Time is UTC or a fixed offset. Named time zones, which follow summer time, need a host primitive.
  • More locales and fuller data (CLDR's parent locales such as en-001, other digits, long compact forms) wait on a generator that reads cldr-json.
