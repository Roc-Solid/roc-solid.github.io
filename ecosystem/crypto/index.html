The ecosystem · packages/crypto

Hashes, signatures and keys, in Roc

SHA-256, HMAC, HKDF, Base64 and hex: store a token as its digest, sign a link so nobody can forge it, derive separate keys from one secret. SHA-1 and Base32 are here too, for authenticator apps' codes. The package is plain Roc on no platform, so the server, a page in the browser and an expect run the same code.

Installing it#

Name the package in your app's header, beside the platform:

Then import the modules you use: import crypto.Hmac, import crypto.Base64, and so on. The platform's crypto page uses them with the server platform's encryption and random bytes, for tokens and sealed secrets.

A signed link#

A link that carries who it is for and when it expires, signed so that changing either breaks it. From the server platform's test app:

The signing key comes from the app's APP_SECRET through HKDF, with "links" as its purpose, so it signs links and nothing else. The link's text is signed with HMAC-SHA256, and the signature is written in Base64's URL alphabet, which needs no escaping in a URL. Hmac.verify_sha256 compares signatures in constant time, so the time it takes doesn't tell a forger how much of a signature was right.

The modules#

ModuleWhat it has
Sha256hash (the 32-byte digest), hex (the digest as 64 lowercase hex digits), chunks (the digest of several pieces, without joining them first)
Sha1hash (the 20-byte digest) and hex: for authenticator apps' codes alone (below)
Hmacsha256(key, message); verify_sha256(key, message, signature); sha1 and verify_sha1, the same over SHA-1; equal, a constant-time comparison of two byte lists
Hkdfsha256(key, salt, info, length), which fails with TooLong past 8160 bytes; its two steps, extract and expand
Base64encode and decode (standard alphabet, padded); url_encode (URL alphabet, unpadded) and url_decode; encode_unpadded, url_encode_padded; lines (76-character lines, as MIME wants)
Base32encode (padded), encode_unpadded, decode (either case, padded or not): how an authenticator app's secret is written
Hexencode (lowercase), decode (either case)

Decoding is strict, so each value has exactly one text: only the alphabet asked for, no spaces or line breaks, padding either left out or exactly right, and the last character's unused bits zero. Anything else is an error (InvalidBase64, InvalidBase32, InvalidHex). The package's README.md (packages/crypto/) lists every function's type.

SHA-1, HMAC-SHA1 and Base32 serve one job: an authenticator app's six-digit codes (TOTP, RFC 6238), which the auth package's two-factor sign-in checks. SHA-1 is broken for collisions, so don't sign with it or store a token's digest in it. HMAC-SHA1 doesn't rest on collisions, but use HMAC-SHA256 for anything new.

How it is tested#

Each module's expects check it against published test vectors: NIST's SHA-256 and SHA-1 examples, every test case of RFC 4231 (HMAC-SHA256) and RFC 2202 (HMAC-SHA1), RFC 5869's SHA-256 cases (HKDF), and RFC 4648's (Base64, Base32 and hex). Sha256 wraps Roc's builtin Crypto.SHA256; Sha1 is the package's own Roc. The server platform's tests also compare SHA-256, HMAC, HKDF, Base64 and hex with Node's crypto through a running server, and the auth package's tests compare authenticator codes with Node's.

What isn't here#

  • Encryption and random bytes, which need the operating system: they are the server platform's AesGcm and Random.
  • Password hashing (bcrypt, scrypt, Argon2): not yet. SHA-256 and HKDF are too fast to protect passwords.
  • Public-key cryptography: the server platform's P256 has what Web Push needs (ES256 signatures, ECDH with a key pair made for one call, and a new key pair). Verifying a signature, other curves and RSA: not yet.
