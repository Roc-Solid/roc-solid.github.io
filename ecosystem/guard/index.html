The ecosystem · packages/guard

Rate limits, feature flags and guards, as middleware

Guard protects an app's routes: 5 login tries a minute from each address, a new checkout for staff first and then a quarter of everyone, security headers on every answer, and maintenance mode for the whole site. Each guard is middleware that decides in plain Roc, so the tables on this page are the package's own answers, worked out when the site was built.

Installing it#

Name the package in your app's header (main.roc): guard: "../packages/guard/main.roc". Its middleware needs the server platform; the browser's half sees only the modules that need no platform (the logic, and the <Flagged> component).

  • In the server's modules (your middleware, your endpoints): import guard.Guard, and guard.FlagStore for flags.
  • In a .rocx file: import guard.Flagged, which rocx build copies into the app.
  • Optional: to keep feature flags' overrides across a restart, an app with a database lists the package's plugin, plugins: [FlagStore.plugin({})] (feature flags).

A first guard#

A guard goes in the middleware of the directory it guards: routes/+middleware.roc runs around every request, a directory's +middleware.roc around the routes in and below it. The sixth try in a minute gets 429 Too Many Requests, with Retry-After and the RateLimit-* headers. Every guard hands on its context unchanged, so guards go anywhere in a chain. The code is from packages/guard/example/, a whole app its tests ask over HTTP.

Rate limits#

A limit says how many requests a client may send, in how long. RateLimit.per_minute(5) is a token bucket: 5 at once, then one every 12 seconds. .sliding() counts a sliding window instead: never more than 5 in any minute. Both are plain functions: a client's state and the time go in; whether the request may go on, and the client's next state, come out.

The same eleven requests under each limit, as RateLimit.check answered them when this page was built (the clock is a list of seconds, as in the package's tests):

SecondToken bucketSliding window
0 200, 4 left 200, 4 left
1 200, 3 left 200, 3 left

4 200, 0 left 200, 0 left
5 429, Retry-After: 7 429, Retry-After: 67

24 200, 0 left 429, Retry-After: 48

72 200, 2 left 200, 0 left

In the bucket, a refused request costs nothing, so hammering doesn't delay the next allowed one. The sliding window refuses everything after the fifth until the five weigh less: its count is this minute's requests plus last minute's, weighted by how much of last minute the window still covers. So it keeps two numbers per client, however high the limit.

Who is counted

Guard.rate_limit(name, limit, key) counts each key separately. The name keeps one limit's counts apart from another's ("login", "api"). The key says who a request counts as:

KeyCounts
Guard.ip(trust)each address, found as trust says; an IPv6 address by its first 64 bits, the block one household is given. Clients whose address can't be told (an X-Forwarded-For that isn't an address, where it is trusted) all count as one, unknown, so a made-up header doesn't make a client unlimited
Guard.user(|context| context.user, trust)each signed-in user, as the context names them; each address when signed out
Guard.routeeach method and path
Guard.both(key, key)each pair: Guard.both(Guard.ip(trust), Guard.route) is each address on each route
|request, context| …whatever your function says. A request whose key is "" isn't limited

What a client is told

An allowed answer carries RateLimit-Limit, RateLimit-Remaining, RateLimit-Reset (seconds until the whole limit is back) and RateLimit-Policy (5;w=60: 5 in 60 seconds). A refusal is a 429 with those headers, Retry-After (seconds until one more is allowed) and a line of text. A form posted without the runtime goes back to its page with what was typed and a flash of the 429, shown where the form shows any refusal.

Memory stays bounded

Each limit keeps at most 10,000 clients (Guard.rate_limit_with takes another number). Clients whose limit is whole again are forgotten first, which changes nothing; past that, the client seen longest ago is forgotten and starts again. Each limit's clients are split into 64 tallies, so a request reads and writes about 150 of them at most.

The counts live in the server's memory (Kv), never in the database. A request reads its tally and swaps the next one in, reading again if another request changed it first, so no hit is lost. If a tally can't be changed after many tries, the request goes on and the log says why: a failing limiter shouldn't take the site down. A restart resets every limit.

Behind a proxy#

Most apps sit behind a proxy, which adds the address it saw to X-Forwarded-For. A client can write anything in that header too, so it is read only as far as the app says its own proxies wrote it. Take a request from 10.0.0.2, the app's proxy, whose X-Forwarded-For is 6.6.6.6, 198.51.100.4: the client wrote the first address, the proxy added the second. Who the client is, by each way to trust, as ClientIp.of worked it out when this page was built:

TrustThe client is
Direct 10.0.0.2
Header("x-real-ip") 198.51.100.4
Hops(1) 198.51.100.4
Hops(2) 6.6.6.6
Proxies(Ip.private) 198.51.100.4
  • Direct takes the connection's address and ignores the headers: for when nothing is in front of the server.
  • Hops(1) says one proxy is in front, and finds the address it saw. Hops(2) claims two, so here it trusts what the client wrote.
  • Proxies walks the list from the right, past the app's own proxies (Ip.private: the loopback and private ranges, or Ip.cidrs(["10.0.0.0/8"])). It checks the connection came from one of them, so a client reaching the server directly can't name anyone it likes.
  • Header(name) reads one header a proxy sets, such as fly-client-ip or cf-connecting-ip.

Proxies(Ip.private) is right both with no proxy in front and behind one in the server's own network, so the app rocx new makes uses it. Hops(1) with no proxy in front believes the client, who could name a new address each time and never be limited.

Feature flags#

A flag is defined in code: its name, what it's for, and who has it on. A rule is on or off for everyone (off is a kill switch), plus the users and groups it lists, plus a share of everyone else signed in. A hash of the flag's name and the user's puts each user in or out of a rollout the same way every time, so raising the share only adds people. An environment can have its own rule.

Who has it on, as Flags.is_on answered when this page was built. A user's bucket, 0 to 99, is that hash (Flags.bucket): a rollout of 25 takes those below 25.

WhoBucketIn productionIn development
ada, listed 88 on on
bea, in staff 84 on on
cy 35 off on
dee 27 off on
jo 8 on on
kai 87 off on
max 0 on on
signed out none off on

ada is listed and bea is in staff, so they have it whatever their bucket. A signed-out visitor has no id to hash, so a rollout reaches them only at 100. The environment is APP_ENV if set, else dev under --dev, else production.

Changed while the server runs

The code's rule is the default; an admin page can override it until it is reset. Overrides live in the server's memory (Kv), so a restart brings back the code's rules. To keep them across restarts and deploys, an app with a database lists FlagStore.plugin({}): each override is also a row of its table (guard_flags, for Postgres, SQLite and Turso), read back as the server starts. Only admins may set a rule: in the example, Middlewares.admins answers anyone else 403.

On the server, FlagStore.is_on!(flag, { user, groups }) answers in an endpoint, and Guard.feature(flag, who) answers 404 to anyone without the flag, as if the route weren't there.

In a page

The server decides the visitor's flags once, in a GET endpoint the layout reads; a <Flagged> shows its children only when its flag is on. The flags travel in the rendered page, so the browser hydrates with the same values without asking again.

Security.defaults adds these headers to every answer, as Security.headers wrote them when this page was built:

The Content-Security-Policy fits a Roc Solid app: scripts and WebAssembly from the site's own origin (a page needs 'wasm-unsafe-eval' to start its wasm under a CSP), inline styles (components write style="…"), and calls to the site's own server. Security.directive changes one directive (to allow images from another host, say). Under --dev there is no Strict-Transport-Security, and the CSP only reports: a violation shows in the console instead of breaking the page. The dev server's reload script is the site's own file (/__reload.js), so it is no violation.

The server half: Guard holds the guards, FlagStore the flags while the server runs, and Kept the rate limits' tallies. Only the server compiles these three.

The package's README has the whole API in one place.

Tested, and limits#

Every module is tested by its expects, and the middleware in packages/guard/example/, asked over HTTP. Its login limit answers 429 on the sixth try with the headers above, also to clients whose X-Forwarded-For isn't an address (they share one count). Its admin endpoint answers 403 to anyone but an admin. Flag overrides turn its feature route and maintenance mode on and off while it runs, and outlive a restart in its SQLite file.

The server reads a request's body, up to 16 MiB (or its --max-body), before any middleware runs, so Guard.body_limit refuses a large body after it has arrived, not before.
