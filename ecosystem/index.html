The ecosystem

Packages: Roc modules and components for any Roc Solid app

A package is a directory of Roc modules, often with components, added to an app with one line in its header. Use one for what the platforms leave out: charts, form checks, translations, a job queue, email, an admin for your tables. Some packages are also plugins, which add tables, background work or scripts to the server. Twenty-four so far, each with a page here.

What is in a package#

Each package has its own directory under the repository's packages/ (beside dbcheck, which rocx check --sql uses and no app imports). It holds Roc modules, components, or both.

Roc modules

main.roc is an ordinary Roc package header listing the modules. A package that only computes (charts, forms, intl, Markdown, QR codes) names no platform. It can't render or fetch, so the server, the browser and an expect all call the same functions. A package that needs the server (to send email, run jobs, read the database) names the server platform; more than half do.

Components

components/*.rocx are components, such as <BarChart>. They import the platform's Html and Solid, and an app is two programs on two platforms (server and browser). So rocx build copies them into the app, and each half compiles them on its own platform.

A server-platform package can still offer modules to the browser (audio's Audio.play! runs in a click handler). It lists them in a second header, browser.roc, which names the browser platform only if they need it. The browser's half of the app sees that header instead of main.roc. If a page imports any other module, rocx build stops and names the import.

Adding one to an app#

Name the package in the app's header (main.roc), beside the platform. You import it by the name before the colon; use the package's directory name, as every app here does.

That line covers both halves: rocx build writes the browser copy's header from it, on the browser platform, through each package's browser.roc if it has one. A server-platform package with no browser.roc (Stripe, storage, PostHog) is left out of that copy.

Then import modules and components as in any Roc program: import charts.Format, import charts.BarChart. A component is copied to the app's Generated/charts/BarChart.roc and the import points there. Its <style> joins the app's stylesheet, and compiler errors point at the package's file. The charts page's bar chart, from site/Demos/BarDemo.rocx:

Plugins#

Some features need more than functions: a job queue needs a table and background workers, a dev mailbox its own pages, a sound player a script on every page. A package provides these as a plugin: one value, made from options, listed in your program's plugins.

A plugin can add database tables (applied before the app's migrations), background loops, work at start, development pages (only under --dev or --debug), and files it serves, such as a page script or a service worker. It adds no routes: every URL your app answers is a file under routes/ (D-116). A package that answers requests gives you handlers to call from your own route files, behind their folder's middleware.

A plugin can declare what it needs: an environment variable, a database, another plugin. At start the server checks every plugin and stops on any problem (a missing variable, a required plugin not listed, two files at one place), listing them all. The server platform's page covers what a plugin can add and how to write one.

The packages that are plugins, and what each adds:

  • Auth: Auth.plugin({ providers }) adds the session tables. Its handlers answer your sign-in routes (a mailed link, a provider and back, the second factor, signing out, the dev sign-in) with your admit!, and its middleware passes on the signed-in user.
  • Stripe: Stripe.plugin({}) adds tables of customers, checkouts and subscriptions, kept in step by Stripe.webhook_route! on your webhook route, with your on_event!. Its functions send people to Checkout and the Customer Portal, and say who has paid.
  • AI: Ai.plugin({}) reads the API key and model at start (outside --dev, no key, no start) and logs the model. Its functions ask Claude for an answer (whole, streamed to a page, or read into a Roc type), with the app's functions as tools. Its agents are models with a role and their own tools, and can be each other's tools.
  • Jobs and cron: Job.plugin({ jobs: App.jobs, crons }) adds the queue's table, its workers, the schedules' loop, and a sweep of old finished jobs.
  • Email: Email.plugin({}) adds the dev mailbox under --dev, and logs at start whether the SMTP server answers. Outside --dev, no SMTP_URL, no start.
  • Push: Push.plugin({}) adds the subscriptions' table, the sending job (it needs the jobs plugin), the service worker and the page's script; under --dev with no VAPID keys, a key pair for the run. Three handlers answer your routes for the key and a page's subscriptions.
  • Guard: FlagStore.plugin({}) keeps feature-flag overrides in a table, so they survive a restart. Rate limits and guards need no plugin.
  • Audio: AudioPlayer.plugin({}) adds the player for Audio.play!, a script every page loads.
  • Vibrate: Vibrator.plugin({}) adds the script that passes Vibrate.pattern! to the browser's vibration motor. A phone app needs none.
  • PostHog: PostHog.plugin({}) sends errors to PostHog's error tracking; its handlers answer your routes for the page's script and its report endpoint.
  • OpenTelemetry: Otel.plugin({}) reads the OTEL_* settings at start and adds the loop that sums the app's measurements and sends them to the collector. Its middleware times every request.
