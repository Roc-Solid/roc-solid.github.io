The ecosystem · packages/forms

Forms: the rules written once, checked in the browser and at the endpoint

Write a form's rules once, in Roc, as zod does for TypeScript. The browser checks each field as it is typed; the endpoint runs the same code, reading the post into a typed record or refusing it with the same issues. The rules go past what a type can say: lengths, patterns, email addresses, ranges, choices, days, and checks across fields.

Installing it#

Name the package in your app's header, main.roc; rocx build gives the browser's half the same packages, so you name it only here. Forms isn't a plugin, so App.program needs nothing.

Then import forms.Form where you write a schema, and import forms.LiveForm and the field components in a .rocx file.

Try it#

Type in a field, then leave it: a failed check shows its issue under the field until the field passes. Send shows every issue at once, with a summary above the form linking to each field. With none left, the demo shows the record the form reads.

18 or over.

This site is static, so the demo sends nothing: it checks in your browser with the code an endpoint would use. In an app, Send posts the form, and the endpoint has the last word.

One schema#

Build a form with Roc's record builder: each field under the name it is posted as, with its checks in order. The record's type is what the form reads: here age is an I64 and terms a Bool. The two passwords are a small form inside it, so the check comparing them runs whenever both can be read, whatever is wrong elsewhere.

In an app, the schema is a module that page and endpoint both import. Its checks are data, so it also gives each input its attributes and describes the form as JSON Schema. form.json_schema(), as this site is built:

At the endpoint#

An endpoint reads its body with the same schema: its route file names the form beside the handler, whose body is the form's record (D-093):

The platform reads the fields (URL-encoded, multipart, or a JSON object) with the form and gives post! the account. What doesn't pass never reaches it: the endpoint answers 422 with the issues as JSON (application/json). An unticked box, which a browser doesn't send at all, is the form's to judge. Generated/Api makes the endpoint so in both copies (Endpoint.checked(Endpoint.remote("POST", "/signup"), Signup.form)), so a page's submission is read with the form too, and /openapi.json documents the body with the form's schema. In the page#

LiveForm holds a form's state in a component: what each field holds, which fields you have left, and whether the form was sent. Make it once, like a signal. The field components take their attributes from the schema (type="email", required, maxlength, min) and say when they are invalid (aria-invalid, aria-describedby). The demo uses a local form, read only by the browser:

An app's page posts to its endpoint instead: make the live form with LiveForm.of!(Signup.form, Api.post_signup({})) and write <form method="post" action={live.url()} novalidate>, with no on:submit. With the runtime, the form is sent in the background; the page stays and shows the endpoint's issues at their fields. Without it, the browser posts the form, and the page comes back with what was typed (passwords aside) and the issues (a submission read from the flash).

An edit form starts filled in: LiveForm.filled!(TaskForm.editing, save, [("title", task.title), ("notes", task.notes)]). From a handler, live.reset!() puts back what the form started with and forgets every issue, keeping the inputs and focus (Start again, in the demo). An add form resets once the endpoint accepts it: create_effect!(|| live.accepted!(), |accepted| if (accepted) live.reset!() else {}). examples/tasks does both.

Values and their checks#

Each kind of value takes checks, run in order, and reports everything wrong, not just the first. A text check other than Required passes an empty value, as a browser's minlength and pattern do: Value.text([Email]) takes "" or an address.

ValueReadsChecks
Value.text(checks) Str, as typed Trim, Lowercase, CollapseSpaces (each changes the text for the checks after it); Required; MinLength(n), MaxLength(n) (characters); Matches(pattern) (the whole text); Email (as <input type="email"> checks one); Url (http or https); OneOf(options); Secret (a password, never written back into a page)
Value.int(checks)I64: 42, -3, +7Min(n), Max(n), Step(n) (counted from the Min, or from 0, as a browser's step is)
Value.dec(checks)Dec: 2.5, .5; no exponentMin(x), Max(x), Step(x)
Value.checkbox(checks)Bool: sent or not[Required]: it must be ticked
Value.choice(options)what the option stands for: [("free", Free), ("pro", Pro)]one of them
Value.date(checks)a Date: 2026-11-21Min("2026-01-01"), Max(…)

An empty number, choice or day fails as Required. For anything else, .check(ok, code) adds your own check, and .map and .try_map turn the value into another type (a Username, an Isbn) or an issue.

A bad pattern crashes where the value is made. Roc computes top-level values at compile time, so a typo in a top-level form's pattern stops the build instead of reaching a user.

Issues#

An issue is { field : Str, code : Issues.Code, message : Str }: where, what, and the English. A code is a plain tag carrying what its message needs, so a translation can match on it or look it up by its key and params (as intl does). Issues.at(issues, field) picks out a field's issues, and Issues.under a list's, its items' too. Issues.refusal is an endpoint's 422, and Issues.from_problem reads one back from a submission's error!() or Endpoint.send!.

Patterns#

Roc has no regular expressions, so the package has an engine in plain Roc. A pattern compiles once, to a program; a Pike VM runs it over the text, following every possible match at once, one step per character, so no pattern or text can make it slow. The price: no backreferences, no lookaround. The syntax is JavaScript's, so a pattern means the same in an input's pattern attribute: characters and ., classes ([a-z], [^,], \d \w \s), ^ $ \b, groups, |, and * + ? {m,n}. Matched as this site is built:

PatternTextmatchesfind
\d{2}-\d{3}12-345yes"12-345" at 0
\d{2}-\d{3}12-3456no"12-345" at 0
[a-z]+(-[a-z]+)*roc-solidyes"roc-solid" at 0
colou?rcolouryes"colour" at 0
\bcat\ba cat satno"cat" at 2
\d+ab 123 45no"123" at 3
(a+)+$aaaaaaaaaaaaaaaaaaaaaaaaaaaaaa!nonowhere

The last row is the classic trap: a backtracking engine (JavaScript's, say) tries hundreds of millions of ways to split those a's into groups before saying no. Here it is one step per character. Regex.compile says what is wrong with a pattern, and where; Regex.must crashes instead, which in a top-level value stops the build.

Not yet#

Everything above works today; roc test packages/forms/main.roc runs the package's expects. Waiting on proposals in packages/forms/PROPOSALS.md:

  • The platform's own refusal with field issues (RFC 9457 problem details). Today it is a 422 with the issues' JSON (application/json), which Issues.from_problem reads back.
  • Holding back a send in the browser when the form has issues. Today it always reaches the endpoint, which refuses it with the same issues.

And for now: decimals use a .; patterns have no flags or captures; form.parse_body(text) (for a page holding a form's text) reads URL-encoded only (the platform reads an endpoint's body for the form, JSON too).
