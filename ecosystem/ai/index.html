The ecosystem · packages/ai

Claude, from your app's server

Stream answers to a page, read them into Roc types, give the model your app's functions as tools, and build agents that hand work to each other. Plain Roc on the server platform's HTTP client: no SDK, no platform change.

The package does the parts that are easy to get wrong: it rebuilds streamed messages exactly, retries when the API asks, makes a refusal an error, stops the model when the page goes, turns Roc types into JSON Schemas, and logs tokens. Your app keeps its prompts, its tools, and what it does with the answers.

Installing it#

Name the package in the app's header with the two packages it uses (crypto and tools), and list its plugin. It names the server platform, so only the server's half of the app sees it. The example app's main.roc:

Then set ANTHROPIC_API_KEY (from console.anthropic.com) in the environment or in a .env where you run rocx dev (which passes it to the server). Without a key the server doesn't start, except under --dev, where each call answers NoKey.

Asking#

Every call takes an Ai.Request. All fields have defaults; give a prompt or messages.

FieldDefaultWhat it is
prompt""the user's message, after messages
messages[]the conversation so far: an earlier reply's messages, or Message.loaded
system""its role, the rules, the app's facts
modelthe plugin'sthis call's model
max_tokens64_000how much the model may write, thinking included
effortMediumLow, Medium, High, XHigh or Max: how hard it thinks. More costs more and takes longer
cacheBool.Trueuse the API's prompt cache: a later call that starts the same reads it at a tenth of the price
max_turns10how many turns run! takes at most
label""names the call on the log (ai.turn's label: "summary", an agent's name)
updatesBool.Falsewhether run! reports what the model is doing (updates)

Low effort suits a chat or a label; High and above, careful work. Ai.ask! waits for the whole answer. The example sums up the notes with it:

The reply is { text, messages, stop, usage, model }:

  • text: the answer;
  • messages: the conversation with the answer, to go on with or keep;
  • stop: why the model stopped: EndTurn, MaxTokens (text cut off), ToolUse, and a few more;
  • usage: tokens spent, { input, output, cache_read, cache_write } (summed over all turns, for run!);
  • model: the model that wrote it.

Streaming to a page#

Ai.stream!(request, heard!) passes each piece of text to heard! as it is written, then answers the whole reply. In an endpoint's events!, send each piece as an event for the page's Endpoint.listen!:

When the page goes, the model stops

send! answers Err(Gone) and heard! passes it on. The package closes the API request, so the model stops writing and costing. stream! answers Err(Stopped(Gone)); events! returns Err(Gone).

events! takes no body, so a page posts its question first, then listens on a path that names it. The example's chat posts to /api/chat/[chat], then listens there:

heard! gets Event(said) for each event, then Ended or Failed(problem). On the server, post! adds the message to the chat's conversation (in Kv, by chat id). events! streams the assistant's answer (an agent, via Agent.chat!): its text, a status line while the team works (updates), then the current notes. If the team runs out of turns, its work is kept.

Typed answers#

Ai.extract!(request, Ai.schema(tags)) holds the model to the JSON Schema of the answer's type (the API's structured outputs), then reads the answer into it with Json, as an endpoint reads a body. The annotation gives the type:

The example's meal endpoint reads what the user typed into that type:

  • The schema is the platform's, the one the OpenAPI document uses. tags lists the tags of the type's unions (["Breakfast", "Lunch"]; [] for none), because a union's parser doesn't say them.
  • It is cut to the API's subset: every object closed (additionalProperties: false), oneOf written as anyOf, and what the API doesn't enforce (an integer's range, a string's length) left out. Json checks those while reading, so an answer outside a U32 is InvalidJson, not a wrong number.
  • A type that isn't a record is asked for as an object's result field.
  • Ai.schema is a value, made where the type is known, like McpHttp.openapi({}).

An answer that reaches max_tokens before its JSON ends is Truncated.

Tools#

Ai.run!(request, tools, context, heard!) gives the model tools. The tools a turn asks for run in order, each given context, and their answers go back, until the model stops asking or max_turns is reached (TooManyTurns(reply), with its messages and usage to keep and bill). A turn cut off at max_tokens ends the run; its half-written tool call is neither run nor kept, so the conversation can be sent again. A refused turn runs no tools. heard! gets Text(piece) as the model writes, Calling(name) before a tool runs, and, with updates, Update(…) (below).

A tool is packages/tools' Tool, which the MCP package serves too, so one tool serves both. Ai.tool makes one from a name and description for the model, a function of the app's (given the typed arguments and the context), and the arguments' schema. The example's notes, and its notes keeper's three tools:

Tools from McpHttp.endpoint, McpHttp.tool and Tool.typed work too, with their own context (an MCP tool's is McpHttp.Caller(c): the request, the context, progress!). A tool's input streams in, then is checked against its type before the tool runs. The model gets back:

  • the tool's answer, as JSON text;
  • its Err(why), as a tool error the model can read and act on;
  • arguments that don't fit the tool's type, input that isn't JSON, or an unknown tool, as tool errors too;
  • a failure inside (Failed), as "<name> failed.", its reason logged (ai.tool), not sent.

Agents#

An Agent(ctx) is a model with a role and tools: a plain value, made once and asked as often as needed:

FieldWhat it is
name, descriptionwhat a model using the agent as a tool reads
systemits role
toolsthe tools it may use ([])
modelits model (the plugin's)
efforthow hard it thinks (Medium)
max_turns, max_tokensas a request's (10, and 64,000)
updateswhether it reports what it is doing (Bool.False; updates)
doingwhat a page shows while another agent has it at work ("")

Agent.ask!(agent, prompt, context, heard!) asks one message; Agent.chat!(agent, messages, context, heard!) answers a conversation whose last message is the user's. Both are Ai.run! with the agent's settings, logged under its name (label).

Agents as tools. agent.as_tool() is the agent as a Tool taking one argument, task: the work, in words. A team is plain values: specialists with their own prompts and tools, and a calling agent that stays in charge and knows which to ask. The example's chat (streaming to a page) talks to such a team:

  • A task is a conversation of its own. The agent sees nothing of its caller's, so the task must hold everything. Say so in the caller's system prompt, as the assistant's does.
  • An agent's text isn't streamed to its caller. With updates, its progress notes and tools are (below).
  • Its answer is the tool's result. A failure is a tool error ("<name> couldn't do it: …"), and so is a call with no task, without asking the API.
  • One context. Every agent in a team gives its tools the context it was given.
  • An MCP tool too. Being a Tool, an agent can be an MCP server's tool.

Updates#

With updates: Bool.True, a request or agent sends its listener Update(update) (the tools package's Tool.Update) for a page to show while the model works:

  • Progress({ agent, says }): a note the model wrote between tool calls (“I'll look through your notes first.”). Asked for on Claude Opus 5.5, Sonnet 5.5, Fable and Mythos, whose reasoning stays hidden. Claude Haiku 5.5 writes them as plain Text.
  • Using({ agent, tool, says }): one of the app's tools starting, with what it says it is doing: Ai.tool(…).doing("Looking through your notes…"), or an agent's doing field.
  • Agents used as tools pass theirs up, each under its name (agent).

Your app decides where they go. The example's chat sends each as an event on its page's stream (above), shown as a status line: “Counting the calories…”, “Seeing to your notes…”, “notes_keeper: Writing that down…”. A page that started the work with a form can listen on a channel instead:

Progress notes stay in the conversation and go back to the API. They are billed as output, shown or not.

Conversations#

A conversation is a List(Message); Message.user(text) makes the user's. The model's are kept exactly as the API wrote them, thinking blocks and signatures included, because the API needs them back. To go on, pass reply.messages as the next request's messages with a new prompt.

Message.save(messages) writes a conversation as JSON text, for Kv or a table; Message.load(text) reads it back exactly. Message.text(message) is its text alone, without thinking or tool use. The example keeps each chat in Kv for a day:

After a mid-turn server-side fallback (another model took over where the first declined), the message drops the first model's thinking and tool uses before the fallback block, as the API asks, and keeps the block.

What it costs#

Each turn is logged with its tokens (ai.turn):

  • label: the request's, or the agent's name, so each agent's spending can be told apart (absent when empty);
  • input: read without the cache;
  • cache_read: read from the cache, at a tenth of the price;
  • cache_write: written to the cache, once, at a quarter more;
  • output: what the model wrote; ms: how long the turn took.

With cache on (the default), each turn reads the previous one from the cache. A prompt under the model's minimum (512 to 4,096 tokens, by model) isn't cached, and asking costs nothing extra. The other levers are the model and effort: --dev uses claude-haiku-5-5, and the example Low effort.

What went wrong#

A failed call answers an Ai.Problem(err); Ai.explain(problem) puts it in a sentence:

TagWhen
NoKeyno ANTHROPIC_API_KEY (under --dev)
Status(code, why)the API refused: 400 the request, 401 the key, 429 too many (still, after two tries), 529 overloaded
Unreachable(why), TimedOut, Broken(why)no whole answer came
Refused(category)the model declined (the API's category, as "cyber"; often "")
Truncatedextract!'s answer reached max_tokens before its JSON ended
InvalidJson(why)extract!'s answer didn't fit its type
TooManyTurns(reply)run! took max_turns turns and the model still wanted its tools; reply is what it did (its messages and usage)
Stopped(err)heard! answered Err(err): from an endpoint's events!, the page went (Stopped(Gone))

A 408, 409, 429, 500, 502, 503, 504 or 529, or a stream error event meaning one (overloaded, a rate limit, a timeout, the API's own error), is retried twice after retry-after (a minute at most; else half a second, then a second), each retry logged (ai.retry). Nothing is retried once text has been passed on, or when the connection fails (Unreachable).

What it sends#

POST <base_url>/v1/messages, with anthropic-version: 2026-10-21, x-api-key and "stream": true: every call streams, so a long answer never times out (30 minutes at most). output_config carries the effort and extract!'s format; cache_control asks for the prompt cache. No sampling parameters (that version refuses temperature and the rest), no thinking (models think as they need; effort says how much), no forced tool_choice (Claude Opus 5.5 refuses it). With updates, on models that write progress notes, thinking is {"type": "adaptive", "display": "updates"} and anthropic-beta lists thinking-display-updates-2026-08-18.

effort is always sent. Claude Opus 4.5 and every model from 4.6 on accept it; Claude Haiku 4.5 and Sonnet 4.5 refuse it (a 400), so ANTHROPIC_MODEL can't name them.

On models that support it (claude-opus-5-5, claude-opus-5, claude-sonnet-5-5, claude-fable-5-2, claude-fable-5-1, and Mythos 5.2 and 5.1), it sends "fallbacks": "default" with anthropic-beta: server-side-fallback-2026-07-01. When the model's safety classifiers decline a request, the API reruns it, in the same call, on the model it names for that refusal. claude-haiku-5-5 has no fallback: a refusal there is Refused.

The example app#

packages/ai/example is a notes assistant, its notes and chats kept in Kv. Its page has:

  • a streamed chat with an assistant that hands notes to a notes keeper and meals to a nutritionist, agents it uses as tools;
  • a button that sums up the notes (ask!);
  • a meal described in words, read into a typed record (extract!).
