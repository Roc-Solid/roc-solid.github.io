The ecosystem · packages/admin

An admin for your tables, read from the database itself

A Django-style admin: see and fix your data without building pages for it. Each table gets a page of rows with a search, a filter in every column, sorting and pages, and a form to add, change or delete a row. The admin reads your tables from the database's catalog (Postgres or SQLite) on each request: no code to generate, nothing to keep in step with your schema.

Mount it with one route file, behind your app's middleware. The package also draws the jobs page, a plugin showing the queue of packages/jobs.

Installing it#

Name the package in your app's header (main.roc) by its directory's name, as the docs site does:

The package names the server platform (for the jobs page), so its pf must be your app's platform file. The admin runs only on the server: nothing in the browser imports a +server.roc, so the browser's half never compiles it.

A first admin#

Add a route file at the admin's path: routes/admin/db/+server.roc is /admin/db. Its respond! hands every request to AdminPage.respond! with:

  • the context from the route's middleware (its directory's +middleware.roc, middleware = Middlewares.staff, says who is asking);
  • the options: only mount (the route's path) and access are required, and per table only its name;
  • the effects the admin runs on: Db.all!, Db.run!, Random.bytes! and Db.backend!.

In your app these go in the route file. Here they are a module the compiler checks, but nothing answers with them: the docs site has no database.

Why you hand it Db.all!

AdminPage uses no platform, so either half of an app can import the admin's modules (this page renders the admin's pages that way, below). A module on no platform can't call Db, so your route passes it the server's effects, and the compiler checks they fit. Db.backend! tells the admin whether to write its statements for Postgres or SQLite.

What it looks like#

The package's View rendered these with this page, from a made-up catalog (books and authors) and the options above. No database is asked, and the frames are sandboxed: links and forms do nothing. Like the jobs page, they use the admin look: tables in a sidebar (across the top when narrow), a header with the page's actions, panels, and light or dark to match your system.

The made-up tables, and the pages rendered from them: site/Demos/AdminPreview.rocx

Its pages#

Every page is the admin's path plus a query, so one route file is enough. A query can name only the tables and columns the app lets the admin show.

QueryPage
(none)the tables, each with its estimated row count (Postgres only), its comment, and a link to add a row
?table=books its rows, 50 a page (page=2), counted and paged by the database; a search (q=cloud), a filter in each column (has.title=cloud, from.price=10, f.state=draft, is.author_id=null: see Filters), and a sort (sort=title, or sort=-price for descending)
?table=books&k.id=21a row's form: k. plus each primary-key column, so two-column keys work too
?table=books&newa new row's form, with its constant defaults filled in (true, 'draft', 0)
?table=books&k.id=21&deletea confirmation, and the button that deletes the row

Sending a form adds, changes or deletes the row, then shows the row's page saying Saved. An update writes only changed columns. If the database refuses (a price that isn't a number, an author books still name), the form comes back with what you sent and the database's reason. A table without a primary key is listed, but its rows can't be opened.

Filters#

Each column a list shows gets a filter under its heading, chosen by its type; a hidden column never does. Filters can't be turned off: filtering a shown column reveals nothing a visitor can't already see. To filter by a column, list it.

ColumnFilterQuery
text, varchar, uuid, json and any other typethe text it contains, in any case; % and _ match themselveshas.title=cloud
a number: integer, bigint, numeric, real, …from, to, or both, inclusivefrom.price=10&to.price=20
date, timestamp, timestamptz (in UTC), timefrom, to, or both, inclusive, with the browser's pickersfrom.published_at=2026-03-01T00:00
booleana select: any, yes, nof.in_print=true
an enum, or a check that it is one of a few valuesa select of its valuesf.state=draft
a foreign keythe value it equalsf.author_id=3
any of these, if it may be nullalso empty and not empty: in its select, or in a small select under its inputsis.blurb=null, is.blurb=set

The filters are one GET form, no JavaScript: Enter in any of them, or the Filter button beside the search, sends it. Filtering keeps the search and sort and returns to the first page; page links and sorting keep the filters; Clear filters drops them all.

Each value is checked in Roc before it reaches SQL (a number for a number, 2026-03-14 for a date, one of an enum's labels), and a range's value is cast to its column's type ("price" >= $3::numeric). A wrong value is ignored and its filter says so (Ignored: not a number), so a bad query never makes the page an error.

Who may use it#

The route's middleware runs first, so it can send a stranger to sign in. Then access decides from the context it handed on:

access saysThen
Editevery page, and adding, changing and deleting rows
ReadOnlythe tables, rows and values; no forms
Refuseda 403, and nothing is read

A form's POST must come from the same site (its Origin header) and send back its page's token. The token lives in a cookie, rocx_admin_csrf: sent only to the admin's path, unreadable by scripts (HttpOnly), and not sent with another site's form (SameSite=Lax). Any other POST gets a 403 before a table is read.

Options#

Admin.Config(context) configures the admin. Only mount and access are required.

FieldWhat it is
mount : Strthe route's path
access : context -> [Edit, ReadOnly, Refused]what someone may do, decided from the middleware's context
tables : List(Admin.Table)the tables it shows, in order, with their options (none by default)
include : [Listed, All]Listed (the default) shows only those tables; All adds every other table of the schema, with default options, except the platform's own (rocx_…)
schema : Strthe Postgres schema: "public" by default (SQLite's is always main)
title : Strwhat its pages call it: "Database" by default
back : { label : Str, href : Str }a link to the app's pages, first in every sidebar ({ label: "Status admin", href: "/admin" }); none by default

Admin.Table holds a table's options, naming columns as the table does. A table or column the schema doesn't have stops the admin: its pages say what is wrong and show nothing else until it is fixed, since a misspelt hidden would show the column it should hide.

Widgets#

A widget is a column's input on a row's form, chosen from the column's type in the catalog (for a domain, its base type):

ColumnWidget
a foreign key to a table the admin showsa select of that table's rows, by their title (an input, when there are more than 200), and a link to the row
an enum, or a check that it is one of a few values (check (state in ('draft', 'published')))a select of them
booleana checkbox; a select of yes, no and null when it may be null
smallint, integer, biginta number
numeric, real, double precisiona decimal's input
date, timestamp, timestamptz, timethe browser's pickers; a timestamptz in UTC
json, jsonba text area, in a monospace font
text, varchar(n), uuid and the restan input (with maxlength for a varchar(n)), or a text area for a value of several lines; the database reads what is typed as the column's type
a generated column, byteashown, never written

An empty input is null where the column allows it, else an empty text for a text column. In a new row, an empty input leaves a column's default to the database. To change a column's widget, name it in the table's widgets; the README lists every Widget.Kind.

How it works#

On each request, the admin reads the schema from the catalog into tables (Catalog.read): columns and types, which may be null or have defaults, primary and foreign keys, enums, and the values a check allows. On Postgres that is four small statements over pg_catalog. On SQLite it reads pragma_table_list, pragma_table_xinfo and pragma_foreign_key_list, and each table's checks from its create table. A SQLite type is read as Postgres would name it (integer as int8, boolean as bool), so it gets the same widget and filter.

A table or column a request names is looked up there, among those the app lets the admin show. Only the catalog's names go into SQL, double-quoted; every value is a parameter:

A list is two statements built by Sql: a count, then the page's rows. These are the statements for ?table=books&q=cloud&f.state=published&from.price=10&sort=-price&page=2 above, built as this page rendered:

Every statement answers rows of one shape, each cell as text plus whether it was null (Catalog.Row), so one Db.all! reads any table. The database cuts a list's cells to 81 characters, so the page can tell one was cut; a key is never cut.

Pages go out with Content-Security-Policy: default-src 'none' (no script, nothing loaded from elsewhere, forms sent only to this site), X-Frame-Options: DENY and Cache-Control: no-store, and every value is escaped.

The jobs page#

The queue of packages/jobs also goes on a route of yours. Put its route file in your admin pages' folder, so that folder's middleware decides who sees it, and give mount the route's path:

A request passes the app's middleware, then the folder's, then the page, which needs the jobs plugin listed. back works as the tables admin's option does (none by default). The jobs page's own section says what it shows and does.

The tables admin, the jobs page and the dev mailbox of packages/email share one look (Look, and AdminHtml on it). Each sidebar ends with Back to the app: to the app page the reader came from (kept in a cookie until the browser closes, so the page's filters and forms keep it), or to the front page, /, when they came from nowhere (a typed address, a bookmark) or another site. The stories catalog has it too.

The modules#

AdminPage is the one module with effects: those your route hands it. JobsPage and AdminHtml run on the server platform. The rest is plain Roc on no platform; roc test packages/admin/main.roc runs their expects.

ModuleWhat it does
Adminthe options (Config, Table, Access), what they name that the schema doesn't have (problems), and what they mean for a table: showing, listed, searchable, writable, title, ordering, widget
AdminPagerespond!(request, context, config, effects): the access check, the token, the catalog, then the page or the form
Catalogthe statements that read the schema, on Postgres or SQLite, and read (read_sqlite), their rows as tables
Sqlident, contains (a search's or a filter's pattern), the conditions a list's rows meet, and the statements: rows, count, one, insert, update, delete, titles
Widgeta column's widget from its type (of), its input (input), what a form's text writes (param), whether it changed (same), a new row's value (initial)
Listinga list's search, filters, sort and page, read from the query and written back (read, params, conditions, order, key); each column's filter (kind) and the check of its values (check)
Pagingof(total, size, asked), offset, shows, links: the first two pages, three each side of this one, the last two
Vieweach page's HTML: index_page, list_page, row_page, delete_page, problem_page, problems_page, and the sidebar (side)
Lookthe admin look: the rules every admin page shares (shared) and its helpers (side, header, panel, empty, icon, button_with), light and dark; the tables admin's own rules, its document, and the headers it is sent with
Forma query's or a form's fields, decoded, and links, encoded
JobsPagethe jobs page: respond!(request, { mount, back }), from a route of the app's (server only)
AdminHtmlthe server's admin pages (the jobs page, the dev mailbox), on Look: a page with its stream of changes, times, links (server only)

Not yet#

Everything above works on Postgres and SQLite, tested over HTTP on both: the index, a new row's form, a row created, found by search and filter, changed and deleted. Not yet:

  • A list counts its rows (count(*)) and pages with offset: fine for thousands of rows, slow for millions.
  • A text filter, like the search, reads every row (no index helps ilike '%…%').
  • A foreign key in a list shows its value, linked to its row, not the row's title; its filter takes a value.
  • A foreign key or a check over several columns gives no widget: each column is edited alone.
  • No actions on several rows at once, and no history of who changed what.
  • Every route passes the effects. A server-only AdminPage could take Db itself (AdminPage.respond!(request, context, admin)); the package's PROPOSALS.md weighs it.

The package's README is the full reference, with its proposals beside it in packages/admin/. The pages and code above are the package's own.
