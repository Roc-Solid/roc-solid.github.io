The ecosystem · packages/mcp

Your app's tools, for AI agents

MCP, the Model Context Protocol, is how AI agents (and the apps they run in: Claude, an editor, the MCP Inspector) learn what an app can do, and do it. This package makes a Roc Solid app an MCP server. An endpoint becomes a tool in one line, with the JSON Schema the platform writes for /openapi.json from the same Roc types.

Use it to let agents search, read and add to your app's data. An MCP server offers three kinds of things:

  • Tools: actions the agent calls with arguments, such as "create a note".
  • Resources: data the agent reads by URI, such as notes://index. A template is a family of resources whose URIs follow a pattern, such as notes://note/{id}.
  • Prompts: ready-made messages a person picks from a menu in their agent (a slash command, say), filled in with their arguments.

The protocol is plain Roc on no platform, so you can test it with expects. A small module on the server platform, McpHttp, serves it over HTTP and makes tools from your endpoints. The notes example is a full app that agents use this way.

A first server#

A server is a record: a name, a version, and what it offers. This one converts temperatures. Its tool's handler is a Roc function from a record to a record: the package reads the agent's arguments into its argument type and sends its answer back as JSON. When the handler returns Err, the tool refuses, and the model reads why.

The JSON Schemas here are written by hand, since this server has no HTTP side. Over HTTP, McpHttp.tool writes them from the handler's types (below). The other fields:

  • resources: each read by its URI. Resource.text takes a URI, a name, a MIME type and a function that makes the text.
  • templates: each matches a family of URIs. In temperatures://boiling/{substance}, {substance} takes whatever the URI has in that place, and the read function gets it by name.
  • prompts: each makes messages from the arguments a person gives.

Serving it over HTTP#

McpHttp serves the MCP server from a route, such as routes/mcp/+server.roc, behind its directory's middleware, which decides who may ask. It makes tools from an endpoint, a function of the app's own, or a handler written for the tool. An endpoint's tool calls it as a handler does, through its own route and middleware with the MCP request's token, so an agent can do what the same credentials can do over HTTP, and no more. This sketch serves one and makes one tool of each kind:

McpHttp.What it is
respond!(server, request, context)The answer to one request to the MCP route, for its route file's respond!.
endpoint(Api.x, about, McpHttp.openapi({}))An endpoint as a tool. Api.x, in Generated/Api, is the function from the endpoint's path params to the endpoint. The tool's arguments are one object holding the path's params and the body ({ "id": "7", "tags": ["work"] }), sent with the MCP request's headers. The endpoint's answer is the tool's, and a refusal goes back to the model.
function(Module.name!, about, McpHttp.openapi({}))A function of the app's own as a tool, run inside the MCP request, behind the MCP route's middleware.
tool(about, handler!, McpHttp.openapi({}))A handler written for the tool, arg, Caller(c) => Try(result, Str), its schemas written from its types.
Caller(c)What a handler gets: { request, context, progress! }. context is what the middleware passed on, such as who is asking.
AboutA tool's { name, description }, and optionally title and tags.

McpHttp.openapi({}) is always the same argument: the platform's schema writers, passed as a value. A compiler limit means one generic function can't both read a type with Json and describe it with OpenApi, so the writers are passed in where the types are known.

A tool marked .reporting() may call progress! to say how far it has got. A client that asks for progress gets the answer as server-sent events: each step as it is taken, then the answer.

McpHttp is on the server platform: name the package mcp in the app's header and write import mcp.McpHttp. The browser's half of the app sees only the protocol's modules, which run anywhere.

Who may ask#

The middleware in front of the MCP route decides, as for any route: it can check a session cookie, an API key or an OAuth access token. The notes example checks a personal access token, which its users make on a settings page.

MCP's own way is OAuth: a client without a good token gets a 401 that says where to learn how to get one. The Bearer module builds those answers:

  • Bearer.token(headers): the token a request carries (Authorization: Bearer …).
  • Bearer.challenge: the 401, with a WWW-Authenticate header.
  • Bearer.insufficient: the 403 for a good token that lacks a scope.
  • Bearer.metadata: the document a server serves at /.well-known/oauth-protected-resource.

Not yet: issuing tokens. The platform has no authorization server of its own; that is a proposal.

The package also refuses a request a browser sends from another site's page (by its Origin header), so a web page can't reach an MCP server on the reader's own computer.

Testing a server#

Mcp.receive is pure, so an app's expects can send its server requests and read the answers with no network. Mcp.problems(server) lists what MCP won't accept:

  • a tool name that isn't 1 to 128 letters, digits, _, - and .;
  • a name or a URI given twice;
  • a schema that isn't JSON;
  • an endpoint's tool whose path params and body have a field with the same name.

What it speaks#

MCP over Streamable HTTP: one endpoint, where each POST carries one JSON-RPC message and is answered with JSON, or with a stream of events for a tool that reports progress. The endpoint speaks both eras of the protocol:

  • 2026-07-28, the current version, has no handshake. Each request states its version and the client's capabilities in its _meta, and its headers repeat them (MCP-Protocol-Version, Mcp-Method, Mcp-Name). server/discover says what the server offers, and each list says how long a client may keep it.
  • 2025-11-25, 2025-06-18 and 2025-03-26 start with initialize, then notifications/initialized. The server keeps no session between requests, as these versions allow, so it sends no Mcp-Session-Id.

The modules#

The protocol reads a request, checks it, and either answers it or says what to run. It has no effects: tools, resources and prompts are functions the app gives it. roc test packages/mcp/main.roc runs its expects, including the spec's example messages; the README lists every function.

What a tool is (Tool), what it answers (Content) and JsonValue come from the tools package: a tool made there is served here as it is, and the AI package's models use it too. Name tools in your app's header beside mcp, and import tools.Tool.

ModuleWhat it does
McpMcp.Server(ctx), what a server offers. handle!(server, incoming, ctx) answers a request. receive does the same purely: it returns an answer, or what to run. problems(server) is for a test.
ResourceResource.text(uri, name, mime, read!) and Resource.new(uri, name, read!): what reading a URI gives. Resource.contents is text or bytes.
TemplateTemplate.new(pattern, name, read!): a family of resources. read! gets the values the URI gave the pattern's names.
PromptPrompt.new(name, description, arguments, get!): messages made from string arguments (Prompt.argument, Prompt.optional, Prompt.user, Prompt.assistant).
BearerThe pieces of OAuth's answers, for the app's middleware (above).
RpcJSON-RPC 2.0: read one message; write a result, an error or a notification.

Mcp.Server(ctx) needs only name and version. The rest have defaults:

  • title: the server's name for people;
  • instructions: for the model, how the tools fit together;
  • tools, resources, templates, prompts: none by default;
  • page_size: how many items go in one page of a list (100);
  • ttl_ms: how long a client may keep a list, in current MCP (5 minutes);
  • origins: other sites' pages whose requests are answered. The server's own site's pages, and requests from no page at all (an agent, curl), always are.

The package has no components: its readers are agents, not people.

What is tested#

  • The protocol, in both eras, by 93 expects (what a tool is has its own, in the tools package).
  • Over HTTP, in an app built with rocx build on the server platform, with the official clients: the MCP Inspector's command line (2.16.0, speaking 2025-11-25) and the TypeScript SDK's client (2.4.0) on 2026-07-28. Covered: tools from an endpoint (with its path's params among the arguments), a function and a handler; refusals; resources; a template; a prompt; and a tool's progress, streamed as events.
  • examples/notes, whose server is its route routes/mcp/ and whose tests call its tools over JSON-RPC.

Waiting on a proposal (in packages/mcp/PROPOSALS.md):

  • a tag union in a tool's arguments, which the schema calls "any value" until the generated Api lists the tags it found;
  • an endpoint's doc comment as its tool's description (today you repeat it);
  • an OAuth authorization server of the platform's own.

Limits#

  • Not yet: list-change notifications, resource subscriptions, completions, logging to the client, and requests from the server to the client (sampling, asking the user).
  • No sessions: nothing is kept between requests.
  • Every field of a typed tool's arguments is required, as the platform's schemas say. For an optional argument, use a Tool.new tool, which takes any JSON.
  • A batch (a JSON array of messages) is refused: MCP has had no batches since 2025-06-18.
