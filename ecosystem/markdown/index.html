The ecosystem · packages/markdown

Markdown, parsed in Roc and rendered as markup

A Markdown parser in plain Roc: CommonMark, plus GitHub's tables, strikethrough, task lists, bare links and footnotes. The <Markdown> component renders it as the platform's markup, so a post is one tag. Raw HTML shows as text and a link that could run script points nowhere, unless you say otherwise. Frontmatter is read into a record you declare, and a folder of posts becomes a typed list, checked when the app is built.

Use it for text people write in Markdown: a blog, docs pages, release notes, a comment preview. The parser, the component and the frontmatter reader are plain Roc, so they run the same on the server, in the browser and in a test.

The HTML it renders

The component renders wherever the page does: on the server, or here, when the site was built. Each heading gets an id from its text, as on GitHub (a-morning-by-the-river). A tight list (no blank lines between items) has no <p> around its items.

rocx build copies the component from the package's components/ into the app (Generated/markdown/Markdown.roc), because a package can't import the platform's Html for server and browser at once. There is nothing to register: it is a package, not a plugin.

The document is data#

Md.parse turns Markdown into a document: a list of Blocks (paragraphs, headings, lists…), each holding Inlines (text, emphasis, links…), plain Roc values any function can walk. A table of contents is the list of headings; a reading time is a word count. Parse once, and give the document to <Markdown> as doc:

Two headings with the same text get intro and intro-1, so each link finds its own heading. Blocks and inlines compare with ==, so a test can check a parse without rendering it.

Hooks#

A hook draws one kind of node your own way. <Markdown> has hooks for heading, code, link and image, plus footnote and notes for footnotes. A hook gets what the node says, its children already rendered, and returns the element. The defaults are public (Markdown.heading, Markdown.code, Markdown.link, Markdown.image, Markdown.footnote, Markdown.notes), so a hook can fall back on them, as the link hook above does.

To colour code, Markdown.highlight(lines) makes a code hook from any highlighter. lines(text, lang) returns the code's lines, each a list of tokens ({ kind : Str, text : Str }). A token with a kind becomes a <span class="t-kind"> for your CSS to colour.

<Markdown>#

PropWhat it is
source : StrThe Markdown.
doc : List(Block)Or the document, already parsed for something else too (a table of contents).
raw : [Escape, Drop]Raw HTML in the source: shown as text (Escape, the default) or left out (Drop).
class : StrThe class of the <div> it renders in: "markdown" by default.
heading : Markdown.Heading -> HtmlDraws a heading, given { level, id, text, children }. The default is <h2 id="…"> for a level 2.
code : Markdown.Code -> HtmlDraws a code block, given { lang, info, text }. lang is the info string's first word (roc after three backticks), or "". The default is <pre><code class="language-roc">.
link : Markdown.Link -> HtmlDraws a link, given { url, title, children }.
image : Markdown.Image -> HtmlDraws an image, given { url, title, alt }.
footnote : Markdown.Footnote -> HtmlDraws a footnote's reference in the text, given { number, href, id }.
notes : List(Markdown.Note) -> HtmlDraws the notes at the end, given each one's { number, id, children, backs }.

Every prop has a default: give source or doc, and <Markdown source={text} /> is a whole use. The component is pure (its view has no !): it makes markup from its props and runs nothing after.

Footnotes#

Footnotes are GitHub's: [^salt] in the text refers to a note, and [^salt]: About 2% of the flour's weight. on its own line is the note. Notes are numbered in the order the text first refers to them, and put at the end. A note nothing refers to is left out; a reference to a missing note stays text, as on GitHub. The default hooks draw what GitHub draws: a numbered <sup> link, and a list of notes, each with a link back (↩) to every reference. The back links are labelled in English, so a page in another language gives its own notes hook. Md.footnote_problems(source) lists what is wrong with a file's footnotes, for a build or a test.

Safe by default#

Markdown may hold raw HTML, and a link may point at javascript:. Neither reaches the page as written, unless you say so:

By default: the HTML as text

A <b>bold</b> claim, and a link that would run script.

<script>alert("hello")</script>

With raw={Drop}: the HTML left out

A bold claim, and a link that would run script.

Either way, the link's href is about:invalid#rocx-unsafe-url. A URL may be relative, or start with http:, https:, mailto: or tel:. Anything else is replaced, even with tabs or line breaks hidden in it, as the platform does for every href (Safety).

For HTML text from a source you wrote yourself, Md.to_html_with(doc, { raw: Trusted }) writes raw HTML as it is and checks no URLs. <Markdown> has no such option: the platform's Html can't put a string into a page as markup.

Frontmatter and collections#

Frontmatter is YAML between two --- lines at the top of a post. Declare its shape as a record type: a nominal type (:=), so fields can have defaults (??), with parser_for : _, so Roc writes its parser. The field types decide each value: 2026 is a number for a U64 field and text for a Str one.

A collection is a folder of such files, as in Astro. Collection.load reads each file's frontmatter into the record and parses its body. In a top-level value, the files are read when the app is built, so bad frontmatter fails the build, naming the file and the field: winter: draft: expected true or false, found "maybe". This page lists its two posts by hand:

An entry is { id, data, body, doc }: its path without .md, its frontmatter, its body, and the body parsed. Frontmatter.read(source) does the same for one file. The YAML reader covers what frontmatter uses: maps, lists (- item or [a, b]), inline maps, quoted and plain text, | and > blocks, comments, and null, which leaves a field to its default. It doesn't read anchors, aliases or tags.

In an app, rocx build finds the files

In an app you don't list the files. Each lower-case folder under content/ is a collection: rocx build finds its Markdown files, at any depth, and writes a module for it, such as Generated/Content/Posts.roc for content/posts/, each file imported as text. Put the frontmatter's type beside them (content/posts/Post.roc), and Posts.all is every entry, read as the app is built, and Posts.get(id) is one. A new post is just a new file. Without a type, the module has only Posts.files, for the app to read its own way.

The modules#

roc test packages/markdown/main.roc runs the package's tests, 202 of them examples from the CommonMark and GitHub Flavored Markdown specs. The package's README has the full API.

ModuleWhat it does
Mdparse(source) makes the document. to_html(doc) writes it as HTML text (for a feed or an email), and to_html_with(doc, { raw, ids }) with options. Also headings, slug, words, reading_minutes, safe_url, href, escape, and the footnote helpers.

In the browser#

This page's examples are rendered once, when the site is built, inside <NoHydration>: the browser keeps the server's markup, and none of the parser is in its wasm. Do the same for a post or a docs page. Hydrating <Markdown> carries the parser to the browser: about 225 KB more wasm (73 KB gzipped), measured in a small app.

A live preview is worth that. Keep the text in a signal, draft!, set by a <textarea>'s on:input.value, and render it in a hole: {Markdown.view({ source: draft!() })}. The hole renders again whenever the draft changes.

What works, and what doesn't yet#

Works today:

  • The parser passes 649 of CommonMark 0.31.2's 652 examples. The other three are bare links (https://…, www.…, someone@example.com), which GitHub's extension links and CommonMark leaves as text. Every GitHub extension example passes except the tag filter.
  • <Markdown>, its hooks and Markdown.highlight, on the server and in the browser.
  • Frontmatter read into a record, collections found by rocx build under content/, and a bad file failing the build.

Not yet (each a proposal in packages/markdown/PROPOSALS.md):

  • Trusted raw HTML in <Markdown>, or HTML from an allowlist.
  • The highlighter these docs use, in a package of its own, so any app can colour code.
  • A component that never hydrates, so <Markdown> stays out of the wasm without <NoHydration> around it.

Limits: a reference's label is case folded for ASCII, Latin-1, Latin Extended-A, Greek, Cyrillic and ß, not all of Unicode. No heading attributes ({#id}), smart quotes or maths.
