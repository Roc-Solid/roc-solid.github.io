The ecosystem · packages/push

Notifications that arrive with every tab closed

Web Push lets a server notify a browser that agreed to it, even with none of the site's tabs open. This plugin has every part: a button that asks and subscribes, a table of each browser's subscription, and a job that sends.

Use it for news a user wants while away from your site: a reply to their question, a finished export, a shipped order.

A first app#

Each file below is from packages/push/example: a page with the subscribe button and a button that notifies everyone. It can't run on this site, which is static files: Web Push needs a server.

1. Keys. Web Push identifies your server by a key pair, the VAPID keys. Under rocx dev you need none to start: the server makes a pair for the run and logs the two settings that keep it:

rocx dev restarts the server at each change to its code, and a new pair means each browser's button shows off until clicked again. To keep the pair, copy the two settings into .env. Without VAPID_SUBJECT, the run tells push services mailto:dev@example.com, and logs that.

A deployed server needs all three in its environment: VAPID_PUBLIC_KEY, VAPID_PRIVATE_KEY and VAPID_SUBJECT (mailto: and an address, or an https: URL). Give it its own pair: under rocx dev, /__rocx/push/keys answers a new one each time, as the two lines to set.

A browser can only be sent to with the pair it subscribed with, so keep the keys once you have users. Without --dev, a missing key or subject, or two keys that don't belong together, stop the server at start, and it says why and how to make a pair.

2. The plugin. Name the package in the app's header and list its plugin, with the jobs plugin, which runs the job that sends:

The plugin brings:

  • its table, push_subscriptions, in the app's database (Postgres or SQLite);
  • its job, push.deliver, which the jobs plugin's workers run;
  • the service worker at /push-sw.js and a script every page loads, both served before the app's middleware, so a guard never blocks them;
  • under --dev only, GET /__rocx/push/keys.

Its three endpoints are your routes, each a file calling the package's handler behind its folder's middleware: GET /push/key (the public key), POST /push/subscribe and POST /push/unsubscribe, where <PushButton api="/push"> looks. Put them elsewhere and give the button that path.

Push.key_route!(request) and Push.unsubscribe_route!(request, owner) answer the other two the same way.

3. The page. The button, and a handler that asks an endpoint to notify everyone:

<PushButton>#

A button that turns this browser's notifications on and off. A click calls the plugin's script (static/push.js) with Browser.call!, which asks the browser's permission, registers the service worker, subscribes with the server's public key and posts the subscription to the server. Turning off unsubscribes and tells the server. Browsers show the permission prompt only during a click, key press or tap, so subscribing starts from a button.

PropIs
api : Str where your routes for push are: with "/push", GET /push/key, POST /push/subscribe and POST /push/unsubscribe

Browser.call! can't return an answer, so the script reports with a pushstate event, which every <PushButton> on the page hears: how a click went, and, when the page loads, where this browser stands. The button shows each report as a PushState:

The script saysThe button shows
"": until the script has looked Turn notifications on
off: the browser can, and hasn't subscribed Turn notifications on
working: after a click: asking, subscribing, telling the server One moment…, disabled
on: subscribed, and the server has it Turn notifications off. Beside it: Notifications are on in this browser.
blocked: the user said no to the prompt Turn notifications on, disabled. Beside it: Notifications are blocked for this site: the browser's site settings can allow them.
unsupported: no service worker or Push API here, or not a secure page Turn notifications on, disabled. Beside it: This browser can't show notifications from a site. On an iPhone or iPad, add the site to the Home Screen, and open it from there.
failed:no network: a click went wrong: failed:, then why Turn notifications on. Beside it: That didn't work: no network

aria-pressed says whether notifications are on, and a screen reader reads the note when it changes (aria-live). On an iPhone or iPad, a site gets Web Push only once it is added to the Home Screen and opened from there.

A notification#

A notification is a title, a body, the page a click opens (url) and a tag. Its options tell the push service how to treat the message. Change them below to see what a server would send, worked out by the package's own functions in your browser.

Kept for
Urgency

The data, Notification.to_json: 78 of 3993 bytes

{"title":"Your export is ready","body":"orders.csv, 3 MB","url":"/exports/17"}

The headers the push service reads, Options.headers

TTL: 86400
Urgency: normal

Push.notify! would queue it: a job for each of the user's browsers.

The request has two more headers: Authorization (the VAPID token, vapid t=…, k=…) and Content-Encoding: aes128gcm. The data is encrypted: the push service sees only bytes.

FieldIs
title : Strthe notification's first line; empty: the site's host name
body : Strthe text under it
url : Strthe page a click opens, on this site only; empty: the front page
tag : Stra newer notification with the same tag replaces this one, rather than piling up
icon : Stran image's URL

Notification.new(title, body) makes one with the other fields empty, and { ..Notification.new(title, body), url: "/orders/17" } sets more. Empty fields are left out of the JSON.

OptionIs
ttl : U64 how many seconds the push service keeps the message for a browser that is offline. 0 means now or never; more than four weeks is sent as four weeks.
urgency : [VeryLow, Low, Normal, High] how soon it must arrive. A phone on battery may hold the low ones back.
topic : Str a newer message with the same topic replaces one still waiting, so only the latest status arrives. At most 32 characters, of letters, digits, - and _.

Options.defaults is a day, Normal, and no topic.

Sending#

On the server, a job or endpoint calls Push.notify! (one user's browsers) or Push.broadcast! (every browser). Each checks the notification and options, queues a push.deliver job for each subscription, and answers how many it queued. Inside a transaction, the jobs are queued only if it commits.

A jobs worker sends each message; the push service's answer decides what happens next:

The push service answersThe job
201, or any 2xxis done, and notes when it sent
404 or 410deletes the subscription: the browser unsubscribed, or it expired
408, 429 or 5xx, with Retry-Aftersends it again at that time, five times at most, while the message's TTL lasts
408, 429 or 5xx without it, or no answerfails the attempt; the worker tries again, waiting longer each time (five attempts)
400, 401, 403, 413, or anything elselogs it and notes it on the subscription; sending again wouldn't help

A retry sends the TTL that is left, so a message never outlives it. A 403 doesn't delete the subscription: push services answer 403 to wrong VAPID keys, and a mistake in the server's settings shouldn't delete every subscription.

How it works#

  1. A click on <PushButton> asks the browser's permission.
  2. The browser subscribes at its push service (Google's for Chrome, Mozilla's for Firefox, Apple's for Safari, Microsoft's for Edge) with the server's public key. It gets a subscription: a URL at that service, and two keys.
  3. The page posts the subscription to the app, which keeps a row for each browser.
  4. Later, the server calls Push.notify!, which queues a job for each of the user's subscriptions.
  5. The job encrypts the notification for that one browser (RFC 8291), signs a token that says which server sent it (VAPID, RFC 8292), and posts both to the subscription's URL (RFC 8030). The elliptic-curve work and the AES are the server platform's (P256 and AesGcm).
  6. The push service wakes the browser. The package's service worker shows the notification, and a click on it opens the page it names.

The modules#

Plain Roc, on no platform: the formats, the key derivation, the token, and what each answer means. The browser's half of an app can use them too (browser.roc lists them). roc test packages/push/main.roc checks them against the RFCs' own examples. Every function is in packages/push/README.md.

ModuleWhat it does
Subscriptiona browser's subscription: parse (the page's JSON), from_body (an endpoint's body), from_text and to_text (a table row), to_json; known_service: is it at Chrome's, Firefox's, Safari's or Edge's push service?
Notificationwhat the service worker shows: new, to_json, data
Optionshow a push service treats a message: defaults, check (the topic), headers, remaining (the TTL left for a retry)
Deliveryrequest (the POST to a subscription's URL); outcome (what an answer means: Delivered, Gone, RetryAfter(ms), Retry(why), Refused(why)), retry_after, http_date
Vapidthe server's token, RFC 8292: Keys and from_text (from the environment), audience, claims (valid 12 hours), signing_input, token, authorization
WebPushthe message's encryption, RFC 8291: prepare (everything before the AES), body, max_data (3993 bytes)
Ecethe aes128gcm content coding, RFC 8188: header, parse_header, pad, unpad, keys, nonce
PushStatewhere a browser stands, as the page's script reports it: what <PushButton> shows

HMAC-SHA-256, HKDF-SHA-256 and base64url come from the crypto package, which push names in its own header: an app names push alone.

The plugin, Push.plugin({}), on the server platform, which the package names in its header (plugins): its table and its migrations (migrations/, for Postgres and for SQLite), the job that sends, and the handlers the app's routes call. Each function's owner is the app's id for a user, as text, or "" for a visitor.

ModuleWhat it does
Pushplugin(setup), the plugin (at, owner); subscribe!(body, owner) and unsubscribe!(endpoint, owner), which its endpoints call; notify! and broadcast!; public_key! and keys! (from the environment, or under --dev without keys the pair the run made); deliver, the job; send!, one attempt
PushStorethe push_subscriptions table: save! (a row for each endpoint), remove!, remove_id!, find!, of_owner!, everyone!, and delivered! and refused!, which the job calls

The browser's part: <PushButton>, in components/, which rocx build copies into the app, and these files in static/, which the plugin serves:

FileWhat it does
push.jsthe page's script, at /rocx/plugins/push/push.js, on every page: the push.subscribe and push.unsubscribe effects the button calls. Once a visit, it sends the server the browser's subscription again, in case it lost it. On a site served under a base path (/rocx/), every URL it uses is under that path.
push-sw.jsthe service worker, at the site's root (/push-sw.js), so its scope is the whole site. It shows a message's notification; a click focuses a tab already at its URL, or opens one. When the push service replaces a subscription, it tells the server.

Safety#

  • The server posts to whatever URL a subscription names, so Push.subscribe! accepts only https: URLs at the browsers' own push services. Under --dev (as rocx dev starts it), it also accepts an http: URL on this machine, for a stand-in push service.
  • The private key never leaves the server; the page gets only the public key. Only under --dev, on your machine, is a pair logged or answered; a deployed server never makes one.
  • A click on a notification opens only this site's pages.
  • Messages are encrypted for the browser: the push service sees only bytes.

Status#

Tested today:

  • All the plain Roc, by expects against the RFCs' own examples. The server platform's tests check its AES against RFC 8291's and RFC 8188's examples, and its ECDH, ES256 and key pairs against Node's crypto.
  • The plugin, in the example app on SQLite, and on Postgres when one is available. It saves and forgets subscriptions, and refuses one at an unknown service or with a key off the curve. A broadcast goes to a push service the test runs, which plays the browsers too: it checks each request's VAPID token and signature, decrypts each message as a browser would, and answers so that a gone subscription is deleted and a refusal is noted on its row. The key checks at start, the dev pair and /__rocx/push/keys are tested too.
  • The button, script and service worker, in Chromium behind a guard that refuses every script the app would serve: the plugin's files still come through, the worker's scope is the whole site, and the button subscribes.

No test sends to a real push service (Google's, Mozilla's, Apple's or Microsoft's). They accept what the RFCs say, which the tests check; a real browser's first notification is the last check.

Not yet (each has a proposal in packages/push/PROPOSALS.md):

  • Jobs that give up, or come back at a set time. Today a refused message ends its job as if it had been sent, and a Retry-After queues a copy of the job for that time.
  • Browser.call! with an answer. Until a call can answer, the script tells the button how it went with a DOM event (pushstate).

A limit: a message holds 3993 bytes of data, the notification's JSON. Push.notify! refuses a longer one.
