Tooling

A few commands, and the compiler you already have

rocx turns markup into Roc, builds and serves your app as you edit, and points the Roc compiler's reports at your .rocx lines. It is written in Roc, and lives in ~/.rocx/bin once installed, or at bin/rocx in a clone of the repository.

Commands#

dir is an app's folder (the one with routes/), the current one by default. rocx or rocx --help lists the commands; rocx help build or rocx build --help shows one command's options. At a terminal, each build step shows a ✓ and its time; in a pipe, in CI or with NO_COLOR set, the output is plain text.

rocx new [dir]--db sqlite|postgres|turso

Makes an app from rocx's template in dir, which must be empty or new (asked for at a terminal). People sign in with the auth package (an email link; Google and GitHub once their keys are set; any address under rocx dev), into the app's own users table. Other sites' posts are refused, guard's security headers are on, and sign-in mail is rate limited. The database is SQLite unless you pick another (it asks at a terminal). .rocx-version names the app's rocx version (commit it); .rocx is the link the app's header reaches the platform and packages through (gitignore it). From a clone of the repository, .rocx links to the clone and there is no .rocx-version. The app's README.md says what to change first.

rocx dev [dir]--port 8080--android [--lan]-- <server options>

Serves the app at http://localhost:8080 in development mode. Each save rebuilds it, restarts the server and reloads open pages. A failing build's errors show at their .rocx lines while the last good build keeps running. The first run writes the smallest main.roc if there is none. Each start also checks the app's SQL (rocx check --sql).

The port is --port, else PORT, else 8080. Options after -- go to the server (--database-url postgres://…), which also reads its environment (DATABASE_URL) and a .env file in the current folder (SMTP_URL=… lines; the environment wins). Development mode adds the stories (/__rocx/stories), plugins' development pages (the email package's mailbox) and crash messages in 500 answers. Builds use Roc's fast-compiling development backend; building it yourself makes an optimized one.

--android also builds for Android: it installs a development client on an emulator or a USB-connected phone, and reloads it on each save. --lan also serves the app on your network and prints a QR code for a phone on the same Wi-Fi. This needs the Android SDK and NDK; the pomodoro example runs this way.

rocx build [dir]--out dist--target arm64musl

Builds the app to deploy: dist/server, optimized for speed, and dist/static, the app's static/ and the browser's files (wasm optimized for size). Run dist/server --static dist/static behind a TLS proxy (Caddy, say). --target is arm64mac, x64mac, or arm64musl or x64musl (static Linux executables for a container). The server has only the database engine the program names (SQLite if none); a Linux build has no debug info. The build replaces dist (or --out) only when complete; that folder must be empty or an earlier build (with a server).

rocx build [dir] --image--out <name>.tar--tag name:tag

The release as a container image, which rocx writes itself: no Dockerfile, no Docker. The server is a static Linux executable with its TLS roots inside, so the image has no base and one layer: /app/server, /app/static, a user to run as (65532), /tmp, and /app/data for a volume (a SQLite app's data/app.db). It runs in /app on PORT 8080. The output is an OCI image tar, <name>.tar after the app's folder (or --out), for docker load -i or podman. --tag defaults to the folder's name, :latest; --target is arm64musl or x64musl (default: this machine's).

rocx build [dir] --static--out dist--base /path/--route <path>--built <build>-- <server options>

Writes the app as static files into dist/ (or --out) for a host with no server: GitHub Pages, a CDN, any web server. It builds for production, runs the server on a free port, and saves /, every page whose path has no params, and every page they link to, each as <path>/index.html. Beside them go 404.html (for paths nothing answers), the app's static/, and rocx/ (the runtime and the wasm). Each page carries the answers to its reads, so its data needs no server. This site is built this way.

--base puts every URL under a path (--base /docs/ for example.github.io/docs/). --route adds a path no page links to: a page with params (/blog/hello) or an endpoint's answer as a file (/feed.xml). --built uses a build you made (its server and client/static). The copy replaces its folder only when complete; the folder must be empty or an earlier copy.

The build lists what only a server can answer, which the copy leaves out: methods that write (post!), events and channels, pages behind a directory's middleware (it runs per request), pages with params no link or --route reached, and links to paths that answered an error.

rocx generate [dir]…--client <out>--dev

Only the code generation rocx build and rocx dev start with, for editors and scripts. Each .rocx file under the folders becomes a .roc file beside it, its markup as calls to the platform's Html. For an app it also writes Generated/: Routes.roc (the router), Paths.roc (typed links), Api.roc and Handlers.roc (the endpoints' contract and handlers), Styles.roc (the stylesheet), App.roc (which main.roc completes), Root.roc for an app with pages (the page at the browser's path, in its layouts), and route files' own Roc. Packages' components are copied into Generated/<package>/, and each folder under content/ becomes Generated/Content/<Name>.roc, listing its Markdown files.

--client also writes the browser's copy of the app into <out>: endpoints without their handlers (method, URL and types kept), <NoHydration>s without children, and no imports only those used. For an app with pages, it adds the browser's main.roc and static/rocx/: start.js, the runtime, and the stylesheet named by its content (styles-hash.css). The runtime is minified (about half the size with brotli), except in a --dev build. A --static or --release build ships only the runtime code the app's wasm and pages reach: in-place navigation only for an app of several pages (or one that navigates), and drags, pointer positions and glides only where its markup has them. An app of endpoints alone has no browser program, and the build says so. When the browser's copy reaches a module that imports something server-only (pf.Db, directly or not), the build warns at the page's or component's import, before the browser's build fails far from it.

--dev also builds the stories and their catalog.

rocx check [dir]

Builds the app from its sources (never an older build's files) as rocx dev does, then type-checks the server's program and, for an app with pages, the browser's. Each problem shows at its .rocx line. Exits 0 when clean, 1 on an error, 2 on warnings only, rocx's own included: a match arm's value or a list row's item given to a component that reads it once (if, match and .map). Needs a main.roc. Run it in CI.

rocx test [dir]

Builds the app as rocx check does, then runs its expects with rocx's compiler, each failure at its .rocx line. Exits 1 if one fails.

rocx check -- <command>

Runs a command (roc check, roc build, just check) and points the compiler reports it prints at the .rocx files (errors at your lines). Exits with the command's code.

rocx check --sql [dir]--engine sqlite|turso--verbose-- <server options>

Checks the app's SQL with its own database engine, and its row types with the compiler. Each string statement at a Db.all!, Db.one! or Db.run! is prepared on a scratch database built from the migrations: a temporary file for SQLite or Turso, or a database created, then dropped, on the Postgres server --database-url (or DATABASE_URL) names. It reports SQL the engine refuses, parameters that don't match their statement and row types that don't fit, at their lines, and exits 1 (how it works).

--engine checks a SQLite app on Turso, or a Turso app on SQLite. --verbose also lists the calls it couldn't check, such as SQL built at run time.

rocx lint <dir>…

Refuses Html.source_text in hand-written .roc files under the folders: it puts any string in a page as markup (why). Mentions in comments or strings don't count. Exits 1 if a file calls it.

rocx routes [dir]--server--client

Lists an app's routes: each method and path, and the middleware around it, outermost first (what runs, in what order). --server lists only the endpoints; --client only the pages (the error page too).

rocx fmt <path>…--check

Formats the Roc in each .rocx file, and each .roc file rocx didn't write, under the paths, with roc fmt: rocx's compiler (an installed version's, a clone's .tools/roc-active, else the one ROC names), else the roc on your PATH. Markup and the Roc in its holes stay as written: markup moves only with the code around it, and <pre> or <textarea> text never moves. --check lists unformatted files, and exits 1 if there are any.

rocx qr <text>--pbm

Prints the text as a QR code in the terminal (as rocx dev --android --lan does), or as a PBM image with --pbm. A code holds at most 2,331 bytes.

rocx upgrade [version]

Installs rocx (the latest, or the version you name) into ~/.rocx as the default. In an app, it also moves the app's .rocx-version and .rocx link to it. Every command on an app runs the version the app names, installing it if needed, so a team shares one version through the repository. A rocx from Nix leaves upgrading to Nix.

rocx agents [dir]--force

Writes rocx's rules for coding agents into the app's AGENTS.md, as a block between two markers, and a CLAUDE.md that imports it if there is none. The block points at .rocx/agents/guide.md, the guide for the app's rocx version. Run it again after an upgrade: it rewrites only the block, so the app's own notes stay. It refuses an edited block without --force. rocx check says when the block is from another version. rocx new writes both files.

rocx help [command]

The commands, or one command's usage and options (rocx <command> --help too).

rocx --version

Which rocx this is: an installed version's number, commit and compiler; a clone's commit.

rocx build writes a file only when its content changes, so watchers don't loop. It deletes the .roc files it wrote whose .rocx file is gone, and stops at the first markup problem, with its line and column. Generated files end with a # rocx: generated from … line. Keep them out of version control: ignore Generated/, build/ and the .roc files beside your .rocx files.

Errors at your lines#

Markup mistakes (an unclosed tag, an attribute rocx refuses) are rocx's: rocx build reports each at its line and column, with a caret, and stops. The rest are the Roc compiler's. Line N of a generated file is line N of yours, so its reports already name your line. rocx check and rocx dev also rewrite the location, quote your line, and move the caret onto your code. A route file's Roc (+server.roc) is reported at its lines too.

In an editor#

The repository's editors/ folder has a grammar for .rocx files. It colours Roc (by the official Roc grammar), markup (tags, a component's tag as a type, attributes like class:active and on:click.prevent), the Roc in holes and markup inside it, and CSS in a <style>. Its one guess: a < before a letter starts markup, unless a value comes right before it. So a <b (a comparison with a space before < and none after) is coloured as markup.

VS Code: just vscode-extension installs the extension for every workspace (it needs code on your PATH, and Node). Besides highlighting, it adds a task type: Terminal → Run Task… → rocx lists dev (runs rocx dev in its own terminal) and check (runs rocx check once) for each app. Their reports show at the .rocx line and in the Problems panel until the next run. A task of your own in .vscode/tasks.json runs any command the same way ({ "type": "rocx", "command": "just check" }). There is no language server yet: the editor shows what the build reports.

Orca: just orca-plugin installs a plugin that highlights .rocx and .roc files. It runs nothing, so it needs no access. Orca plugins can't show errors: use rocx check.

Stories#

A component's stories are the ways it looks, written beside it, as in Storybook. Each <story name="…"> among the component's definitions holds one story's markup. rocx makes each a definition (story_tip! for <story name="Tip">), so every build checks it against the component. Only a development build shows them: rocx dev (or rocx build --dev) serves a catalog at /__rocx/stories.

The catalog lists every story in a sidebar:

  • S folds the sidebar, / searches it, and ↑ and ↓ step through it. Its parts and components fold, and its edge drags wider.
  • The story you pick shows in a frame, with the line it is written at. F fills the window with it; Esc comes back.
  • A component's name shows all its stories side by side.
  • The pin beside a story (P) picks it to compare, from any component, and "Compare … side by side" (C) opens the picked ones together.
  • A story with a video in it gets a transport: play and pause (Space), a frame at a time (← and →), a scrubber, a speed and looping. Every video shown follows it, so videos side by side play in step. Render copies the command that films them.
  • A dot marks a story the browser hasn't shown yet, and its component and part: N opens the next, and searching for new lists them.
  • The browser remembers what it has seen, what is folded, what is picked and the width.

Each story is the app's page at its own path (/__rocx/stories/…), rendered in the root layout and hydrated, so it works as in the app. A layout can tell a story by its path (this site shows one with nothing around it). An app with no pages can't show stories, so they are an error there.

An app's stories/ folder holds modules of stories only: drafts, each a component with its own <style>, side by side in the catalog. Only a development build compiles it, so none of it is published, styles included. This site's site/stories/Landing.rocx has the front page as it is, and drafts of it in six themes.

Building an app yourself#

An app is two programs (the platform): the server's, native code in a Rust host, and the browser's, the same pages in WebAssembly. rocx dev builds both (getting started); rocx build --release builds them to ship (below). The server's program, Generated/App.roc, is rocx's: every request goes through the app's middleware (routes/+middleware.roc) to the router, where every URL is a file. The app's main.roc says only what rocx can't know:

  • init! makes the app's context once, at start; every request's middleware gets it.
  • Middleware isn't here: a +middleware.roc under routes/ runs around its directory's routes, routes/+middleware.roc around every request (middleware). Before it, changes sent from other sites' pages are refused (why) unless the app says cross_site: Allowed.
  • It may also say database (Sqlite("data/app.db") unless it says Postgres, Sqlite(path) or Turso(path)) and plugins (what packages add: tables, jobs, loops, scripts; never a route).

rocx writes the browser's program too (rocx build --client): its root is the page at the browser's path, which the browser hydrates. This site's:

For a release, rocx build compiles the browser's wasm with --opt=size --specialize=yes, and the server's program and host into one executable with --opt=speed, with what it serves beside it. Its --target works from a Mac too (deploying). The executable takes its port, database and the rest as flags or environment variables (running it).

The server is built with boxy lowering (--specialize=no) by default. With Roc's default, lambda-set specialization, the function that renders pages gets a stack frame that grows with the app, and a large app's could outgrow its stack. Boxy lowering renders about as fast and builds much faster; --specialize=yes (or ROCX_SPECIALIZE=yes) opts back in. Specializing the browser's wasm makes it smaller with brotli, and faster.

Both platforms have requests, routes, endpoints, events and middleware (pf.Server, pf.Endpoint, pf.Middleware, pf.Events, pf.OpenApi) and the modules components are written with, so a component compiles on both. The database, the key-value store, channels, live rooms and actors are the server platform's alone; jobs, cron and email are packages for it (the ecosystem).

To work on Roc Solid itself, clone the repository and run just setup. It uses your system's Zig 0.17.1 and Rust 1.85 or newer (from Nix, say), else downloads them into .tools/, and adds Rust's wasm32-unknown-unknown target (for the browser's host) with rustup. Roc is a fork of a pinned nightly with the compiler fixes Roc Solid needs: just setup builds it from a clone of the fork if there is one, else downloads it prebuilt from the repository's releases (macOS on Apple silicon, Linux on arm64). Scripts use that compiler, never the roc on your PATH. Only the repository's checks and tests, the site's build and the VS Code extension need Node; rocx and your apps don't.

bin/rocx also has commands for the repository's scripts: rocx site dev and rocx site prepare (this site), rocx self-build (rebuilds bin/rocx when its Roc changed) and rocx internal (the tests' calls into rocx's functions).
