Roc Solid in js-framework-benchmark

js-framework-benchmark is the yardstick most web frameworks are measured with: one page, a table of rows and six buttons. Its runner opens each framework's page in Chrome, clicks, and times until the page has painted; it also measures memory and downloads. Roc Solid's two entries are in benchmarks/jsframework/, here beside vanillajs (the floor: hand-written DOM code), Solid (the closest relative), Leptos (signals in Rust and wasm), Joy (the other Roc framework) and React.

Roc Solid's page is HTML the server rendered, so the browser paints it at once, the best of them; its buttons answer once the runtime and the wasm have come and hydrated the page, the last of them here. The benchmark's server compresses each file as it sends it (brotli, at its slowest), one at a time, which costs by the raw byte, and Roc Solid's page has the most of them: from a server that sends files compressed beforehand, as a deployment does, the wait is much shorter. Ready to use is measured here, beside the runner: a cold load, five times, until the buttons answer.

What they say#

The first paint is the best of them: the page is server-rendered HTML (here, files written by rocx build --static), shown before its wasm loads. Ready to use is the reverse: the page answers a click only once the runtime and the wasm have arrived and hydrated it. On the benchmark's server, which compresses each file slowly as it sends it, that is the last of them. The download is most of that: the runtime ships only what the page uses (D-087), 128 KB of its 180 in the run shown, but with the wasm it is still more than Joy's, Leptos's or React's, and many times Solid's, which is JavaScript alone.

Updating existing rows is close to the others: a row's holes rerun only when its data changed (compared with ==), selecting one runs the two rows it leaves and comes to (create_selector!, D-083), and a swap moves the two rows that moved. Making rows is slower: about twice vanillajs, for 1,000 rows and for 10,000. A row is a template (D-084): its markup comes once, and each row is a copy with its parts put in, so Roc builds no markup beyond its holes. But each hole is its own computation, run by a call into the wasm, noting what it read for the next change; vanillajs writes the text and is done. Memory follows: a computation for the row and each hole, each with what it read. The repository's TODO.md lists what is left.

How CPU time got here, against the fastest:

  • 5× in the first run (D-074). 2.06× after fixing how the host noted what runs allocate, and how a .map reorders rows.
  • 1.83× (React: 1.74×) after D-083 to D-087, on 2026-11-25 and 26: the selector, templates, cheaper notes, fewer calls per row, the runtime shaken to what a page uses. Creating 1,000 rows: 45.8 → 39.3 ms; selecting one: 11.8 → 7.7; download: 73.4 → 66.2 KB. Each step was measured alone. Two were taken back for their cost elsewhere: preload hints (a later first paint) and delegated handlers (more memory).
  • 1.68× (React: 1.70×) in the run shown (2026-11-26, at 505b0e7), after the browser's host became Rust (D-090, its memory shared with the phone's, D-091), a list whose rows all go is emptied at once, and each computation keeps less. Creating 1,000 rows: 39.3 → 36.1 ms; 10,000: 448 → 381; replacing 1,000: 43.3 → 40.5; appending: 46.6 → 42.1; selecting one: 7.7 → 6.2; clearing: 19.8 → 15.0; run memory: 4.8 → 4.5 MB; first paint: 37 → 30 ms; ready to use: 288 → 262 ms. The download grew from 66.2 to 67.7 KB with the runtime features that landed meanwhile.

The entries#

Each entry is a one-page app with the vanillajs entry's markup (the runner finds buttons by id and rows by class). keyed keeps each row by its id (.map with key={row.id}), so a row moves with its data; non-keyed keeps a row by position (.map_with_index with key={i}), so a swap rewrites the two rows instead. The rows' data is plain Roc (Rows.roc): an id and a three-word label from a fixed-seed generator. Nothing is batched or cached beyond what an app would do, and the wasm is built as an app ships it.

The others are the benchmark's own entries, built as its README says (Leptos's build is in its repository). Joy's entries aren't in the benchmark yet; they're built from its 0.35.0 release as Joy's benchmarks/jsframework/README.md says. Upstream retired its non-keyed entries in October 2026, but its runner still measures them, so ours, Joy's and vanillajs's are kept.

Run it#

The benchmark lives outside the repository, in a clone of krausest/js-framework-benchmark with its runner installed, the other entries built and a Chrome for the runner; set it up once, as benchmarks/jsframework/README.md says. The runner needs a small patch (in the same folder): it counted events from before tracing began as the click's. Then:

The runner is headless, the benchmark's server on port 8089; each round runs one benchmark at a time for every entry, the second round in reverse order. Run it on mains, with nothing else heavy running. Results land in site/js-framework-benchmark.json, which this page reads. Like the examples' numbers, they're measured only when asked, never by the site's build.
